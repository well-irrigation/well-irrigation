# مراجعة هجرات قاعدة البئر

**النوع:** مهارة داخلية خاصة بالمشروع.

## حدود لا تتجاوز

1. ابدأ بـ`AGENTS.md` ثم `npm run c:state` مرة واحدة في الجلسة.
2. استخرج السقف والرقم التالي من `AGENTS.md` وحده؛ لا تنسخ رقمًا ثابتًا من
   هذه المهارة أو وثيقة تاريخية.
3. الهجرات المختومة لا تعدّل. التراجع بهجرة جديدة.
4. لكل هجرة جديدة اختبار دائم واحد على الأقل في `supabase/tests`.
5. لا تشغّل `db:reset` أو `db:test` أو `db:index` أو Docker أو تحقق السحابة؛
   جهّز للمالك أوامر متوافقة مع `TERMINAL_COMMAND_PROTOCOL.md`.
6. لا تقرأ هجرة قديمة كاملة لإثبات schema. استخدم
   `docs/technical/db/*.txt`. يجوز قراءة الهجرة الجديدة نفسها لأنها موضوع
   المراجعة، لا بوصفها فهرسًا للتاريخ.

## سير المراجعة

### 1. العقد والأثر

حدّد: الكائنات المضافة أو المعاد تعريفها، العقود العامة المتأثرة، من يقرأ
ومن يكتب، الأثر المالي/التاريخي، طريقة التراجع، وهل التوثيق الحاكم يسمح به.
ارفض UI أو Flutter مبنيًا على عقد متخيّل.

### 2. سلامة المعاملة والبيانات

- الهجرة ذرية بقدر الإمكان، وترتيبها لا يترك نافذة صلاحيات واسعة.
- القيود والفهارس تطابق invariant المجال ولا تكرر مصدر حقيقة آخر.
- لا حذف نهائي لسجل مالي أو تشغيلي.
- المال `BIGINT` بالريال الكامل، والزمن `timestamptz`، ولا تقريب.
- أوامر إعادة التشغيل لا تكرر أثرًا؛ استخدم Idempotency حيث يتطلب المجال.

### 3. حد Data API

- `api` هو السطح المكشوف وحده لمنطق الأعمال.
- دوال `api` تبقى `SECURITY INVOKER`، ولا EXECUTE لـ`anon`.
- كل دالة جديدة تسحب `PUBLIC` صراحة قبل grants المحددة.
- لا Direct DML لـ`authenticated` أو `anon` على المخططات الداخلية.
- الدالة الداخلية `SECURITY DEFINER` تضبط `search_path` الموثوق وتتحقق من
  الهوية والصلاحية الخادمية؛ لا تثق بمعرف actor من العميل.
- RLS وgrants والفحص المسمّى طبقات مستقلة؛ نجاح طبقة لا يعوض غياب الأخرى.

### 4. اختبار القبول الدائم

يجب أن يثبت الاختبار، حسب الانطباق:

- وجود التوقيع والخصائص والمنح الصحيحة.
- رفض `anon` والفاعل غير المخول.
- عزل بئرين/مستأجرين وعدم وجود IDOR.
- النجاح المصرح به والنتيجة المجالية الصحيحة.
- إعادة المحاولة دون تكرار أثر.
- الحالات الحدية والفشل المغلق.
- بقاء Direct DML وAPI SECURITY DEFINER وanon EXECUTE عند الصفر.

لا تجعل الاختبار يكرر جسم التنفيذ أو يحرس صيغة خاطئة؛ اختبر الخاصية.

## التسليم للمالك

عند الحاجة إلى تحقق قاعدة، سبقه بأربعة أسطر: وضع المالك الآن، وما سيتغير،
ولماذا، وترجمة المصطلح. كل سطر أمر أقل من 60 محرفًا كما يفرض البروتوكول.
لا تذكر PASS قبل أن يعيد المالك ناتج التشغيل.

## توافق الوكلاء

- **ZCode وClaude Code:** نفس سير القراءة والكتابة؛ اختلاف الأدوات لا يغير
  توزيع المسؤولية.
- وجود أدوات Supabase أو Shell أوسع في Claude Code لا يمنحه إذن تشغيل أوامر
  القاعدة أو السحابة.
- لا تحذف مهارات Supabase pentest؛ هذه مراجعة هجرة بيضاء الصندوق، وتلك
  تدقيقات شبكية مصرح بها منفصلة.

## بوابة ما قبل التسليم

- [ ] الرقم مشتق من المصدر الحاكم والهجرة المختومة لم تُمس.
- [ ] يوجد اختبار دائم مرتبط بالهجرة.
- [ ] Data API وRLS وgrants وsearch_path مفحوصة.
- [ ] اختبار السلوك السلبي وعدم التكرار موجود عند الانطباق.
- [ ] لم يُشغّل الوكيل أمرًا محجوزًا للمالك.
- [ ] أي حالة Verified مدعومة بناتج فعلي.
