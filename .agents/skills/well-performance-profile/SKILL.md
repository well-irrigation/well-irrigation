# قياس أداء تطبيق البئر

**النوع:** مهارة داخلية خاصة بالمشروع.

## قاعدة القياس أولًا

1. طبّق `AGENTS.md` واقرأ مسار الاستخدام الحاكم.
2. شغّل `npm run c:state` مرة واحدة إن لم يكن قد شُغّل.
3. حدد سؤالًا واحدًا قابلًا للقياس: بدء بارد، تقطع قائمة، ذاكرة جلسة، أو
   طلبات زائدة. لا تبدأ بإعادة هيكلة عامة.
4. سجّل الجهاز، API level، build mode، نسخة التطبيق، البيانات، وحالة الشبكة.
5. Debug mode ليس دليل أداء إصدار؛ استخدم profile/release حيث يلزم وبأمان.

## القياسات

### بدء التشغيل

- افصل cold/warm start.
- خذ عدة تشغيلات واذكر الوسيط والمدى، لا أفضل رقم منفرد.
- لا تخلط زمن المصادقة أو الشبكة بزمن بناء أول frame دون توضيح.

### الإطارات وإعادة البناء

- قس frame times وjank أثناء سيناريو ثابت.
- استخدم Flutter DevTools/timeline أو أداة مكافئة.
- افحص build المتكرر، العمل المتزامن على UI isolate، الصور والقوائم.
- لا تضف `const` أو memoization بالجملة دون hotspot مثبت.

### الذاكرة ودورة الحياة

- قس baseline ثم بعد تكرار السيناريو ثم بعد الخروج منه.
- ابحث عن controllers/subscriptions/timers غير محررة وصور أو قوائم محتجزة.
- فرّق بين cache مقصودة وتسرب يتزايد مع كل دورة.

### البيانات والشبكة

- عدّ الطلبات وحجم الحمولة وزمنها والنداءات المكررة.
- لا تحل البطء بكسر `api.*` أو تحميل raw tables أو حساب totals في Flutter.
- cache لا يوصف Live ويجب أن يحافظ على صلاحيات وعزل الحساب.

### الحجم والبناء

- قس APK/AAB الفعلي حسب ABI وفسّر assets/native libraries الكبيرة.
- لا تحذف خطوطًا أو موارد لازمة للعربية والإتاحة لمجرد تقليل الحجم.

## دورة التحسين

1. ثبّت baseline وسيناريو إعادة الإنتاج.
2. حدد hotspot واحدًا من trace.
3. نفّذ أصغر تغيير لا يكسر المعمارية.
4. أعد القياس بنفس البيئة والبيانات.
5. شغّل اختبارات الهاتف وتحليل Dart.
6. اقبل التحسين إذا تحسن المؤشر المستهدف بلا regression وظيفي أو أمني.

لا تنسب تحسنًا إلى تغيير إذا اختلف الجهاز أو build mode أو البيانات.

## ميزانية الأداء

لا تخترع أرقام SLA. استخرج الميزانية من قرار مشروع أو قياس وتجربة مستخدم.
إن لم توجد، اعرض baseline ومقارنة قبل/بعد بوصفها قياسًا، واقترح قرارًا منفصلًا
للميزانية بدل تسميتها معيارًا معتمدًا.

## توافق الوكلاء

- **ZCode:** استخدم `android-dev` للأجهزة والسجلات حيث يغطي الحاجة، وأدوات
  Flutter المحلية للقياس.
- **Claude Code:** استخدم DevTools/ADB أو خطوات مالك مكافئة؛ لا تفترض MCP
  الخاص بـZCode.
- لا تحذف مهارات Flutter العامة؛ هذه المهارة تقيس قبل اختيار التحسين.

## بوابة ما قبل التسليم

- [ ] السيناريو والبيئة وbuild mode موثقة.
- [ ] توجد أرقام baseline فعلية لا انطباعات.
- [ ] المقارنة قبل/بعد بنفس الشروط.
- [ ] hotspot مثبت والاقتراح لا يكسر API/Offline/الإتاحة.
- [ ] لم يُستخدم Debug بوصفه أداء إنتاج.
- [ ] ما لم يُقَس معلن بوضوح.
