# تدقيق أمن Flutter وAndroid

**النوع:** مهارة داخلية خاصة بالمشروع.

## البداية الآمنة

1. طبّق `AGENTS.md` ومصادر الحقيقة قبل أي معيار خارجي.
2. شغّل `npm run c:state` مرة واحدة إن لم يكن قد شُغّل في الجلسة.
3. حدّد النطاق: مصدر، إعداد Android، أو APK/AAB.
4. لفحص APK/AAB استخدم مهارة `flutter-apk-security` بدل تكرار مسارها.
5. لا تنفذ اختبارًا شبكيًا أو هجوميًا دون تفويض واضح؛ هذه المهارة افتراضيًا
   مراجعة بيضاء الصندوق وقراءة محلية.
6. لا تعرض قيمة سر؛ استخدم المسار والنوع وبادئة/لاحقة مقنّعة عند الضرورة.

## نموذج التهديد الخاص بالمشروع

راعِ أن التطبيق مالي وميداني وOffline-first، وأن الهاتف قد يكون مشتركًا أو
مفقودًا، والاتصال متقطع، والطابور المحلي يحمل عمليات حرجة. افحص الحدود بين:

- مستخدمين مختلفين على الجهاز نفسه.
- بيانات محلية معلقة وبيانات مؤكدة خادميًا.
- تطبيق العميل و`api.*` والمخططات الداخلية.
- معرفات عامة مثل Supabase anon key وأسرار امتيازية مثل service role.

## محاور MASVS

### التخزين والخصوصية

- لا كلمات مرور أو رموز استعادة أو أسرار في SQLite أو Outbox أو logs.
- البيانات المحلية الخاصة معزولة حسب الحساب، وLogout لا يسرّب حسابًا لآخر.
- افحص النسخ الاحتياطي، ملفات debug، لقطات الشاشة، الحافظة، والسجلات.
- لا تعتبر تشفير قاعدة محلية علاجًا لتفويض مفقود.

### التشفير والمفاتيح

- لا خوارزمية أو مفتاح منزلي.
- الأسرار في تخزين المنصة المناسب، ولا مفاتيح ثابتة داخل Dart أو resources.
- TLS صحيح؛ pinning قرار تهديد لا نتيجة آلية عامة.

### المصادقة والجلسة

- هوية العمليات مشتقة من الجلسة لا من معرّف يرسله العميل.
- Logout/تعطيل الحساب/تغيير الهوية لا يترك وصولًا عابرًا بين الحسابات.
- الاستعادة لا تفشي وجود المستخدم ولا تسجل OTP.

### الشبكة والـAPI

- Flutter يتعامل مع `api.*` فقط ولا Direct DML.
- الفشل مغلق ولا يتحول إلى mock أو cache موصوفة Live.
- افحص المهلات وإعادة المحاولة ومنع تكرار الأثر، لا توفر الشبكة فقط.

### منصة Android

راجع `AndroidManifest.xml` وملفات Gradle وإعداد الشبكة:

- المكونات المصدرة وIntent filters والروابط العميقة.
- `allowBackup` وcleartext traffic وdebuggable.
- FileProvider والصلاحيات ومبدأ أقل صلاحية.
- WebView وMethodChannel إن وُجدا.

### جودة الكود والمقاومة

- لا بيانات حساسة في رسائل الخطأ أو analytics.
- لا تعتمد على obfuscation لإصلاح سر مضمن.
- تحقق من release flags والتوقيع في artifact، لا تستنتجها من المصدر وحده.

## إثبات النتائج

لكل نتيجة سجّل: فئة MASVS، المسار والسطر، المدخل/الفاعل، الأثر، الضابط
الحالي، الإصلاح الأدنى، وطريقة التحقق بعده. صنّفها P0–P3 حسب قابلية الوصول
والأثر، وميّز بين ثغرة مؤكدة وتقوية دفاعية.

## توافق الوكلاء

- **ZCode:** استخدم أدوات Android Emulator المتاحة للاختبار المصرح به، ولا
  تنشئ AVD أو تقبل رخصًا دون موافقة لازمة.
- **Claude Code:** استخدم أدوات Android/ADB المتاحة لديه أو سلّم خطوات الجهاز
  للمالك؛ لا تفترض وجود MCP الخاص بـZCode.
- احتفظ بمهارات Supabase وClaude Code كما هي؛ تستدعى منفصلة عند الحاجة ولا
  تستبدلها هذه المهارة.

## بوابة ما قبل التسليم

- [ ] فُصلت الحقائق العامة عن أسرار الامتياز.
- [ ] كل نتيجة قابلة للوصول وليست مطابقة نصية فقط.
- [ ] لم تُطبع أسرار أو بيانات حساسة.
- [ ] فُصل فحص المصدر عن إثبات artifact والجهاز.
- [ ] لا ادعاء MASVS كامل دون بيان النطاق والاستثناءات.
- [ ] التقرير يتبع عناوين المشروع الأربعة بالعربية.
