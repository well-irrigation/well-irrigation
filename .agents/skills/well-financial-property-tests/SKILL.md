# اختبارات الخصائص المالية

**النوع:** مهارة داخلية خاصة بالمشروع.

## مصادر الحقيقة

1. اقرأ `AGENTS.md` ثم `technical/INVARIANTS.md` والوثيقة المالية الخاصة
   بالموضوع.
2. شغّل `npm run c:state` مرة واحدة إن لم يُشغّل في الجلسة.
3. لا تستخرج قاعدة مالية من الكود المراد اختباره؛ الكود هو المتهم، والقرار
   أو invariant هو oracle الاختبار.
4. لا تضف dependency عشوائية لاختبار الخصائص. ابدأ بحلقات حتمية وبيانات
   مولدة ببذرة ثابتة، ولا تضف حزمة إلا عند حاجة مثبتة وبإصدار مقيد.

## خصائص إلزامية حسب المجال

### المال والوقت

- كل قيمة مالية عدد صحيح بالريال اليمني الكامل؛ لا `double` أو `float`.
- لا تقريب للوقت أو المال.
- تكلفة كل مقطع تحسب بالقسمة الصحيحة منفصلًا ثم تجمع؛ لا تقسم مجموع الثواني.
- الجلسة غير المقفلة لا تدخل مجاميع يوم، ويوم الجلسة يوم النهاية.
- الحدود الزمنية تتبع منطقة البئر ولا تتأثر بمنطقة جلسة قاعدة البيانات.

### الفواتير والدفعات

- الفاتورة ليست دفعة.
- `paid + outstanding = total` للحالة السارية.
- زيادة الدفعة تبقى Advance ولا تنتج متبقيًا سالبًا.
- إعادة الأمر بنفس Command ID لا تنشئ دفعة أو تخصيصًا أو فاتورة ثانية.
- نتيجة مجهولة لا تعاد كأمر جديد قبل reconciliation.

### الحصص والتوزيع

- مجموع النسب مليون جزء دائمًا.
- مجموع التوزيعات يساوي المبلغ القابل للتوزيع.
- كامل باقي القسمة يذهب لصاحب أكبر حصة وفق القرار الحاكم.
- تغيّر الحصص لا يعيد حساب فترة تاريخية مغلقة.

## تصميم مجموعة الاختبار

1. اكتب مثالًا حارسًا معروفًا، ثم خاصية عامة، ثم حدودًا سالبة.
2. استخدم بذرة ثابتة واطبعها عند الفشل حتى يمكن إعادة الحالة.
3. ولّد أعدادًا ضمن حدود `int`/`BIGINT` الآمنة، وأضف حالات قرب الصفر والحد
   الأعلى ومعاملات تؤدي إلى باقي قسمة.
4. لا تستخدم نفس دالة الإنتاج لحساب expected.
5. عند فشل حالة مولدة، اختزلها إلى أصغر مثال regression دائم.
6. اختبر invariants لا تفاصيل ترتيب أو صياغة غير حاكمة.

## فصل طبقات الاختبار

- **Dart unit test:** تحويلات العرض والمنطق النقي المسموح في العميل.
- **Flutter widget test:** عدم عرض صفر كاذب، التفقيط، وحالات pending/confirmed.
- **PostgreSQL test:** الحساب والتفويض والذرية وIdempotency؛ يكتبه الوكيل
  ويشغّله المالك فقط.
- لا تنقل Accounting Engine إلى Flutter لمجرد سهولة الاختبار.

## التحقق

شغّل الاختبار المستهدف ثم `flutter analyze` و`flutter test` داخل
`apps/mobile` عند تغير الهاتف. لا تشغّل فحوص القاعدة. سجّل الأرقام التي خرجت
فعليًا فقط، وميّز Implemented عن Verified.

## توافق الوكلاء

- **ZCode:** استخدم أدوات الملفات وFlutter المتاحة مباشرة.
- **Claude Code:** استخدم الأدوات المكافئة؛ لا تجعل توفر subagents شرطًا.
- مهارات Dart العامة تبقى مفيدة لبنية الاختبار، وهذه المهارة تضيف oracle
  المالي الخاص بالمشروع ولا تستبدلها.

## بوابة ما قبل التسليم

- [ ] كل خاصية مرتبطة بقرار أو invariant.
- [ ] لا أعداد عشرية في المال ولا حساب موازٍ في Flutter.
- [ ] التوليد حتمي وقابل لإعادة الفشل.
- [ ] توجد حالات صلاحية/إعادة محاولة عند الحاجة.
- [ ] expected مستقل عن implementation.
- [ ] لا نتيجة نجاح دون تشغيل فعلي.
