# مراجعة الكود الآمنة لمشروع البئر

**النوع:** مهارة داخلية خاصة بالمشروع.

## السلطة وحدود التنفيذ

1. اقرأ `AGENTS.md` أولًا، وهو أعلى من هذه المهارة.
2. إن لم يُشغّل `npm run c:state` في الجلسة، شغّله مرة واحدة فقط.
3. خذ المواصفة والحالة من مصادر الحقيقة التي يحددها
   `docs/PROJECT_MAP.md`، ولا تستنتج المطلوب من اسم الفرع وحده.
4. لا تستخدم وكلاء فرعيين؛ وجودهم في Claude Code لا ينسخ منع المشروع.
5. المراجعة قراءة فقط ما لم يطلب المالك إصلاح النتائج صراحة.
6. لا تشغّل أوامر القاعدة أو الشبكة أو Git history؛ يسلّمها الوكيل للمالك
   وفق `TERMINAL_COMMAND_PROTOCOL.md`. يجوز للوكيل تشغيل فحوص الهاتف فقط.

## سير المراجعة

### 1. ثبّت نطاق المقارنة

- استخدم المرجع الذي حدده المستخدم.
- عند غيابه، قارن التغييرات الحالية مع نقطة الدمج مع `main`، مع إبقاء
  التغييرات غير المحفوظة ضمن النطاق.
- لا تخلط عيوبًا قديمة خارج الفرق بنتائج المراجعة؛ اذكرها منفصلة إن كانت
  تمنع التحقق من التغيير.

### 2. اربط الفرق بالمطلوب

استخرج المتطلبات القابلة للاختبار من الوثيقة الحاكمة، ثم صنّف كل واحدة:
منفذة، جزئية، مفقودة، أو خارج النطاق. افصل بين:

- مطابقة المواصفة.
- مطابقة ثوابت `technical/INVARIANTS.md`.
- صحة السلوك وحالات الخطأ.
- أمن المصادقة والتفويض وعزل البيانات.
- كفاية الاختبارات وعدم وجود نجاح كاذب.

### 3. تتبّع المسار القابل للوصول

لا تبلغ عن تطابق نصي بوصفه ثغرة. لكل نتيجة حدّد:

- المدخل الحقيقي ومن يسيطر عليه.
- المسار إلى موضع الأثر.
- الحواجز الموجودة ولماذا لا تكفي.
- الضرر القابل للتحقق ونطاقه.
- ملفًا وسطرًا ضيقين.

راجع خصوصًا: `api.*`، Direct DML، RLS والمنح، `auth.uid()`، المال الصحيح،
Idempotency، الفشل المغلق، وعدم تحويل خطأ الخادم إلى بيانات بديلة.

### 4. قيّم الاختبارات

- ابحث عن اختبار يفشل قبل الإصلاح ويمر بعده، لا عن زيادة عدد الاختبارات فقط.
- افحص الحالات السالبة، حدود الصلاحية، إعادة المحاولة، والقيم الحدية.
- لا تصف شيئًا Verified إن لم يُشغّل دليله.

## شدة النتائج

- **P0:** كشف سر امتيازي، فساد مالي/تاريخي واسع، أو تجاوز عزل مؤكد.
- **P1:** خلل أمني أو وظيفي قابل للوصول يمنع الدمج أو الإنتاج.
- **P2:** نقص اختبار أو حالة حافة مهمة قد تسبب انحدارًا واقعيًا.
- **P3:** تحسين محدود لا يغيّر صحة السلوك الحالي.

لا ترفع الشدة بسبب الانطباع؛ اربطها بالاستغلال والأثر.

## التقرير

استخدم عناوين المشروع الأربعة. تحت «ما الحال الآن» ضع النتائج أولًا، مرتبة
بالشدة، وكل نتيجة تحمل: العنوان، الدليل، الأثر، والإصلاح الأدنى. إذا لم توجد
نتائج، قل ذلك صراحة واذكر ما فُحص وما لم يمكن إثباته. لا تملأ التقرير بملخص
تنفيذي قبل النتائج.

## توافق الوكلاء

- **ZCode:** استخدم أدوات القراءة والبحث والفروق المتاحة، وتعليقات السطر عند
  الحاجة فقط.
- **Claude Code:** استخدم أدواته المكافئة، لكن لا تفعل مسار الوكلاء الفرعيين
  الموجود في مهارة `code-review` إلا إذا طلب المالك ذلك صراحة.
- لا تعدّل أو تحذف `code-review`؛ فهي محفوظة لجلسات Claude Code التي يختارها
  المالك.

## بوابة ما قبل التسليم

- [ ] النطاق ونقطة المقارنة مثبتان.
- [ ] كل نتيجة داخل الفرق ولها مسار قابل للوصول.
- [ ] استُشهد بالمصدر الحاكم، لا بذاكرة المحادثة.
- [ ] لم تُعرض ملاحظة أسلوبية كنتيجة أمنية.
- [ ] حالة الاختبارات دقيقة: لم يُشغّل ≠ نجح.
- [ ] التقرير عربي ومساراته قابلة للنقر.
