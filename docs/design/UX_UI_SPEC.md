# مواصفات تجربة المستخدم والواجهات — إدارة البئر والسقي

**الحالة:** وثيقة حية معتمدة — 2026-08-18
**النطاق:** Stage 7 — الصفحات والأقسام والأزرار والسلوك
**الهوية البصرية الحاكمة:** `VISUAL_IDENTITY.md`

---

## 1. الغرض

هذه الوثيقة هي المصدر التفصيلي لقرارات تجربة المستخدم
والواجهات بعد اعتماد الهوية البصرية العامة.

تُوثق كل شاشة أو قسم رئيسي فور انتهاء مناقشته واعتماده،
وقبل الانتقال إلى تنفيذ واجهة إنتاجية.

---

## 2. منهج التوثيق المعتمد

الدورة المعتمدة لكل شاشة أو قسم:

1. مناقشة تجربة المستخدم والسلوك.
2. حسم العناصر والأقسام والأزرار والحالات الضرورية.
3. اعتماد المالك.
4. توثيق النتيجة مباشرة في هذه الوثيقة.
5. تحديث `memory/RESUME_POINT.md`.
6. الانتقال إلى الشاشة أو القسم التالي.

لا يُنشأ ملف مستقل لكل شاشة.

تجمع الشاشات داخل هذه الوثيقة كفصول متتابعة حتى تبقى
رحلة المستخدم قابلة للقراءة من البداية إلى النهاية.

القرارات العامة التي تغير قاعدة على مستوى التطبيق كله
يمكن رفعها إلى قرار مرقم مستقل في `memory/DECISIONS.md`.

---

## 3. قالب توثيق الشاشة

كل شاشة توضح عند الحاجة:

- معرف الشاشة واسمها.
- حالة الاعتماد.
- متى تظهر.
- الغرض.
- ما يراه المستخدم.
- الأقسام والعناصر.
- الأزرار والإجراءات.
- السلوك والانتقالات.
- حالات التحميل والفراغ والخطأ.
- متطلبات الوضوح وإمكانية الوصول.
- الأمور المؤجلة أو غير المحسومة.

لا تُضاف عناصر لم تُناقش أو تعتمد.

# UX-00 — Splash Screen / شاشة البداية

**الحالة:** معتمدة — 2026-08-17
**قرارات المناقشة:** 137–140

## متى تظهر؟

تظهر عند تشغيل التطبيق وفق سلوك Android الطبيعي
لشاشة البداية.

ليست صفحة تشغيلية يتفاعل معها المستخدم.

## الغرض

- انتقال بصري نظيف عند فتح التطبيق.
- إظهار هوية المنتج أثناء استعداد التطبيق.
- عدم تعطيل المستخدم بانتظار مصطنع.

## 137 — الخلفية

**المعتمد:**

خلفية بيضاء باردة بخفة.

ليست أبيض نقيًا حادًا، بل تميل بدرجة بسيطة جدًا
إلى الإحساس البارد المرتبط بالنظافة والماء والهدوء.

**غير محسوم بعد:**

قيمة اللون النهائية الدقيقة.

تحدد عند إعداد الأصل النهائي وتجربته بصريًا على جهاز حقيقي.

## 138 — العنصر المركزي

**المعتمد:**

استخدام نسخة محسنة من صورة الختم التي شاركها المالك سابقًا
بدل الاكتفاء بأيقونة التطبيق المنفردة.

شروط التحسين:

- الحفاظ على معنى وشخصية الختم الأصلي.
- تحسين الوضوح والتوازن على الهاتف.
- تبسيط التفاصيل التي تضيع عند الحجم الصغير إذا لزم.
- عدم إضافة زخارف أو عناصر جديدة غير معتمدة.

الختم المحسن مخصص لشاشة البداية.

أما أيقونة التطبيق فتبقى أصلًا مستقلًا ومبسطًا للاستخدام
كأيقونة النظام.

**حالة الأصل:**

النسخة الإنتاجية النهائية للختم المحسن لم تُجهز بعد.

## 139 — الحركة

**المعتمد:**

حركة Android الطبيعية والهادئة فقط.

لا تستخدم:

- حركة دوران للماء.
- تكبير أو تصغير استعراضي.
- مؤثرات متتابعة للشعار.
- حركة زخرفية مستمرة.

## 140 — مدة الظهور

**المعتمد:**

لا توجد مدة ثابتة مصطنعة.

تبقى شاشة البداية فقط بقدر الوقت الذي يحتاجه التطبيق
ليصبح جاهزًا، ثم ينتقل فورًا.

لا نفرض انتظارًا لمدة ثانيتين أو ثلاث لمجرد عرض الشعار.

## محتوى الشاشة

تحتوي فقط على:

- الخلفية البيضاء الباردة الخفيفة.
- الختم المحسن في مركز التكوين البصري.

ولا تحتوي على:

- أزرار.
- حقول إدخال.
- اسم مستخدم.
- اختيار بئر.
- قوائم.
- إعلان.
- شريط تقدم مصطنع.
- نسبة تحميل.
- رسالة ترحيب تشغيلية.

## ما بعد شاشة البداية

الوجهة التي ينتقل إليها المستخدم بعد Splash Screen
لم تُحسم ضمن UX-00.

ستناقش باعتبارها الخطوة التالية في رحلة المستخدم.

# UX-01 — App Entry Routing / توجيه الدخول إلى التطبيق

**الحالة:** معتمد — 2026-08-17
**قرارات المناقشة:** 141–143

## الغرض

تحديد مسار المستخدم مباشرة بعد UX-00 / شاشة البداية.

UX-01 ليست شاشة مرئية مستقلة، بل منطق توجيه يحدد
الواجهة التالية حسب حالة جلسة الدخول.

## 141 — التعريف الأولي

**المعتمد:**

لا توجد شاشات Onboarding / تعريف أولي قبل تسجيل الدخول.

لا تظهر شرائح تعريفية أو صفحة «ابدأ الآن» لمجرد أن
التطبيق يعمل لأول مرة على الجهاز.

## 142 — المستخدم غير المسجل

**المعتمد:**

إذا لم توجد جلسة دخول صالحة، ينتقل المستخدم مباشرة
إلى شاشة تسجيل الدخول.

وتعامل الجلسة المنتهية أو غير الصالحة كعدم وجود جلسة.

لا توجد صفحة ترحيب مستقلة قبل تسجيل الدخول.

## 143 — المستخدم صاحب الجلسة الصالحة

**المعتمد:**

إذا كانت جلسة الدخول صالحة، لا يطلب التطبيق تسجيل
الدخول مرة أخرى.

ينتقل المستخدم مباشرة إلى مساره داخل التطبيق وفق
UX-05 / التوجيه الذكي حسب أدواره الفعلية.

لا توجد شاشة عامة ثابتة يجب أن يمر بها كل المستخدمين.

## المسار المعتمد

    فتح التطبيق
        ↓
    UX-00 / Splash Screen
        ↓
    فحص جلسة الدخول
        ↓
    لا توجد جلسة صالحة
        ↓
    شاشة تسجيل الدخول

    توجد جلسة صالحة
        ↓
    UX-05 / التوجيه الذكي حسب الدور
        ↓
    المالك → الرئيسية
    المشغل فقط → التشغيل
    الشريك فقط → صفحة الشريك
    الأدوار المركبة → الرئيسية الموحدة

## ما لا يظهر بين شاشة البداية والوجهة

- لا Onboarding.
- لا صفحة ترحيب مستقلة.
- لا زر «ابدأ الآن».
- لا شاشة تحميل مصطنعة ثابتة.
- لا إعادة تسجيل دخول لصاحب الجلسة الصالحة.

# UX-02 — Login Screen / شاشة تسجيل الدخول

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 144–156

## الغرض

توفير دخول مباشر وبسيط للمستخدمين الذين لديهم حساب
في التطبيق، دون خيارات دخول متعددة أو خطوات غير ضرورية.

طريقة الدخول اليومية المعتمدة هي:

    رقم الهاتف + كلمة المرور

ولا يستخدم OTP كطريقة دخول يومية.

## 144–145 — هوية الدخول وطريقته

رقم الهاتف هو اسم المستخدم في التطبيق.

تظهر بادئة اليمن:

    +967

ويكتب المستخدم بقية الرقم بالأرقام الإنجليزية 0-9.

طريقة الدخول الوحيدة في النسخة الأولى:

- رقم الهاتف.
- كلمة المرور.

لا يوجد:

- بريد إلكتروني للدخول.
- Google Sign-In.
- دخول كضيف.
- OTP يومي.
- اختيار دور قبل تسجيل الدخول.

## 146 — إنشاء الحسابات

لا يوجد تسجيل ذاتي عام بعنوان «إنشاء حساب».

الحسابات التشغيلية المرتبطة ببئر ينشئها مالك البئر
ضمن بئره.

السوبر أدمن يستطيع إدارة وإنشاء الحسابات على مستوى
المنصة كلها وفق ق-85.

الاستثناء الوحيد في شاشة الدخول هو المسار الواضح:

**إنشاء بئر جديد**

وهو مخصص لشخص يريد إنشاء حساب مالك وبئر جديد،
وليس تسجيلًا عامًا بلا بئر أو مسؤولية محددة.

## 147 — استعادة كلمة المرور

لا يظهر زر «نسيت كلمة المرور؟» في النسخة الأولى
قبل اعتماد وتنفيذ مسار استعادة فعلي وموثوق.

يمكن إضافة مسار الاستعادة لاحقًا دون تغيير طريقة
الدخول الأساسية.

## 148 — أعلى الشاشة

يظهر:

- أيقونة الشعار المبسطة.
- اسم المنتج «إدارة البئر والسقي».
- عنوان «تسجيل الدخول».

لا يستخدم الختم الكامل الخاص بشاشة البداية هنا.

لا توجد عبارة تسويقية أو ترحيب طويل.

## 149 — رقم الهاتف

حقل واضح بعنوان:

**رقم الهاتف**

السلوك:

- +967 ظاهرة كبادئة.
- الأرقام الإنجليزية 0-9.
- لوحة أرقام مناسبة.
- يسمح باللصق.
- تزال المسافات والشرطات غير المهمة قبل المعالجة.
- لا يطلب من المستخدم إدخال مفتاح الدولة يدويًا كل مرة.

## 150 — كلمة المرور

حقل بعنوان:

**كلمة المرور**

- مخفية افتراضيًا.
- يوجد إجراء إظهار/إخفاء.
- لا تعرض شروط إنشاء كلمة المرور داخل شاشة الدخول.

## 151 — زر الدخول

زر رئيسي واضح:

**تسجيل الدخول**

لا توجد بجانبه طرق دخول أخرى.

ويظهر أسفله إجراء ثانوي واضح:

**إنشاء بئر جديد**

## 152 — حفظ الجلسة

لا يظهر خيار «تذكرني».

بعد نجاح الدخول يحتفظ التطبيق بالجلسة وفق سياسة
الجلسات المعتمدة.

وعند فتح التطبيق لاحقًا يطبق UX-01 ولا يطلب تسجيل
الدخول من جديد إذا كانت الجلسة صالحة.

## 153 — خطأ بيانات الدخول

لا يكشف التطبيق هل الخطأ في الهاتف أم كلمة المرور.

الرسالة:

**رقم الهاتف أو كلمة المرور غير صحيحة.**

يبقى رقم الهاتف المدخل ولا يمسح تلقائيًا.

## 154 — حالة التنفيذ

عند الضغط على «تسجيل الدخول»:

- يدخل الزر حالة انتظار هادئة.
- يمنع الضغط المتكرر.
- لا تفتح شاشة تحميل مستقلة.
- عند النجاح ينتقل المستخدم مباشرة إلى سياقه داخل التطبيق.
- عند الفشل يعود الزر إلى حالته الطبيعية وتظهر الرسالة.

## 155 — عدم وجود الإنترنت

إذا لم توجد جلسة صالحة وكان الدخول يحتاج اتصالًا،
تظهر رسالة:

**لا يوجد اتصال بالإنترنت. تحقق من الاتصال وحاول مرة أخرى.**

ويظهر إجراء:

**إعادة المحاولة**

ولا تمسح الحقول بسبب انقطاع الشبكة.

## 156 — التكوين البصري

التكوين بسيط ومتوسط الكثافة:

    [ أيقونة الشعار ]

    إدارة البئر والسقي
    تسجيل الدخول

    رقم الهاتف
    +967 | __________

    كلمة المرور
    __________________  إظهار/إخفاء

    [ تسجيل الدخول ]

    إنشاء بئر جديد

لا توجد صورة خلفية زراعية أو بطاقات كثيرة أو روابط
ثانوية غير ضرورية.

# UX-03 — Create New Well & Setup / إنشاء بئر جديد وإعداده

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 157–201 بالصيغ النهائية بعد التنقيحات

## الغرض

تمكين مالك جديد من إنشاء حسابه وبئره وإكمال الحد الأدنى
اللازم للتشغيل عبر خطوات قصيرة ومفهومة.

كما يستطيع مالك موجود مسبقًا إضافة بئر آخر من حسابه
الموحد دون إنشاء حساب جديد.

## 157 — نقطة الدخول

من شاشة UX-02 يظهر الإجراء:

**إنشاء بئر جديد**

تبدأ الرحلة بطلب رقم الهاتف.

بعد إدخال الرقم ينفذ التطبيق تلقائيًا في الخلفية تحقق
حق إنشاء بئر وفق ق-86.

لا يسأل المستخدم:

«هل لديك تفعيل؟»

ولا يطلب منه إدخال:

- كود ترخيص.
- مفتاح تفعيل.
- رقم فاتورة.
- رمز شراء يدوي.

إذا كان للرقم حق تفعيل متاح، يكمل التطبيق الرحلة
طبيعيًا دون شاشة أو سؤال إضافي.

إذا لم يوجد حق تفعيل متاح، تتوقف رحلة إنشاء البئر
وتظهر رسالة واضحة:

**هذا الرقم غير مفعّل لإنشاء بئر جديد. يرجى التواصل معنا لتفعيل البئر.**

وتظهر إجراءات مباشرة:

- **محادثة واتساب**
- **اتصال هاتفي**

ولا ينشأ حساب مالك جديد قبل اجتياز هذا التحقق.

إذا كان رقم الهاتف مرتبطًا بحساب موجود أصلًا،
لا ينشأ حساب ثان.

يسجل المستخدم الدخول إلى حسابه الموجود، وعند طلب
إضافة بئر جديد يخضع البئر الجديد لنفس تحقق حق التفعيل.

## 158 و162–163 — OTP

OTP هو رمز تحقق لمرة واحدة لإثبات ملكية رقم الهاتف،
وليس طريقة الدخول اليومية.

في النسخة الأولى:

- مالك جديد يتحقق من هاتفه أثناء إنشاء حسابه.
- الحساب الذي أنشأه المالك لشريك أو مشغل لا يرسل له
  OTP وقت الإنشاء.
- عند أول استخدام فعلي لذلك الحساب من هاتف صاحبه،
  يبدأ التحقق عبر OTP.
- تغيير الهاتف أو استعادة الحساب يمكن أن يستخدما OTP
  مستقبلًا بعد اعتماد مساراتهما.

المزود الأول المرشح تقنيًا هو Twilio لسهولة تكامله،
مع بقاء مزود SMS قابلًا للتغيير بعد اختبار التوصيل الفعلي.

أثناء التطوير يجوز استخدام Test OTP محلي فقط،
ولا يعد ذلك مسار إنتاج.

## 159 — الحساب الموجود

نفس رقم الهاتف لا ينشئ حسابًا جديدًا.

القاعدة الحاكمة موجودة تفصيليًا في ق-84:

    رقم هاتف واحد
        =
    شخص واحد
        =
    حساب تطبيق واحد

إذا كان الشخص موجودًا أصلًا تضاف له العلاقة أو الدور
الجديد فقط.

## 160 — معالج إعداد مبسط

تجمع رحلة إنشاء البئر في خمس مراحل مفهومة:

    1. حساب المالك
        ↓
    2. بيانات البئر
        ↓
    3. الشركاء
        ↓
    4. فريق التشغيل
        ↓
    5. تجهيز التشغيل
        ↓
    جاهز

لا تعرض بنية قاعدة البيانات الداخلية للمستخدم.

ولا توجد شاشة باسم Tenant أو «الجهة» لمجرد أن قاعدة
البيانات تستخدم هذا المفهوم داخليًا.

## 161 و172 — الحفظ والاستكمال

يستطيع المالك التوقف والعودة لاحقًا.

يحفظ النظام تقدم الإعداد.

يجب أن يوجد مفهوم مستقل لحالة الإعداد مثل:

- draft / الإعداد غير مكتمل.
- ready / جاهز للتشغيل.

ولا يستخدم status التشغيلي للبئر كبديل غير دقيق
عن حالة الإعداد.

تنفيذ هذا السلوك يحتاج إضافة Backend مستقبلية.

## 164 — إنشاء حساب المالك

يطلب من المالك الجديد الحد الأدنى:

- الاسم الكامل الحقيقي.
- رقم الهاتف الفريد.
- كلمة المرور.
- تأكيد كلمة المرور.

ثم يتحقق من رقم الهاتف عبر OTP.

لا يطلب بريدًا إلكترونيًا.

## 165 — Tenant داخلي فقط

مفهوم Tenant يبقى داخليًا.

عند إنشاء أول بئر ينشئ النظام البنية الداخلية اللازمة
دون مطالبة المستخدم بفهمها أو تسميتها ككيان تقني.

عند إنشاء بئر ثانٍ لنفس الحساب لا ينشأ حساب مستخدم جديد.

## 166 — بيانات البئر الأساسية

الحد الأدنى:

- اسم البئر: إلزامي.
- المحافظة: مطلوبة في الإعداد الأول.

ويمكن إكمال لاحقًا:

- المديرية.
- القرية أو المنطقة.
- وصف الوصول.
- GPS.
- تفاصيل الموقع الأخرى الموجودة في النموذج.

الهدف عدم تحويل الإنشاء الأول إلى استبيان طويل.

## 167 — الشركاء

المالك المنشئ يضاف تلقائيًا ضمن هيكل ملكية البئر.

إذا لم يوجد شركاء آخرون تطبق عليه النسب الكاملة وفق
قواعد الملكية والأرباح الحاكمة.

عند إضافة شريك جديد يطلب الحد الأدنى الحقيقي اللازم:

- الاسم الكامل الحقيقي.
- رقم الهاتف الفريد.
- كلمة مرور الدخول الأولى.
- نسبة الملكية.
- نسبة الأرباح.
- البيانات الإضافية المطلوبة عند الحاجة لحسم الهوية.

يمكن أن تكون نسبة الأرباح مساوية لنسبة الملكية افتراضيًا
لتقليل الإدخال، مع السماح بفصلها وفق القواعد الموثقة.

تطبق جميع قيود النسب المالية السابقة دون إعادة تعريفها
أو تجاوزها داخل UX.

## حساب الشريك

إضافة الشريك من المالك تنشئ حساب التطبيق الخاص به
مباشرة وتربطه بالشريك.

لا ينتظر النظام أن يفتح الشريك التطبيق حتى يصبح شريكًا.

من لحظة الحفظ يعامل كشريك كامل في:

- الملكية.
- الأرباح.
- التقارير.
- البيانات التشغيلية المسموح له بها.
- الإشعارات والسجلات المتعلقة به.

عدم فتح التطبيق لا يوقف حقوقه أو حساباته أو إشعاراته
المحفوظة داخل النظام.

إشعار Push إلى جهاز فعلي لا يمكن إرساله قبل تسجيل جهاز
قابل للاستقبال، لكن سجل الإشعار وحق الشريك لا يتوقفان.

## 168 و175 و186 — المشغلون والتفعيل الأول

المالك يستطيع إضافة مشغل من إعداد البئر.

عند إنشاء حساب شريك أو مشغل بواسطة المالك:

- ينشأ الحساب فورًا.
- لا يرسل OTP عند الإنشاء.
- ينشئ المالك كلمة مرور الدخول الأولى.
- عندما يحاول صاحب الحساب استخدامه لأول مرة،
  يتحقق النظام من كلمة الدخول الأولى ثم يرسل OTP.
- بعد نجاح OTP يطلب من المستخدم تعيين كلمة مرور شخصية
  جديدة لا يعرفها المالك.
- بعدها يصبح الدخول اليومي رقم الهاتف + كلمة المرور
  الشخصية فقط.

هذا يحتاج First Activation Flow / مسار تفعيل أول
على Backend موثوق ولا ينفذ بمفتاح إداري داخل Flutter.

## 169 — المضخة

وجود مضخة فعالة واحدة على الأقل جزء من جاهزية التشغيل.

في الإعداد الأول نطلب الحد الأدنى:

- اسم المضخة: إلزامي.
- النوع: اختياري.
- القدرة: اختيارية.

التفاصيل الفنية الأخرى يمكن استكمالها لاحقًا.

إدارة المضخة من Flutter تحتاج عقد API مناسب قبل التنفيذ.

## 170 — خطوط المياه

إعداد خطوط المياه غير إلزامي لإكمال الإنشاء الأول.

يمكن إضافتها لاحقًا.

تبقى بنيتها الحالية وقواعد التوازي مصدرًا وظيفيًا عند
استخدامها، لكن لا نثقل بها المالك في البداية.

## 171 — مصادر الطاقة والأسعار

يختار المالك مصادر التشغيل التي يستخدمها البئر.

تعرض فقط الحقول المتعلقة بالمصادر المختارة.

تضبط الأسعار اللازمة قبل اعتبار البئر جاهزًا للتشغيل،
لأن الجلسة التشغيلية لا يجوز أن تبدأ دون تسعير صالح
وفق قواعد الأعمال الحالية.

## جاهزية البئر

لا يعتبر البئر جاهزًا للتشغيل قبل الحد الأدنى التالي:

- حساب مالك صالح ومؤكد الهاتف.
- إنشاء البئر وربط المالك به.
- اكتمال هيكل الشركاء وفق القيود المالية الحاكمة.
- مضخة فعالة واحدة على الأقل.
- تسعير صالح لمصادر التشغيل المختارة.

ولا يشترط في الإنشاء الأول:

- GPS.
- خط مياه.
- مشغل مستقل عن المالك.
- إدخال كل مزارعي المنطقة مسبقًا.
- إدخال كل الأراضي مسبقًا.

## 173 و179 — رقم الهاتف والهوية

رقم الهاتف في التطبيق هو اسم مستخدم وهوية حساب،
وليس مجرد جهة اتصال.

تفاصيل القاعدة الحاكمة في ق-84.

ممنوع إنشاء شخصين أو حسابين داخل النظام بنفس رقم
الهاتف المطبّع.

## 180 — كشف التكرار والتأكيد

يستمر استخدام التطبيع العربي وكاشف التشابه ومنطق
منع التكرار الموجود سابقًا، لكن سلوك UX النهائي هو:

### تطابق رقم الهاتف

إذا كان الرقم موجودًا:

- لا يسمح بإنشاء شخص جديد.
- يعاد استخدام الشخص والحساب الموجودين.
- يمكن إضافة دور أو علاقة جديدة فقط.

لا يوجد خيار «شخص آخر بنفس الرقم».

### تشابه الاسم مع رقم مختلف

إذا وجد اسم مطابق أو شديد التشابه برقم مختلف،
يعرض النظام تنبيهًا بسيطًا:

**وجدنا شخصًا باسم مشابه. هل هو نفس الشخص؟**

إذا كان هو نفسه:

- يربط بالسجل الموجود.
- لا ينشئ شخصًا جديدًا.

إذا اختار المستخدم «شخص آخر»:

- لا يكفي الضغط على الزر وحده.
- يجب أن تكون هناك بيانات حقيقية تميز الشخص الجديد.
- رقم هاتف مختلف وفريد شرط أساسي.
- إذا بقي الاشتباه مرتفعًا، يطلب النظام معلومة تعريفية
  إضافية حقيقية فقط عند الحاجة، مثل اسم الأب أو اسم
  العائلة أو رقم هوية إذا كان متاحًا.

لا نطلب هذه البيانات الإضافية من الجميع؛ تظهر فقط
عند حالة الاشتباه التي تحتاج حسمًا.

## 181 و183 — الحساب الموحد وتعدد الأدوار

لا يملك الشخص حسابًا مستقلًا لكل دور أو بئر.

يسجل الدخول مرة واحدة.

ثم يجمع الحساب الواحد جميع علاقاته، مثل:

- مالك في بئر.
- شريك في بئر آخر.
- مشغل في بئر ثالث.
- أكثر من دور في البئر نفسه.
- أدوار في عدة آبار.

لا توجد شاشة «ادخل كمالك» أو «ادخل كمشغل».

الواجهة تقرأ الأدوار الفعلية وتعرض لكل بئر ما يسمح
به دور المستخدم فيه.

## 182 — بياناتي كمزارع

إذا كان صاحب حساب التطبيق نفسه مسجلًا كمزارع/عميل سقي
في بئر آخر يستخدم التطبيق، ترتبط بياناته بحسابه الموحد
برابط هوية صريح ومؤكد.

يظهر له قسم:

**بياناتي كمزارع**

في النسخة الأولى يكون القسم للعرض والمتابعة، ويجمع
بياناته الشخصية عبر الآبار المسجلة التي يسقي منها، مثل:

- الآبار.
- الأراضي التابعة له.
- جلسات السقي.
- الساعات.
- التكاليف والفواتير.
- المدفوعات.
- الرصيد المستحق أو المتبقي.
- التاريخ التشغيلي المرتبط به.

لا يمنحه هذا القسم صلاحيات إدارية على البئر الآخر.

يرى فقط بياناته التي تخصه كمزارع وفق سياسات الوصول.

لا يجوز ربط Farmer Well Account بحساب دخول عبر
تشابه الاسم أو التخمين.

يلزم رابط هوية صريح وحتمي.

## 184 — المزارع العادي

حساب دخول المزارع العادي الذي لا يملك دورًا آخر في
التطبيق مؤجل إلى نسخة لاحقة.

هذا التأجيل لا يلغي تسجيل المزارع تشغيليًا داخل البئر.

تظل سجلات:

- المزارع.
- الأرض.
- جلسات السقي.
- الفواتير.
- المدفوعات.
- الأرصدة.

جزءًا من النظام التشغيلي في النسخة الأولى.

التأجيل يخص حساب دخول المزارع وواجهته الذاتية فقط.

## 176 و185 — المناوب الافتراضي

لا نبني جدول دوام مسبق في النسخة الأولى.

المستخدم الذي يفتح Shift / المناوبة يصبح المناوب الفعلي.

المالك نفسه هو المشغل/المناوب الافتراضي الأول للبئر،
لأن صلاحيات المالك تسمح له بالتشغيل.

لا يجبر على إنشاء حساب مشغل مستقل.

إذا كان لديه عامل أو مشغل آخر يختار:

**إضافة مشغل آخر**

ويمكن إضافة أكثر من مشغل عند الحاجة.

## 187–201 — حق تفعيل البئر وضبط الانتشار العشوائي

المصدر الحاكم لهذه القاعدة هو ق-86.

### المبدأ التجاري

النسخة الأولى بيع مباشر يدوي وليست اشتراكًا.

كل عملية شراء تمنح:

**حق إنشاء وتفعيل بئر واحد.**

إذا اشترى المالك أكثر من بئر، يمنح عددًا مطابقًا من
حقوق التفعيل.

لا تعطي عملية شراء واحدة حق إنشاء عدد غير محدود من
الآبار.

### مشاركة ملف التطبيق

لا يحاول النظام منع نسخ APK أو إرساله إلى أشخاص آخرين.

نسخ التطبيق أو تثبيته لا يمنح حق إنشاء بئر.

القيمة التجارية محمية في الخادم:

    APK
        ↓
    يمكن تثبيته
        ↓
    إنشاء بئر جديد
        ↓
    تحقق تلقائي من الهاتف
        ↓
    حق تفعيل متاح؟
        ↓
    نعم: متابعة
    لا: تواصل للتفعيل

وبذلك يمكن أن تتحول مشاركة التطبيق إلى وسيلة تعريف
بالمنتج بدل الاعتماد على DRM معقد.

### التحقق التلقائي

يتم التحقق من حق التفعيل تلقائيًا بعد إدخال رقم الهاتف.

لا يظهر سؤال للمستخدم عن حالة التفعيل.

إذا كان الحق موجودًا، لا تظهر خطوة إضافية.

إذا لم يكن موجودًا، تظهر الرسالة:

**هذا الرقم غير مفعّل لإنشاء بئر جديد. يرجى التواصل معنا لتفعيل البئر.**

وتظهر:

- **محادثة واتساب**
- **اتصال هاتفي**

أرقام وقنوات التواصل الرسمية تحدد مركزيًا عند التنفيذ.

### ربط البيع بالهاتف

عند استلام المبلغ يدويًا يسجل السوبر أدمن عملية البيع
ويربط حق التفعيل برقم الهاتف الفريد للمشتري.

رقم الهاتف نفسه هو الهوية المستخدمة لاحقًا لإثبات
استحقاق التفعيل.

لا يوجد كود ترخيص منفصل يحتاج العميل إلى حفظه.

عند إنشاء حساب مالك جديد:

- يوجد حق تفعيل مسبق للرقم.
- يثبت العميل ملكية الرقم عبر OTP.
- ينشأ الحساب.
- ينشأ البئر.
- يستهلك حق التفعيل فقط عند نجاح إنشاء البئر.

### استهلاك الحق ذريًا

لا يستهلك حق التفعيل عند:

- إرسال APK.
- فتح التطبيق.
- إدخال الهاتف.
- إرسال OTP.
- إنشاء الحساب وحده.

يستهلك فقط عندما ينجح إنشاء البئر وربط التفعيل به.

يجب أن تكون العملية ذرية:

    إما إنشاء البئر + استهلاك الحق معًا
    أو لا يحدث أي منهما

إذا فشل إنشاء البئر تقنيًا، يبقى حق التفعيل متاحًا.

### التفعيل الدائم

حق التفعيل في النسخة الأولى دائم ولا يحمل تاريخ انتهاء.

ليس اشتراكًا شهريًا أو سنويًا.

الحالات الأساسية المقترحة:

- available / متاح.
- consumed / مستخدم ومرتبط ببئر.
- revoked / ملغي إداريًا بسبب حالة موثقة.

الإلغاء الإداري ليس انتهاء اشتراك دوريًا، ولا يستخدم
عشوائيًا لإيقاف عميل اشترى حقًا دائمًا.

### البئر هو وحدة البيع

حق التفعيل بعد استهلاكه يرتبط بالبئر.

إذا تغير مالك البئر مستقبلًا وفق إجراء نقل ملكية معتمد،
يبقى التفعيل مع البئر ولا يجبر المالك الجديد على شراء
التطبيق مرة أخرى للبئر نفسه.

حذف البئر أو تعطيله لا يعيد حق التفعيل تلقائيًا.

أي تصحيح أو تحرير أو نقل استثنائي لحق مستخدم يتم بواسطة
السوبر أدمن مع تسجيل السبب في Audit / سجل التدقيق.

### عدة آبار لنفس المالك

الحساب الواحد يستطيع امتلاك عدة آبار.

كل بئر جديد يحتاج حق تفعيل مستقلًا.

مثال:

    حقوق مشتراة = 3
    مستخدمة = 1
    متاحة = 2

إضافة بئر جديد تستهلك حقًا واحدًا فقط عند نجاح الإنشاء.

### الأجهزة وإعادة التثبيت

التفعيل لا يرتبط بـ:

- IMEI.
- Android ID.
- جهاز بعينه.
- نسخة APK بعينها.

إذا غير المالك هاتفه أو أعاد تثبيت التطبيق:

- يسجل الدخول إلى حسابه نفسه.
- تظهر آباره المرخصة.
- لا يشتري التفعيل مرة أخرى.

### الشركاء والمشغلون

لا يحتاج الشريك أو المشغل أو المناوب إلى شراء تفعيل
مستقل لاستخدام بئر مرخص.

التفعيل يتعلق بالبئر وليس بعدد مستخدميه.

يمكن إرسال APK إلى الشركاء والمشغلين، ويسجل كل منهم
بحسابه وصلاحياته المعتمدة.

### الإنترنت

يلزم الاتصال بالخادم في العمليات التي تحتاج تحققًا
مركزيًا مثل:

- التحقق من حق إنشاء بئر.
- إنشاء حساب المالك الجديد.
- OTP.
- إنشاء البئر واستهلاك حق التفعيل.

بعد تفعيل البئر لا يفرض النظام فحص ترخيص متكررًا كل
عدة دقائق أو ساعات.

تبقى استراتيجية Offline / العمل دون اتصال حاكمة
للعمليات التي صممت لدعمها.

### تسجيل البيع يدويًا

النسخة الأولى لا تحتاج نظام اشتراكات أو بوابة دفع.

يكفي أن يستطيع السوبر أدمن تسجيل حق تفعيل يحتوي على
المعلومات اللازمة مثل:

- رقم هاتف المشتري.
- عدد حقوق التفعيل، والافتراضي 1.
- المبلغ المدفوع عند الحاجة للسجل الإداري.
- تاريخ الدفع.
- من منح الحق.
- ملاحظة اختيارية.
- حالة الحق.
- البئر المرتبط بعد الاستهلاك.
- وقت الاستهلاك أو الإلغاء عند حدوثه.

التصميم التقني النهائي للجدول والعقد يحدد عند بناء
Migration 078 أو أحدث.

### الخطأ في تسجيل البيع

إذا سجل حق التفعيل على رقم خاطئ ولم يستخدم بعد،
يستطيع السوبر أدمن تصحيحه أو إلغاؤه وفق إجراء موثق.

بعد استهلاك الحق وربطه ببئر، لا ينقل كتعديل عادي صامت.

تحتاج الحالة إلى إجراء إداري واضح مع تسجيل السبب.

### هدف الحماية

لا نحاول جعل ملف التطبيق غير قابل للنسخ.

الحماية الأساسية هي:

    رقم هاتف فريد
        +
    حق تفعيل مدفوع على الخادم
        +
    إنشاء البئر عبر عقد Backend محمي

حتى لو امتلك شخص نسخة APK، لا يحصل بذلك على حق إنشاء
بئر جديد دون تفعيل مدفوع مسجل له.

- استهلاك حق التفعيل وإنشاء البئر في عملية ذرية واحدة.
- إدارة السوبر أدمن لمنح وتصحيح وإلغاء حقوق التفعيل.
- سجل تدقيق لكل تغيير إداري على حقوق التفعيل.
- عدم ربط التفعيل بجهاز أو IMEI أو Android ID.
- إبقاء Direct DML ممنوعًا وفق ق-79.

لا تُعد هذه القائمة تنفيذًا.

هي قائمة مطابقة بين UX المعتمد وبين ما يجب توفيره
قبل بناء المسارات الإنتاجية.

# UX-04 — Unified Account Context / سياق الحساب الموحد

**الحالة:** معتمد سلوكيًا — 2026-08-18

بعد تسجيل الدخول لا يختار المستخدم هوية أو دورًا جديدًا.

يقرأ التطبيق حسابه الموحد وكل الآبار والأدوار المسموح
له بها، ويقدم السياق المناسب.

إذا كانت له بيانات مزارع مرتبطة بهويته صراحة،
يظهر قسم «بياناتي كمزارع» داخل الحساب نفسه.

تصميم الصفحة الرئيسية، مبدل الآبار، طريقة عرض الأدوار،
وشكل قسم «بياناتي كمزارع» ستناقش لاحقًا قبل تنفيذها.

# UX-05 — Role-Aware Landing / التوجيه الذكي حسب الدور

**الحالة:** معتمد — 2026-08-18
**قرارات المناقشة:** 202–211
**القرار العام الحاكم:** ق-87

## الغرض

توجيه المستخدم بعد تسجيل الدخول إلى المكان الأقرب
لعمله الفعلي، مع الحفاظ على الحساب الواحد وتعدد الأدوار.

لا نفرض الصفحة نفسها على المالك والمشغل والشريك.

وفي الوقت نفسه لا ننشئ حسابًا أو جلسة دخول مستقلة
لكل دور.

## 202 — التوجيه الذكي

بعد نجاح تسجيل الدخول أو استعادة جلسة صالحة، يقرأ
التطبيق الحساب والأدوار والآبار المتاحة ثم يوجه تلقائيًا.

### المالك

إذا كان للحساب دور owner فعال في بئر واحد أو أكثر:

**يدخل إلى الصفحة الرئيسية.**

لا يدخل مباشرة إلى البئر حتى لو كان يملك بئرًا واحدًا.

الصفحة الرئيسية هي مركزه لاختيار القسم الذي يريد،
ومنها يصل إلى الآبار والتشغيل والإدارة والشراكات
وبقية الأقسام المسموحة له.

إذا كان له بئر إعدادُه غير مكتمل، يظهر في الرئيسية
إجراء واضح:

**متابعة الإعداد**

ولا يجبر على الانتقال إليه تلقائيًا إذا كانت لديه أعمال
أخرى متاحة.

### المشغل فقط

إذا كان الحساب مشغلًا ولا يحمل ملكية أو دورًا آخر
يحتاج الرئيسية الموحدة:

**يدخل مباشرة إلى صفحة التشغيل.**

إذا كان مرتبطًا ببئر واحد، يكون سياق التشغيل واضحًا
لهذا البئر مباشرة.

إذا كان مرتبطًا بأكثر من بئر، يبقى داخل صفحة التشغيل
لكن يختار البئر بوضوح قبل تنفيذ أي عملية تشغيلية.

لا يفتح آخر بئر تلقائيًا عند وجود أكثر من بئر بطريقة
قد تسبب تسجيل عملية في البئر الخطأ.

### الشريك فقط

إذا كان الحساب شريكًا فقط:

**يدخل مباشرة إلى الصفحة المخصصة للشريك.**

إذا كان شريكًا في أكثر من بئر، تعرض صفحة الشريك
علاقاته ويختار البئر أو العرض المطلوب من داخلها.

لا يحتاج المرور على صفحة تشغيل أو صفحة مالك.

### الأدوار المركبة

إذا كان الحساب يحمل أكثر من نوع دور ولا يوجد owner
يحسم الوجهة، مثل:

- مشغل + شريك.
- أدوار متعددة في آبار مختلفة.

يدخل إلى:

**الرئيسية الموحدة**

وتظهر فيها الأقسام التي تخصه.

لا تظهر شاشة تسأله «بأي دور تريد الدخول؟».

### أولوية المالك

إذا كان الشخص مالكًا في أي بئر ويحمل أدوارًا أخرى
في آبار أخرى، تكون وجهته الأولى:

**الرئيسية**

ومنها تظهر له جميع علاقاته الأخرى دون حسابات منفصلة.

### السوبر أدمن

إذا كان الحساب Super Admin فقط ولا يملك علاقة شخصية
ببئر، يمكن توجيهه إلى سياق الإدارة.

إذا كان Super Admin وله أدوار أو ملكية شخصية أيضًا،
تبقى الإدارة مدخلًا مستقلًا ظاهرًا في حسابه ولا تختلط
آبار المنصة كلها بقائمة آباره الشخصية.

## 203 — لا توجد شاشة «اختر دورك»

لا يطلب التطبيق من المستخدم اختيار هوية أو دور عند
تسجيل الدخول.

الأدوار تؤخذ من الصلاحيات الفعلية المسجلة في النظام.

مثال:

    بئر الوادي — مالك
    بئر النور — شريك
    بئر الخير — مشغل

كلها تخص الحساب نفسه.

## 204 — تعدد الأدوار داخل البئر نفسه

إذا كان المستخدم يحمل أكثر من دور في البئر نفسه،
لا يبدل يدويًا بين «وضع المالك» و«وضع المشغل»
و«وضع الشريك».

تجمع الواجهة الصلاحيات الفعلية التي يملكها في ذلك البئر
وتعرض الوظائف المناسبة له.

لا ينشأ حساب أو جلسة مستقلة لكل دور.

## 205 — الصفحة الرئيسية

اسم الصفحة:

**الرئيسية**

وليست «لوحة التحكم» كاسم أساسي للمستخدم.

وظيفتها الأساسية للمالك أو الحساب متعدد الأدوار:

- معرفة السياقات المتاحة له.
- الوصول إلى القسم المطلوب بسرعة.
- الوصول إلى آباره.
- الوصول إلى التشغيل عند امتلاكه صلاحية التشغيل.
- الوصول إلى الشراكات والبيانات المالية المسموحة.
- الوصول إلى «بياناتي كمزارع» عند وجودها.
- الوصول إلى الإدارة إذا كان Super Admin.
- متابعة إعداد بئر غير مكتمل.

التصميم التفصيلي لمحتويات الرئيسية سيعتمد في UX-06.

## 206 — ترتيب الآبار ومنع الخطأ

داخل القوائم التي تعرض عدة آبار يمكن ترتيب البئر
المستخدم حديثًا في موضع متقدم لتسهيل الوصول.

لكن الترتيب لا يعني تنفيذ عملية تشغيلية تلقائيًا عليه.

عند وجود أكثر من بئر في سياق حساس، يجب أن يكون البئر
المختار واضحًا قبل:

- بدء مناوبة.
- بدء جلسة سقي.
- تسجيل دفعة.
- تسجيل مصروف.
- أي إجراء مالي أو تشغيلي حساس.

## 207 — إظهار البئر الحالي

عند دخول سياق بئر، يظهر اسم البئر بوضوح في الواجهات
التشغيلية المهمة.

لا يعتمد المستخدم على اللون أو رمز صغير لمعرفة البئر.

عندما يستطيع الوصول إلى أكثر من بئر، يتوفر إجراء واضح
للانتقال أو تغيير البئر وفق الصفحة الحالية.

## 208 — «بياناتي كمزارع» قسم مستقل

«بياناتي كمزارع» لا يظهر كأنه بئر إضافي.

يظهر كقسم مستقل داخل الحساب عندما توجد بيانات مزارع
مرتبطة صراحة بهوية المستخدم.

يعرض بيانات المستخدم نفسه فقط وفق ق-84، ولا يمنحه
صلاحيات إدارية في الآبار التي يسقي منها.

## 209 — السوبر أدمن

لا تعرض كل آبار المنصة تلقائيًا ضمن قائمة آبار المستخدم
الشخصية للسوبر أدمن.

يظهر له مدخل مستقل:

**الإدارة**

ومن خلاله يصل لاحقًا إلى لوحة إدارة المنصة.

إذا كان مالكًا أو شريكًا أو مشغلًا بصفته الشخصية،
تظهر علاقاته الشخصية بصورة طبيعية في حسابه.

## 210 — حساب صالح دون صلاحيات نشطة

إذا نجح تسجيل الدخول لكن لم يعد للحساب أي وصول نشط
ولا بيانات ذاتية متاحة، لا تظهر صفحة فارغة.

تظهر رسالة:

**لا توجد لديك صلاحيات نشطة حاليًا.**

ويظهر توجيه للتواصل مع مالك البئر أو إدارة التطبيق
إذا كان المستخدم يعتقد أن الحالة غير صحيحة.

لا يحذف الحساب ولا يسجل خروج المستخدم تلقائيًا.

## 211 — بساطة تجربة المشغل

المشغل الذي يعمل على بئر واحد لا يرى التعقيد الموجود
في حساب المالك.

رحلته الأساسية:

    فتح التطبيق
        ↓
    جلسة صالحة
        ↓
    مشغل على بئر واحد
        ↓
    صفحة التشغيل مباشرة

لا يمر على:

- اختيار دور.
- الصفحة الرئيسية للمالك.
- لوحة شراكات.
- اختيار بئر غير ضروري.

إذا كان مشغلًا على أكثر من بئر، تكون صفحة التشغيل هي
السياق نفسه، مع اختيار واضح للبئر قبل الإجراء.

## ملخص التوجيه

    جلسة صالحة
        ↓
    قراءة الحساب والأدوار
        ↓
    owner موجود
        → الرئيسية

    operator فقط
        → صفحة التشغيل

    partner فقط
        → صفحة الشريك

    operator + partner دون owner
        → الرئيسية الموحدة

    Super Admin فقط
        → سياق الإدارة

    لا صلاحيات نشطة
        → رسالة حالة الحساب

## ما لم يحسم داخل UX-05

UX-05 يحسم الوجهة والمنطق فقط.

لم يحسم بعد التصميم التفصيلي لكل من:

- الصفحة الرئيسية للمالك.
- صفحة التشغيل.
- صفحة الشريك.
- لوحة السوبر أدمن.
- شكل «بياناتي كمزارع».

كل واحدة تناقش قبل تنفيذها.

# UX-06 — Owner Home / الصفحة الرئيسية للمالك

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 212–239 بالصيغ النهائية المعتمدة

## الغرض

الصفحة الرئيسية هي مركز عمل المالك.

يجب أن تعطيه بسرعة:

- البئر الحالي.
- حالته الآن.
- أهم المعلومات التي تحتاج انتباهًا.
- مداخل الأقسام الرئيسية.
- تنقلًا ثابتًا وبسيطًا.

لا تتحول الصفحة إلى لوحة إحصاءات مزدحمة.

تستخدم بنية مرئية مشتركة يمكن تكييفها لاحقًا مع
المشغل والشريك، لكن كل مستخدم يرى فقط المعلومات
والأقسام والإجراءات التي تسمح بها صلاحياته.

## 212 — رأس الصفحة

أعلى الصفحة يظهر:

**إدارة البئر**

وتحته مباشرة اسم المستخدم.

وفي الجهة المقابلة يظهر اسم البئر الحالي.

المخطط الوظيفي:

    إدارة البئر

    محمد علي                 بئر الوادي ▼

إذا كان الحساب يستطيع الوصول إلى أكثر من بئر:

- يظهر مؤشر بسيط بجوار اسم البئر.
- الضغط على اسم البئر يفتح نافذة منبثقة.
- النافذة تعرض الآبار المتاحة لذلك المستخدم.
- اختيار بئر يغير سياق الصفحة بوضوح.

إذا كان لديه بئر واحد فقط:

- يظهر اسم البئر طبيعيًا.
- لا يظهر مؤشر تغيير غير ضروري.
- الضغط على الاسم لا ينفذ إجراء.

اسم البئر هو عنصر التبديل نفسه عند وجود أكثر من بئر؛
لا نضيف زرًا دائمًا منفصلًا باسم «تغيير البئر».

## 213 — بطاقة البئر الرئيسية

بعد الرأس مباشرة تظهر بطاقة البئر الرئيسية.

هي العنصر الأبرز في الصفحة وتلخص الحالة الحالية.

يمكن أن تحتوي حسب الصلاحية والبيانات الفعلية على:

- اسم البئر.
- حالة البئر.
- المشغل أو المناوب الحالي.
- مصدر الطاقة الحالي.
- جلسة السقي الجارية.
- وقت بداية الجلسة.
- وقت النهاية الفعلي إذا انتهت الجلسة.
- وقت الانتهاء المتوقع إذا كان موجودًا فعليًا.
- المدة حتى الآن إذا كانت الجلسة ما تزال جارية.
- معلومات مالية مرتبطة بالجلسة وفق القواعد أدناه.

لا يعرض وقت متوقع على أنه وقت نهاية فعلي.

إذا كانت الجلسة جارية يمكن عرض:

    البداية: 08:15
    المدة حتى الآن: 02:35

وإذا وجد وقت نهاية متوقع فعليًا:

    الانتهاء المتوقع: 11:30

وبعد انتهاء الجلسة:

    البداية: 08:15
    النهاية: 11:27

## 214 — الضغط على بطاقة البئر

البطاقة كلها مدخل واضح إلى:

**تفاصيل البئر الحالي**

الضغط عليها يفتح تفاصيل البئر المحدد.

المعلومات والإجراءات داخل التفاصيل تخضع لصلاحيات
الحساب.

لا يحصل مستخدم على معلومات إضافية لمجرد قدرته على
فتح بطاقة البئر.

## 215 — المعلومات المالية أثناء الجلسة

إذا كانت الجلسة جارية وكانت هناك تكلفة يمكن حسابها،
تعرض التكلفة بصفتها غير نهائية:

**التكلفة التقديرية**

إذا تم تسجيل مبلغ مدفوع في بداية الجلسة أو أثناءها،
يعرض أيضًا:

**المبلغ المدفوع**

مثال:

    المبلغ المدفوع: 20,000 ريال
    التكلفة التقديرية: 35,000 ريال

إذا لم يتم تسجيل أي مبلغ مدفوع:

- لا يظهر سطر «المبلغ المدفوع».
- لا يظهر «0 ريال» لمجرد ملء المكان.
- تعرض فقط التكلفة التقديرية إذا كانت متاحة.

مثال:

    التكلفة التقديرية: 35,000 ريال

بعد انتهاء الجلسة واكتمال الحساب الفعلي يمكن عرض:

- التكلفة النهائية.
- المبلغ المدفوع إذا وجد.
- حالة الدفع.

مثل:

    التكلفة النهائية: 45,000 ريال
    المدفوع: 20,000 ريال
    حالة الدفع: مدفوع جزئيًا

أو عند عدم وجود دفعة:

    التكلفة النهائية: 45,000 ريال
    حالة الدفع: غير مدفوع

حالة الدفع المهمة تظهر بنص ورمز ولون، ولا تعتمد
على اللون وحده.

## 216 — المحتوى حسب الصلاحيات

كل معلومة داخل البطاقة والصفحة تخضع للصلاحيات.

### المالك

يمكن أن يرى ما تسمح به صلاحياته من:

- حالة البئر.
- المشغل الحالي.
- مصدر الطاقة.
- جلسة السقي.
- الوقت.
- المعلومات المالية.
- التنبيهات.
- الأقسام الإدارية والتشغيلية.

### المشغل

يركز العرض على العمل الميداني، مثل:

- حالة التشغيل.
- المناوبة الحالية.
- الجلسة الحالية.
- المزارع أو الحجز الجاري عند السماح.
- وقت البداية والمدة.
- مصدر الطاقة.
- الإجراءات التشغيلية المسموحة.

لا تعرض له أرباح الشركاء أو معلومات إدارية لا يحتاجها.

### الشريك

يعرض ما تسمح به صلاحيات الشراكة، مثل:

- حالة البئر العامة.
- معلومات التشغيل المسموح بها.
- ملخصات الشراكة والمال والتقارير المسموحة.

لا تظهر أدوات تشغيل لا يملك صلاحيتها.

المبدأ:

**هيكل بصري متناسق + محتوى وإجراءات حسب الصلاحية.**

## 217 — شريط المعلومات والتنبيهات

بعد بطاقة البئر يظهر شريط أفقي للمعلومات المهمة.

لا يستخدم كمساحة إعلانية تجارية.

يمكن أن يعرض مثلًا:

- جلسة سقي جارية.
- دفعة تحتاج متابعة.
- حجز قادم.
- مخزون منخفض.
- إعداد غير مكتمل.
- حالة تشغيلية تستحق الانتباه.

إذا وجدت عدة معلومات مهمة، يمكن عرض عنصر واحد واضح
في المرة مع إمكانية الانتقال بينها.

لا تستخدم حركة آلية سريعة أو مزعجة.

## 218 — تحديث المعلومات

المعلومات الموجودة في الرئيسية قابلة للتحديث.

السلوك المعتمد:

- تحديث دوري مناسب أثناء فتح الصفحة والاتصال متاح.
- تحديث عند العودة إلى التطبيق.
- دعم السحب للأسفل للتحديث يدويًا.
- عند العمل Offline / دون اتصال، تعرض آخر بيانات محفوظة
  عندما يكون ذلك آمنًا ومسموحًا.
- يظهر وقت آخر تحديث عند الحاجة حتى لا يظن المستخدم
  أن البيانات القديمة لحظية.

لا يحول التحديث الدوري الصفحة إلى حركة مستمرة أو
طلبات شبكة غير ضرورية.

## 219 — الهيكل العام

الترتيب المعتمد للصفحة:

    رأس الصفحة
        ↓
    بطاقة البئر الرئيسية
        ↓
    شريط المعلومات والتنبيهات
        ↓
    شبكة الأقسام
        ↓
    شريط التنقل السفلي

لا يوجد صف مستقل إضافي باسم «إجراءات سريعة»
بين شريط المعلومات وشبكة الأقسام.

شبكة الأقسام نفسها هي وسيلة الوصول السريع.

## 220 — شبكة الأقسام

تعرض أقسام العمل على شكل شبكة بطاقات واضحة.

البطاقة تحتوي أساسًا على:

- أيقونة مفهومة.
- اسم قصير وواضح.
- مساحة لمس كبيرة.

لا نضع وصفًا طويلًا داخل كل بطاقة.

شبكة المالك الأساسية تتكون مبدئيًا من 9 مداخل:

    التشغيل والسقي     المزارعون        الحسابات

    الحجوزات           الشركاء          المصروفات

    البئر والمضخات     التقارير          المزيد

ترتيبها البصري النهائي سيختبر مع RTL وحجم الهاتف
قبل التنفيذ الإنتاجي.

## 221 — التشغيل والسقي

قسم التشغيل والسقي هو المدخل التشغيلي الرئيسي.

يشمل لاحقًا حسب الصلاحيات:

- حالة التشغيل.
- المناوبة الحالية.
- الجلسة الحالية.
- بدء أو متابعة أو إنهاء جلسة.
- سجل الجلسات.
- مصدر الطاقة المستخدم.
- معلومات تشغيل المضخة اللازمة.

المالك يستطيع استخدامه وفق صلاحياته لأنه قادر على
التشغيل أيضًا.

## 222 — المزارعون

اسم البطاقة:

**المزارعون**

ولا نثقل اسم البطاقة بعبارة طويلة.

داخل القسم توجد العلاقات اللازمة مثل:

- قائمة المزارعين.
- حساب المزارع في البئر.
- الأراضي.
- جلسات السقي المرتبطة.
- المعلومات المالية المرتبطة بالمزارع وفق الصلاحيات.
- إضافة مزارع.
- إضافة أرض للمزارع.

## 223 — الحسابات

اسم البطاقة:

**الحسابات**

تجمع الجانب المالي اليومي بطريقة مفهومة للمستخدم.

تشمل مبدئيًا:

- المستحقات.
- الدفعات.
- الديون.
- الأرصدة.
- تحصيل دفعة.
- سجل الحركات المالية المتعلقة بالمزارعين.
- سجل المشغلين أو المناوبين.
- سجل الشركاء.

### سجل المشغلين أو المناوبين

هو مدخل للسجل المالي المرتبط بالمشغلين والمناوبين
وفق نموذج الأعمال والصلاحيات.

تفاصيل أنواع الحركات، الأجور، السلف، المدفوعات أو
الأرصدة لا تفترض داخل UX-06، وستحسم عند مناقشة
قسم الحسابات تفصيليًا.

### سجل الشركاء

هو مدخل للسجل المالي المرتبط بالشركاء وفق الصلاحيات.

تفاصيل التوزيعات والحركات والأرصدة والفترات لا تفترض
داخل UX-06، وستحسم عند تصميم قسم الحسابات والشراكة.

لا تظهر للمستخدم مصطلحات جداول قاعدة البيانات أو
دفتر القيود الداخلي كواجهة يومية.

## 224 — الحجوزات

الحجوزات بطاقة مستقلة بسبب استخدامها المتكرر.

يمكن أن يشمل القسم لاحقًا:

- حجوزات اليوم.
- الحجوزات القادمة.
- المكتملة.
- الملغاة عند وجودها.
- إضافة حجز.
- المزارع.
- الأرض.
- الموعد والتفاصيل.

يمكن إظهار رقم صغير على البطاقة عند وجود حجوزات
مهمة لليوم إذا ثبتت فائدته.

## 225 — الشركاء

اسم البطاقة:

**الشركاء**

يدخل منها المالك إلى ما يتعلق بالشراكة وفق الصلاحيات:

- الشركاء.
- نسب الملكية.
- نسب الأرباح.
- حسابات الشركاء.
- التوزيعات.
- الإجراءات الإدارية المتعلقة بالشراكة.

تفاصيل الصفحة نفسها تناقش لاحقًا.

## 226 — المصروفات

المصروفات بطاقة مستقلة لتسهيل تسجيل ومراجعة المصروف.

يمكن أن تشمل لاحقًا:

- تسجيل مصروف.
- مصروفات اليوم.
- سجل المصروفات.
- التصنيفات.
- التفاصيل.

المعالجة المحاسبية الداخلية تبقى من مسؤولية Backend
ولا تعرض تعقيدها في الصفحة الرئيسية.

## 227 — البئر والمضخات

اسم البطاقة:

**البئر والمضخات**

تجمع التفاصيل الفنية الأقل حاجة للظهور في الرئيسية:

- بيانات البئر.
- المضخات.
- مصادر الطاقة.
- خطوط المياه.
- الموقع.
- البيانات الفنية.
- الإعدادات التشغيلية المتعلقة بالمعدات.

## 228 — التقارير

التقارير مدخل واحد واضح.

لا تعرض رسومًا كثيرة داخل بطاقة القسم نفسها.

أنواع التقارير وترتيبها ستناقش في صفحة التقارير
لاحقًا.

## 229 — المزيد

قسم «المزيد» يمنع تضخم شبكة الرئيسية.

يمكن أن يحتوي لاحقًا على عناصر أقل استخدامًا، مثل:

- إعدادات البئر.
- المستخدمون والمشغلون.
- الحساب والملف الشخصي.
- بياناتي كمزارع عند وجودها وفي المكان المناسب.
- إضافة بئر جديد.
- الدعم والتواصل.
- معلومات التطبيق.
- تسجيل الخروج.
- أقسام ثانوية مستقبلية.

لا يعتمد وجود عنصر نهائيًا داخل «المزيد» إلا عند
مناقشة القسم نفسه.

## 230 — إضافة بئر جديد

لا يظهر زر ضخم دائم لإنشاء بئر وسط الرئيسية.

يظهر «إضافة بئر جديد» في المكان المناسب مثل إدارة
الآبار أو «المزيد».

ويخضع تلقائيًا لق-86 والتحقق من حق تفعيل البئر.

## 231 — بياناتي كمزارع

إذا كان صاحب الحساب نفسه يملك بيانات مزارع مرتبطة
بهويته وفق ق-84، يظهر له مدخل:

**بياناتي كمزارع**

ولا يخلط مع قسم «المزارعون».

الفرق:

- «المزارعون» = مزارعو البئر الذي يديره المستخدم.
- «بياناتي كمزارع» = بيانات صاحب الحساب نفسه عندما
  يكون عميل سقي في آبار أخرى.

## 232 — الشريط السفلي للمالك

الشريط السفلي مخصص للتنقل المتكرر وليس لفهرسة
كل وظائف التطبيق.

الترشيح المعتمد للمالك:

    الرئيسية
    التشغيل
    التقارير
    المزيد

الشبكة توفر بقية الأقسام.

## 233 — الشريط السفلي للمشغل

للمشغل فقط يكون الشريط متوافقًا مع العمل الميداني:

    التشغيل
    الحجوزات
    السجل
    المزيد

لا تظهر له مداخل مالك لا تسمح بها صلاحياته.

## 234 — الشريط السفلي للشريك

للشريك فقط يكون الشريط متوافقًا مع دوره:

    الشراكة
    الأرباح
    التقارير
    المزيد

المحتوى الفعلي لكل صفحة يخضع لصلاحيات الشريك.

## 235 — الأدوار المتعددة

إذا كان الشخص مالكًا ومشغلًا، يستخدم هيكل المالك
ويجد التشغيل ضمنه.

إذا كان شريكًا ومشغلًا دون ملكية، يبقى الحساب موحدًا
وفق UX-05، ويحدد شريطه النهائي عند مناقشة الرئيسية
الموحدة للأدوار المركبة.

لا نعرض شريطين في الوقت نفسه ولا نطلب اختيار دور
عند كل انتقال.

## 236 — الانتقال والرجوع

التنقل يحافظ على السياق الطبيعي.

مثال:

    الرئيسية
        ↓
    المزارعون
        ↓
    مزارع
        ↓
    أرض

زر الرجوع يعكس المسار بصورة طبيعية.

تغيير البئر يغير سياق البيانات بوضوح ولا يترك الصفحة
تعرض خليطًا من بئرين.

## 237 — ما لا يظهر في الرئيسية

لا تعرض الرئيسية:

- كل المزارعين.
- كل الحجوزات.
- كل الدفعات.
- كل الشركاء.
- سجل الجلسات الطويل.
- تفاصيل فنية كثيرة.
- جداول محاسبية داخلية.
- عددًا كبيرًا من الرسوم.
- إعدادات متقدمة.
- أدوات Super Admin الخاصة بالمنصة.

وظيفة الرئيسية:

**موجز حالة + مداخل واضحة للأعمال.**

## 238 — القابلية للتكييف حسب الدور

البنية العامة المشتركة هي:

    رأس المستخدم والبئر
        ↓
    بطاقة الحالة المناسبة
        ↓
    المعلومات والتنبيهات
        ↓
    شبكة الوظائف المسموحة
        ↓
    شريط التنقل المناسب

لكن لا يشترط أن تكون شبكة المالك مطابقة لشبكة المشغل
أو الشريك.

كل دور يرى ما يحتاجه وما تسمح به صلاحياته فقط.

## 239 — أولوية البساطة

لا نضيف عنصرًا لمجرد أن Backend يملكه.

الأولوية:

1. معرفة السياق الحالي.
2. معرفة حالة البئر.
3. معرفة الشيء المهم الذي يحتاج الانتباه.
4. الوصول بسرعة إلى القسم المطلوب.
5. إخفاء التعقيد غير الضروري.

# UX-07 — Role Section Cards / بطاقات الأقسام حسب الدور

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 240–253

## الغرض

تحديد شكل شبكة الأقسام وترتيبها وسلوكها لكل دور،
مع الحفاظ على نفس اللغة البصرية العامة للتطبيق.

لا يعاد تعريف الألوان والخطوط والهوية هنا؛
تطبق ثوابت `VISUAL_IDENTITY.md`.

## 240 — شبكة من ثلاثة أعمدة

تعرض شبكة الأقسام بثلاث بطاقات في الصف عند توفر
المساحة المناسبة على الهاتف.

خصائص البطاقة:

- مربعة أو قريبة من المربع.
- أيقونة واضحة في الجزء العلوي أو الأوسط.
- اسم القسم أسفل الأيقونة.
- الاسم بحد أقصى سطرين.
- البطاقة كلها قابلة للنقر.
- لا يوجد وصف طويل داخل البطاقة.
- مساحة اللمس تبقى مريحة ومتوافقة مع الهوية المعتمدة.

إذا تغير عرض الشاشة بما لا يسمح بثلاثة أعمدة
بصورة مريحة، يحافظ التصميم على قابلية القراءة واللمس
ولا يصغر العناصر بصورة مضرة.

## 241 — أهمية البطاقة

البطاقات متقاربة في الحجم والشكل.

لا نحول بطاقة واحدة إلى لوحة كبيرة إلا إذا كان هناك
سبب وظيفي واضح في صفحة مستقلة.

يمكن للبطاقة حمل معلومة صغيرة مرتبطة بحالتها، مثل:

    الحجوزات
    3 اليوم

أو:

    التشغيل
    جلسة جارية

لكن البطاقة تبقى مدخلًا إلى القسم وليست تقريرًا مصغرًا.

## 242 — ترتيب شبكة المالك

الترتيب الأولي المعتمد للمالك في RTL:

    التشغيل والسقي     المزارعون        الحسابات

    الحجوزات           الشركاء          المصروفات

    البئر والمضخات     التقارير          المزيد

يبقى هذا الترتيب ثابتًا في النسخة الأولى حتى يتعلم
المستخدم أماكن الأقسام.

يمكن تعديل الترتيب قبل التنفيذ النهائي إذا أثبت
الاختبار الميداني أن قسمًا معينًا يحتاج أولوية أعلى.

## 243 — أيقونات المالك

الأيقونات مفهومية وبسيطة وفق نظام الأيقونات المعتمد.

المعاني المستهدفة:

- التشغيل والسقي: تشغيل / مضخة / ماء.
- المزارعون: شخص مع دلالة أرض أو زراعة.
- الحسابات: محفظة أو سجل مالي.
- الحجوزات: تقويم أو موعد.
- الشركاء: مجموعة أشخاص.
- المصروفات: إيصال أو دفع.
- البئر والمضخات: بئر أو مضخة.
- التقارير: وثيقة أو مخطط.
- المزيد: شبكة أو رمز المزيد المناسب.

لا تستخدم أيقونات تقنية غامضة للمستخدم الميداني.

## 244 — شبكة المشغل

المشغل لا يرى شبكة المالك الكاملة.

وظائفه الأساسية مشتقة من صلاحياته التشغيلية.

الشكل المبدئي:

    الحجوزات      المزارعون      الجلسات

    السجل         المدفوعات*     المزيد

النجمة تعني أن البطاقة تظهر فقط إذا كان المشغل يملك
الصلاحية المناسبة.

إذا كانت الصفحة نفسها هي صفحة التشغيل، لا نكرر بطاقة
«التشغيل» بلا فائدة داخل شبكة الصفحة.

## 245 — أولوية صفحة التشغيل للمشغل

المشغل فقط يدخل إلى صفحة التشغيل وفق UX-05.

لذلك تركز شبكة المشغل على المداخل الفرعية التي يحتاجها،
مثل:

- الحجوزات.
- المزارعين.
- الجلسات.
- السجل.
- المدفوعات عند السماح.
- المزيد.

لا نضيف بطاقة «التشغيل» إذا كانت الصفحة الحالية نفسها
هي سياق التشغيل.

## 246 — شبكة الشريك

الشريك يرى شبكة مرتبطة بالشراكة والمتابعة، لا شبكة
تشغيل ميداني.

الشكل المبدئي:

    الشراكة       الأرباح          الحسابات

    التقارير      حالة البئر       السجل

    بياناتي كمزارع*   الإشعارات    المزيد

«بياناتي كمزارع» تظهر فقط عندما توجد علاقة مزارع
مرتبطة صراحة بهوية الحساب وفق ق-84.

«حالة البئر» للعرض والمتابعة حسب صلاحية الشريك،
ولا تمنحه صلاحيات تشغيلية لمجرد ظهورها.

## 247 — إخفاء الوظائف غير المسموحة

إذا لم يكن للمستخدم حق الدخول إلى قسم:

**لا تظهر البطاقة أصلًا.**

لا نملأ الشاشة ببطاقات رمادية تحمل «غير مسموح»
دون حاجة.

بعد إخفاء البطاقة تعاد بقية البطاقات في الشبكة
بصورة طبيعية دون ترك فراغات ثابتة.

يمكن كسر هذه القاعدة مستقبلًا فقط إذا وجد سبب UX
واضح لتعليم المستخدم بميزة متاحة عبر صلاحية أخرى.

## 248 — الحسابات متعددة الأدوار

إذا كان المستخدم مالكًا ومشغلًا:

- شبكة المالك هي الأساس.
- التشغيل موجود ضمنها.
- لا تكرر الوظيفة نفسها تحت اسمين.

إذا كان شريكًا ومشغلًا دون ملكية:

- يستخدم الرئيسية الموحدة وفق UX-05.
- تجمع الشبكة وظائف الشراكة والتشغيل المسموحة.
- تزال المداخل المكررة التي تؤدي إلى نفس الوظيفة.

لا تظهر شبكة مستقلة لكل دور داخل الحساب نفسه.

## 249 — الشارات الصغيرة

يسمح على بطاقة القسم بمعلومة إضافية صغيرة واحدة
عند فائدتها.

الأنواع المعتمدة:

1. رقم صغير، مثل عدد حجوزات اليوم.
2. حالة قصيرة، مثل «جلسة جارية».
3. رمز تنبيه عند وجود أمر مهم.

لا نعرض داخل البطاقة:

- مبالغ مالية كبيرة.
- عدة مؤشرات معًا.
- رسومًا بيانية.
- نسبًا كثيرة.
- أكثر من معلومة إضافية تنافس اسم القسم.

## 250 — سلوك الضغط

الضغط على البطاقة:

- يعطي استجابة لمس واضحة وخفيفة.
- يفتح القسم مباشرة.
- لا يعرض تأكيدًا لمجرد الانتقال.

نوافذ التأكيد تحفظ للعمليات الحساسة مثل:

- الدفع.
- الحذف.
- إغلاق جلسة.
- إجراءات مالية أو تشغيلية نهائية.

## 251 — ترتيب ثابت في النسخة الأولى

ترتيب البطاقات حسب الدور ثابت.

لا يعيد التطبيق ترتيب البطاقات تلقائيًا حسب استخدام
كل شخص.

الهدف أن يتعلم المستخدم موضع الوظيفة بصريًا ويجدها
دائمًا في مكان متوقع.

التخصيص الشخصي للترتيب مؤجل إلى ما بعد النسخة الأولى
إذا ظهرت حاجة فعلية له.

## 252 — التمرير

إذا أصبح عدد البطاقات أكبر من المساحة المتاحة:

- لا تصغر البطاقات إلى حجم يصعب لمسه.
- لا تضغط الخطوط.
- يسمح بالتمرير الرأسي الطبيعي.

قابلية الاستخدام الميداني أهم من إجبار كل الأقسام
على الظهور في شاشة واحدة دون تمرير.

## 253 — «المزيد» آخر بطاقة

بطاقة:

**المزيد**

تكون آخر بطاقة في ترتيب شبكة الدور.

تجمع الوظائف الأقل استخدامًا وتبقى مكانًا متوقعًا
للعناصر الثانوية.

لا تستخدم «المزيد» لإخفاء وظيفة يومية رئيسية لمجرد
توفير المساحة.

# UX-08 — Operations Page / صفحة التشغيل

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 254–293
**القرار العام الحاكم للبحث ومنع التكرار:** ق-88

## الغرض

صفحة التشغيل هي الواجهة الميدانية الأساسية للمشغل،
ويستطيع المالك استخدامها وفق صلاحياته.

الأولوية:

- معرفة البئر والمناوبة الحالية.
- الوصول إلى الجلسة الجارية بسرعة.
- تقليل الإدخال المتكرر.
- منع اختيار مزارع أو أرض أو مضخة خطأ.
- إظهار الزمن والمستحق الجاري بوضوح.
- حماية العمليات الحساسة.
- العمل ضمن عقود Backend الحالية وعدم اختراع
  مسار موازٍ في Flutter.

## 254 — رأس صفحة التشغيل

يظهر:

**التشغيل**

ثم اسم المستخدم واسم البئر الحالي.

إذا كان للمستخدم أكثر من بئر يسمح له تشغيله،
يستخدم اسم البئر نفسه للتبديل وفق UX-06.

إذا كان له بئر واحد فلا يظهر إجراء تغيير غير مفيد.

## 255 — عدم وجود مناوبة مفتوحة

إذا لم توجد مناوبة مفتوحة للمستخدم في البئر:

    لا توجد مناوبة مفتوحة

    لبدء العمل على البئر
    ابدأ مناوبتك أولًا

    [ بدء المناوبة ]

يمكن عرض الحجوزات القادمة للمعرفة، لكن لا يبدأ
المشغل جلسة سقي تشغيلية قبل وجود سياق مناوبة صالح
عندما تتطلب قواعد التشغيل الحالية ذلك.

## 256 — المناوبة الجارية

بعد بدء المناوبة تظهر حالتها بوضوح:

    المناوبة جارية

    المشغل: أحمد محمد
    بدأت: 07:10
    المدة: 03:25

لا يتكرر زر «بدء المناوبة» أثناء وجود مناوبة جارية.

## 257 — لا توجد جلسة سقي جارية

إذا كانت المناوبة مفتوحة ولا توجد جلسة:

    لا توجد جلسة سقي جارية

إذا وجد حجز تالٍ مهم، يعرض ملخصه:

    الحجز التالي
    محمد علي
    أرض الوادي
    09:30

    [ بدء جلسة سقي ]

إذا لم يوجد حجز يبقى:

    [ بدء جلسة سقي ]

الحجز ليس شرطًا عامًا لإنشاء جلسة؛ يسمح ببدء جلسة
مباشرة وفق صلاحيات وقواعد البئر.

## 258 — بدء جلسة من حجز

عند البدء من حجز موجود:

- يعاد استخدام المزارع المسجل.
- يعاد استخدام الأرض.
- يعاد استخدام المضخة إذا كانت محددة وصالحة.
- يعاد استخدام مصدر الطاقة المتوقع كاقتراح، لا كحقيقة
  إذا كان المصدر الفعلي عند البدء مختلفًا.
- لا يطلب التطبيق إعادة إدخال بيانات يعرفها مسبقًا.

يمكن تعديل القيم التي يسمح منطق الأعمال بتعديلها قبل
البدء.

## 259 — بدء جلسة دون حجز

الشاشة الأساسية تحتوي فقط على ما يلزم فعليًا:

- المزارع.
- الأرض.
- المضخة عند الحاجة.
- مصدر الطاقة الفعلي.
- مبلغ مدفوع الآن، اختياري.
- الملاحظات عند الحاجة.

اختيار المزارع والأرض والمضخة وكل كيان مشابه يستخدم
نظام Smart Lookup / البحث والاختيار الذكي وفق ق-88.

## 260 — المزارع ثم الأرض

المسار:

    اختيار المزارع
        ↓
    إظهار أراضي هذا المزارع في هذا البئر
        ↓
    اختيار أرض موجودة
        أو
    إضافة أرض جديدة

إذا كان للمزارع أرض واحدة صالحة فقط، يمكن اختيارها
تلقائيًا مع إبقائها واضحة أمام المستخدم.

## 261 — إضافة مزارع جديد

إذا لم يجد المستخدم المزارع:

**إضافة مزارع جديد**

المشغل والمالك يستطيعان إضافة المزارع عندما تسمح
صلاحيات Backend.

بعد نجاح الإضافة:

- يحفظ المزارع مرة واحدة.
- ينشأ/يستعاد حسابه في البئر وفق القواعد الحالية.
- يعود المستخدم مباشرة إلى بدء الجلسة.
- يصبح المزارع الجديد محددًا.
- لا يعاد إدخال بياناته مرة أخرى.

تطبق قواعد ق-84 وق-88 لمنع هوية مكررة.

## 262 — المضخة

إذا كان للبئر مضخة فعالة واحدة صالحة للجلسة:

- تختار تلقائيًا.
- لا يطلب من المستخدم اختيار بلا فائدة.

إذا كان هناك أكثر من خيار:

- تظهر الخيارات الصالحة فقط.
- يستخدم Smart Lookup عند الحاجة.
- تمنع قواعد Backend اختيار مضخة مشغولة أو غير صالحة.

## 263 — مصدر الطاقة

يعرض المصدر الفعلي المتاح للجلسة.

المصادر الحالية التي يدعمها نموذج المقاطع:

- شمسي.
- ديزل البئر.
- ديزل المزارع.

إذا اختير ديزل المزارع، تظهر فقط البيانات الإضافية
التي يحتاجها هذا النوع.

لا تعرض حقول وقود لا تخص المصدر المختار.

## 264 — الدفعة عند بداية الجلسة

يوجد حقل اختياري:

**مبلغ مدفوع الآن**

إذا لم يدخل مبلغ:

- لا يظهر «المدفوع: 0».
- لا ينشأ عرض مالي وهمي.

إذا أدخل مبلغ:

- يسجل بعملية مالية معتمدة.
- يظهر لاحقًا كمبلغ مدفوع.
- يجب أن يكون بدء الجلسة وتسجيل الدفعة منسقين
  بخادم موثوق بحيث لا تترك العملية حالة جزئية غامضة.

العقد الحالي يفصل بدء الجلسة عن تسجيل الدفع؛ لذلك
التنسيق الآمن المطلوب هنا Gap تنفيذية لـMigration 078+
ولا يعد منفذًا بمجرد اعتماد UX.

## 265 — تأكيد بدء الجلسة

قبل البدء تعرض القيم المختارة بوضوح.

مثل:

    محمد علي
    أرض الوادي
    المضخة الرئيسية
    شمسي

    [ بدء جلسة السقي ]

لا نضيف نافذة تأكيد زائدة إذا كان الملخص أمام المستخدم
واضحًا.

يمنع الضغط المزدوج أثناء تنفيذ الطلب.

## 266 — الجلسة الجارية

بعد البدء تصبح الجلسة هي العنصر الرئيسي في الصفحة.

تعرض حسب البيانات والصلاحيات:

- المزارع.
- الأرض.
- وقت البداية.
- المدة الجارية.
- المضخة.
- مصدر الطاقة.
- المستحق حتى الآن.
- المبلغ المدفوع إذا وجد.
- المتبقي أو الرصيد المقدم عند الحاجة.
- الإيقاف المؤقت.
- تغيير مصدر الطاقة.
- إنهاء الجلسة.

## 267 — عداد الزمن

يعرض الزمن بأرقام إنجليزية 0-9.

مثال:

    02:35:18

يتحدث العرض محليًا بصورة سلسة.

الوقت المالي النهائي لا يعتمد على عداد واجهة الهاتف؛
Backend وأوقات الجلسة والمقاطع هما المرجع النهائي.

## 268 — الإيقاف المؤقت

زر:

**إيقاف مؤقت**

يطلب سببًا واضحًا.

يمكن أن تشمل الخيارات:

- عطل.
- توقف المضخة.
- انتظار.
- تغيير تشغيلي.
- سبب آخر.

بعد الإيقاف:

    الجلسة متوقفة مؤقتًا
    مدة التوقف: 00:12:40

    [ استئناف السقي ]

لا يحتسب الوقت غير القابل للفوترة كوقت سقي مدفوع.

## 269 — تغيير مصدر الطاقة

لا تنشأ جلسة جديدة لمجرد تغير مصدر الطاقة.

المسار:

    المصدر الحالي
        ↓
    تغيير مصدر الطاقة
        ↓
    إغلاق المقطع الحالي
        ↓
    فتح مقطع جديد بالسعر والقواعد المناسبة

الجلسة تبقى واحدة والمستحق التراكمي يستمر.

## 270 — إنهاء الجلسة

إنهاء الجلسة عملية حساسة وتحتاج تأكيدًا.

قبل التأكيد يظهر ملخص:

- المزارع.
- الأرض.
- البداية.
- النهاية الحالية.
- مدة السقي.
- المستحق المتوقع قبل الإغلاق.
- المبلغ المدفوع إذا وجد.

ثم:

**تأكيد إنهاء الجلسة**

التكلفة النهائية تأتي من Backend بعد الإغلاق.

## 271 — نتيجة إنهاء الجلسة

بعد النجاح تعرض نتيجة واضحة:

    تم إنهاء جلسة السقي

    المدة النهائية
    التكلفة النهائية
    المدفوع، إذا وجد
    المتبقي، إذا وجد

ثم تظهر الإجراءات المسموحة مثل:

- تسجيل دفعة.
- العودة إلى التشغيل.

لا يظهر إجراء مالي لمستخدم لا يملك صلاحية تنفيذه.

## 272 — إغلاق المناوبة

إغلاق الجلسة لا يغلق المناوبة.

يمكن أن تحتوي المناوبة على عدة جلسات.

زر إنهاء المناوبة منفصل وأقل بروزًا من الإجراء الحالي
للجلسة.

وجود جلسة مفتوحة يخضع لقواعد Backend الحالية، ولا
يسمح للمشغل بتجاوزها إذا كانت صلاحية التجاوز للمالك فقط.

## 273 — التسليم ونقل الجلسة

إذا تغير المشغل والجلسة ستستمر:

- لا نجبر على إنهاء الجلسة.
- يستخدم مسار نقل/تسليم الجلسة المعتمد.

تميز الواجهة بين:

**إنهاء المناوبة**

و:

**تسليم الجلسة لمشغل آخر**

لأنهما عمليتان مختلفتان.

## 274 — العمل دون اتصال

إذا كانت الجلسة معروفة محليًا:

- يمكن استمرار عرض عداد الزمن محليًا.
- تظهر حالة الاتصال بوضوح عند الحاجة.
- لا يدعي التطبيق نجاح عملية خادمية حساسة قبل
  وجود ضمان مزامنة مناسب.

أي كتابة Offline جديدة تبقى مقيدة بـ
`SYNC_ARCHITECTURE.md`.

# 275–293 — Smart Lookup ومنع التكرار والعداد المالي

## 275 — قاعدة عامة لكل التطبيق

كل حقل يختار كيانًا مسجلًا يستخدم مكوّن بحث واختيار
موحدًا.

يشمل ذلك حسب الصفحة والصلاحيات:

- المزارعين.
- الأراضي.
- المضخات.
- الآبار.
- المشغلين.
- الشركاء.
- الحجوزات.
- التصنيفات أو الكيانات الأخرى القابلة للاختيار.

لا يطبق هذا على:

- كلمات المرور.
- الملاحظات الحرة.
- المبالغ.
- التواريخ.
- النصوص التي ليست كيانات مرجعية.

## 276 — عند فتح حقل الاختيار

عند النقر على الحقل قبل الكتابة:

- تظهر خيارات مناسبة للسياق.
- تظهر العناصر المستخدمة حديثًا عند فائدتها.
- تظهر البيانات الموجودة مسبقًا التي يحق للمستخدم
  رؤيتها.
- يوجد «إضافة جديد» فقط إذا كان الكيان يسمح بذلك
  وصلاحية المستخدم تسمح.

## 277 — الاستجابة أثناء الكتابة

السلوك المستهدف:

- بدون كتابة: خيارات حديثة وسياقية.
- حرف واحد: تضييق محلي سريع عند توفر البيانات.
- حرفان: تبدأ نتائج Prefix / بداية الاسم.
- ثلاثة أحرف فأكثر: يضاف البحث التقريبي الذكي.
- الهاتف: يستخدم تطبيع الرقم وقواعد هوية الهاتف.

لا ينتظر المستخدم كتابة الاسم كاملًا.

## 278 — التطبيع

لا ينشأ نظام تطبيع جديد موازٍ.

يعاد استخدام ما هو موجود مثل:

- `core.normalize_arabic`.
- `core.normalize_phone`.
- `core.person_aliases`.
- `pg_trgm`.

أي توسعة تكون فوق هذه الطبقة أو عبر Migration أحدث،
لا بنسخ المنطق في Flutter.

## 279 — ترتيب النتائج

ترتب النتائج بصورة مفهومة وحتمية:

1. تطابق تام.
2. يبدأ بما كتبه المستخدم.
3. تطابق اسم بديل أو لقب.
4. تطابق كلمات.
5. تشابه تقريبي.
6. نتائج أقل صلة.

داخل المستوى نفسه يكون الترتيب مستقرًا ولا يقفز
عشوائيًا بين عمليات البحث المتطابقة.

## 280 — منع التكرار بثلاث طبقات

منع التكرار لا يعتمد على الواجهة وحدها.

الطبقات:

1. UX:
   يعرض الموجود والمشابه قبل «إضافة جديد».

2. API / Business Procedure:
   يعيد التحقق لحظة الإنشاء.

3. Database:
   تفرض قيودًا حتمية عندما توجد قاعدة فريدة يمكن
   تمثيلها بأمان في قاعدة البيانات.

لا يعتبر أي كيان محميًا من التكرار إذا كانت الحماية
مجرد تحذير بصري.

## 281 — المزارعون

يبنى النظام فوق:

- `core.persons`.
- `core.person_contacts`.
- `core.person_aliases`.
- `core.find_person_duplicates`.
- `core.merge_persons`.
- `ops.create_farmer`.

لا تنشأ جداول أشخاص أو مزارعين موازية.

التطابق الحتمي يعيد استخدام الشخص الموجود.

التشابه القوي لا يسمح بإنشاء مكرر بصمت؛ يجب أن يرى
المستخدم المرشحين ويحسم الحالة وفق القواعد المعتمدة.

## 282 — الهاتف

رقم الهاتف الخاص بهوية التطبيق يخضع لق-84:

**رقم هوية واحد = شخص واحد = حساب تطبيق واحد.**

لا نعيد تفعيل السماح التاريخي بمشاركة هاتف الهوية.

هذا لا يعني وضع Unique عشوائي على كل أنواع
`core.person_contacts` دون دراسة، لأن الجدول يحتوي
أنواع اتصال أخرى وتاريخًا سابقًا.

يطبق التفرد على هوية الهاتف الصحيحة في النموذج النهائي.

## 283 — أراضي المزارع

بعد اختيار المزارع:

- تظهر أراضي حسابه في البئر الحالي فقط.
- لا تظهر له أرض تخص حساب مزارع آخر كخيار جلسة.
- يمكن اختيار الموجود.
- يمكن إضافة أرض جديدة إذا كانت الصلاحية تسمح.

تعتمد العلاقة الحالية:

`ops.farms.farmer_well_account_id`

ولا تنشأ علاقة ثانية موازية.

## 284 — إضافة أرض أثناء التشغيل

المسار المطلوب:

    المزارع المختار
        ↓
    قائمة أراضيه
        ↓
    + إضافة أرض جديدة
        ↓
    حفظ
        ↓
    العودة للجلسة
        ↓
    الأرض الجديدة محددة تلقائيًا

Backend الحالي يقصر `create_farm` على owner.

لذلك السماح للمشغل بإضافة أرض **متطلب جديد صريح**
في Migration 078+ أو أحدث.

لا يتحايل Flutter على هذا القيد بكتابة مباشرة.

## 285 — تكرار أسماء الأراضي

نفس اسم الأرض يمكن أن يوجد لمزارعين مختلفين.

مثال العرض:

    أرض الوادي — محمد علي
    أرض الوادي — أحمد صالح

اسم المزارع أو السياق المميز يعرض كDisambiguation /
تمييز، ولا يدمج تلقائيًا داخل الاسم الأصلي المخزن.

إذا كان للمزارع نفسه أرضان حقيقيتان بالاسم نفسه،
يطلب وصف مميز قصير مثل:

- الشرقية.
- عند البيت.
- بجانب الطريق.

يخزن التمييز كبيان مستقل أو نموذج مناسب، وليس كتعديل
عشوائي على الاسم القانوني/الأساسي.

## 286 — الكتابة في البحث ليست حفظًا

النص الذي يكتبه المستخدم للبحث لا يصبح سجلًا دائمًا.

الحفظ يحدث فقط عند:

- اختيار سجل موجود.
- أو تنفيذ «إضافة جديد» بوضوح ونجاح العملية.

هذا يمنع أخطاء الكتابة من التحول إلى سجلات مكررة.

## 287 — أدخل مرة واحدة واستخدم في كل مكان

الكيانات تحفظ مرة واحدة بمعرفاتها الأصلية.

الجلسات والحجوزات والسجلات الأخرى تستخدم UUID
للكيان بدل نسخ اسمه كنص مستقل كل مرة.

عند اختيار كيان موجود، تملأ الحقول المرتبطة التي يمكن
اشتقاقها بأمان تلقائيًا.

لا يطلب من المستخدم إعادة إدخال معلومة يعرفها النظام.

## 288 — حد API للبحث

Flutter لا يبحث مباشرة داخل مخططات الأعمال الداخلية.

البحث يمر عبر Read Contracts داخل `api.*`.

تكون العقود محددة النوع، مثل مفهوم:

- search farmers.
- search farms.
- search pumps.

ولا ننشئ RPC عامة تقبل اسم جدول أو schema من العميل.

العقود الجديدة:

- SECURITY INVOKER.
- anon محجوب.
- صلاحياتها محددة.
- نتائجها محدودة ومصفحة عند الحاجة.
- تحافظ على ق-78 وق-79 وق-82.

## 289 — البحث المحلي والمزامنة

يمكن أن تظهر النتائج المحفوظة محليًا أولًا لتسريع
العمل الميداني.

ثم تدمج نتائج الخادم عند الاتصال.

قواعد الدمج:

- UUID هو الهوية.
- لا يكرر العنصر نفسه عند وصوله من local/server.
- البيانات المحلية ليست ذريعة لإنشاء كيان جديد مكرر.
- إنشاء كيانات Offline لا يعتبر منفذًا قبل حسم
  idempotency والتعارض وفق `SYNC_ARCHITECTURE.md`.

## 290 — عداد المستحق حتى الآن

عندما يكون للجلسة سعر زمني مثبت يمكن حسابه لحظيًا،
تظهر إلى جانب عداد الزمن قيمة:

**المستحق حتى الآن**

مثال:

    المدة
    00:42:18

    المستحق حتى الآن
    7,050 ريال

يتحدث العرض مع الزمن.

العداد يعمل سواء سجلت دفعة أم لم تسجل.

## 291 — أثر الدفعة والتوقف

الدفعة لا توقف عداد المستحق.

إذا كان المدفوع 5,000 والمستحق 7,050:

    المستحق حتى الآن: 7,050
    المدفوع: 5,000
    المتبقي حتى الآن: 2,050

إذا كان المدفوع أكبر من المستحق الحالي:

    المستحق حتى الآن: 1,667
    المدفوع: 5,000
    رصيد مقدم: 3,333

عند Pause / الإيقاف المؤقت:

- يتوقف احتساب الزمن القابل للفوترة وفق قواعد Backend.
- يتوقف الجزء الزمني من العداد المالي.
- يستأنف عند Resume.

## 292 — تغيير مصدر الطاقة

تغيير المصدر لا يصفر المستحق التراكمي.

المستحق الحالي = قيمة المقاطع المغلقة
+ قيمة المقطع الجاري حتى اللحظة
+ أي مكونات قابلة للحساب وفق نموذج التسعير.

إذا كان جزء من التكلفة يعتمد على قياس وقود لم يعرف بعد،
لا يعرض على أنه «مستحق نهائي معروف».

يستخدم وصف واضح مثل:

- مستحق التشغيل حتى الآن.
- تكلفة تقديرية.
- الوقود يضاف بعد القياس.

حسب نموذج التسعير الفعلي.

## 293 — مرجع الحساب النهائي

Flutter يمكنه تحديث عداد العرض كل ثانية محليًا باستخدام:

- وقت البداية.
- المقاطع.
- السعر المثبت.
- حالة Pause/Resume.
- مصدر الطاقة.

لكن لا يكتب التكلفة النهائية من هذا العداد.

Backend هو مصدر الحقيقة عند إغلاق الجلسة.

أي فرق مشروع بين العرض الجاري والحساب النهائي يجب
أن يكون ناتجًا عن قواعد تسعير معروفة، لا عن تقريب أو
اعتماد ساعة الهاتف كمصدر مالي.

# UX-09 — Session Start Form / شاشة بدء جلسة السقي

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 294–316
**القرارات العامة الحاكمة:** ق-88، ق-89

## الغرض

تجعل شاشة بدء الجلسة العملية الميدانية سريعة وقابلة
للاستخدام في مناطق لا توجد فيها تغطية إنترنت.

غياب الاتصال لا يمنع بدء جلسة السقي.

الواجهة تعيد استخدام البيانات الموجودة، وتمنع الإدخال
المكرر، وتحفظ كل عملية محليًا بصورة دائمة عند الحاجة.

## 294 — نموذج واحد قصير

شاشة بدء الجلسة نموذج واحد وليس Wizard متعدد الصفحات.

الترتيب:

    بدء جلسة سقي

    البئر والمناوبة

    المزارع
    الأرض

    المضخة
    مصدر الطاقة

    السعر أو حالة التسعير

    مبلغ مدفوع الآن — اختياري

    الملخص

    [ بدء جلسة السقي ]

تظهر الحقول الإضافية عند الحاجة فقط.

## 295 — البئر والمناوبة

لا يطلب اختيار البئر مرة ثانية إذا كان السياق الحالي
محسومًا.

يظهر:

    بئر الوادي
    المناوبة: أحمد محمد — بدأت 07:10

ويتحقق النظام من صلاحية السياق من البيانات المتاحة.

عند Offline يستخدم آخر سياق صلاحيات موثوق ومخزن محليًا
مع تسجيل أن التحقق الخادمي النهائي Pending.

## 296 — المزارع

أول حقل أعمال هو:

**المزارع**

ويستخدم Smart Lookup وفق ق-88.

عند فتح الحقل تظهر بيانات حديثة وسياقية.

من حرفين يبدأ Prefix.

من ثلاثة أحرف يضاف البحث التقريبي.

تظهر بيانات تمييز عند تشابه الأسماء.

## 297 — إضافة مزارع

يوجد:

**+ إضافة مزارع جديد**

ويطبق منع التكرار قبل الإنشاء.

عند Offline يمكن حفظ إنشاء المزارع محليًا كأمر Pending
إذا كانت هذه القدرة منفذة ضمن ق-89.

لا يقال «تمت المزامنة» قبل قبول الخادم.

بعد الإنشاء يعود المستخدم إلى النموذج والمزارع محدد.

## 298 — الأرض مرتبطة بالمزارع

لا يفعل حقل الأرض قبل اختيار المزارع.

بعد الاختيار تظهر أراضي هذا المزارع في البئر الحالي.

يوجد:

**+ إضافة أرض جديدة**

وعند Offline يمكن حفظ الأرض الجديدة محليًا ضمن نفس
سياق المزارع، ثم مزامنتها لاحقًا وفق ق-89.

## 299 — تمييز الأراضي المتشابهة

إذا كان نفس اسم الأرض لمزارعين مختلفين:

    أرض الوادي
    محمد علي

    أرض الوادي
    أحمد صالح

ولا يغير الاسم الأساسي المخزن.

إذا كان للمزارع نفسه أرضان حقيقيتان بالاسم نفسه،
يطلب وصف مميز مستقل.

## 300 — التعبئة التلقائية

المعلومة الحتمية تملأ تلقائيًا.

المعلومة التي قد تتغير تقترح فقط.

لا يختار التطبيق قيمة حساسة بصمت لمجرد أنها آخر قيمة
استخدمت في جلسة سابقة.

## 301 — المضخة

إذا كانت مضخة فعالة واحدة فقط صالحة:

- تختار تلقائيًا.
- تبقى ظاهرة للمستخدم.

إذا كانت عدة مضخات:

- يختار المستخدم من الصالح فقط.
- تطبق قواعد التوازي الحالية.

عند Offline يعتمد التطبيق Snapshot محليًا لحالة المعدات،
ثم يحسم أي تعارض عند المزامنة وفق ق-89.

## 302 — مصدر الطاقة

إذا كان مصدر واحد متاحًا فقط يمكن تحديده تلقائيًا.

إذا تعددت المصادر يعرض الاختيار.

مصدر الحجز المتوقع اقتراح فقط.

المصدر الذي يحدد عند بدء الجلسة هو المصدر الفعلي.

## 303 — السعر قبل البدء

### Online

عند الاتصال:

- لا يكتب المشغل السعر يدويًا.
- يعرض السعر الفعال الذي يحسمه النظام.
- السعر للقراءة في نموذج الجلسة.
- تعديل التسعير يتم من صلاحية وإعداد مخصص.

### Offline مع سعر موثوق مخزن

إذا كان الجهاز يحمل Pricing Snapshot موثوقًا:

- يعرض السعر المخزن.
- يستخدم لعداد «المستحق حتى الآن».
- تحفظ هوية/نسخة قاعدة السعر مع الأمر المحلي.

### Offline بلا سعر موثوق

غياب السعر المحلي لا يمنع التشغيل الميداني.

تبدأ الجلسة مع حالة:

**التسعير بانتظار المزامنة**

ويعرض الزمن دون ادعاء مبلغ معروف.

عند المزامنة يجب حسم السعر الذي كان ساريًا في
وقت البداية الأصلي.

لا يستخدم السعر الحالي وقت وصول الإنترنت إذا كان
مختلفًا عن السعر التاريخي الواجب التطبيق.

إذا تعذر الحسم القطعي:

- لا يخمن النظام.
- تنتقل الحالة إلى مراجعة واضحة.
- لا تصبح التكلفة نهائية بصمت.

## 304 — نماذج التسعير المركبة

لا نفترض أن كل جلسة «سعر ساعة» بسيط.

تعرض للمستخدم مكونات التسعير الضرورية لفهم ما سيطبق.

أي مكون لا يمكن معرفته قبل القياس يوصف بأنه تقديري
أو Pending حسب الحقيقة.

## 305 — الدفعة المقدمة

الحقل:

**مبلغ مدفوع الآن — اختياري**

إذا كان صفرًا أو فارغًا لا يظهر سطر مدفوع.

إذا أدخل مبلغًا تظهر طريقة الدفع عند الحاجة.

### Offline

تسجل الدفعة محليًا بCommand ID ثابت وتظهر:

**محفوظ محليًا — بانتظار المزامنة**

لا تعتبر مرحّلة محاسبيًا على الخادم قبل نجاح المزامنة.

إعادة المحاولة لا يجوز أن تنشئ دفعة ثانية.

## 306 — ملخص البدء

قبل الضغط يظهر ملخص قصير:

- المزارع.
- الأرض.
- المضخة.
- مصدر الطاقة.
- السعر أو «التسعير بانتظار المزامنة».
- الدفعة إن وجدت.
- حالة الاتصال.

لا يعرض الحقل غير الموجود لمجرد ملء المساحة.

## 307 — فحص الجاهزية

قبل البدء يتحقق التطبيق من البيانات التي يمكن فحصها
محليًا.

غياب الإنترنت وحده ليس مانعًا.

المانع المحلي الحقيقي يجب أن يظهر بسبب واضح.

أمثلة:

- لا يوجد مزارع محدد.
- لا توجد أرض.
- لا توجد مضخة صالحة في Snapshot المحلي.
- بيانات أساسية ناقصة.

التعارضات التي لا يمكن معرفتها Offline تحسم عند Sync.

## 308 — بدء الجلسة دون إنترنت

**قاعدة معتمدة وحاكمة:**

بدء جلسة السقي يجب أن يعمل دون اتصال بالإنترنت.

عند الضغط:

1. ينشئ التطبيق Session Identity محلية ثابتة.
2. ينشئ Command ID ثابتًا للعملية.
3. يحفظ البيانات في قاعدة محلية Durable قبل إعلان النجاح.
4. يبدأ العداد المحلي.
5. تظهر حالة «محفوظ محليًا».
6. تدخل العملية Outbox للمزامنة.
7. لا يحتاج المستخدم إلى إبقاء التطبيق مفتوحًا بعد ذلك.

لا يجوز استخدام ذاكرة مؤقتة RAM فقط لحفظ الجلسة.

## 309 — البدء من حجز

يستخدم نفس النموذج.

البيانات الموجودة في الحجز تملأ تلقائيًا.

عند Offline يستخدم آخر Booking Snapshot محلي صالح.

لا تنشأ شاشة ثانية لمجرد أن المصدر حجز.

## 310 — حفظ سياق النموذج

إضافة مزارع أو أرض لا تمسح النموذج الأم.

بعد العملية الفرعية يعود المستخدم إلى الموضع نفسه
بالبيانات السابقة والكيان الجديد محدد.

ينطبق ذلك Online وOffline.

## 311 — هوية محلية ثابتة للأوامر

كل عملية Offline حساسة تحتاج:

- UUID محلي ثابت للعملية.
- Command ID ثابتًا.
- وقت الحدث الأصلي.
- المستخدم والبئر والسياق.
- Payload المطلوب.
- حالة المزامنة.

إعادة التطبيق أو الهاتف لا تولد Command ID جديدًا
لنفس العملية.

## 312 — دورة الجلسة Offline

يجب أن تدعم دورة الجلسة الميدانية الحرجة Offline:

- البدء.
- الإيقاف المؤقت.
- الاستئناف.
- تغيير مصدر الطاقة.
- الإنهاء.
- الدفعة المرتبطة بالتشغيل عند السماح.

الأحداث تحفظ بالترتيب.

المزامنة تعيد تشغيلها بترتيب يحافظ على معنى الجلسة.

## 313 — المزامنة الخلفية التلقائية

عند توفر الاتصال:

- التطبيق يحاول المزامنة تلقائيًا.
- لا يشترط أن تكون واجهة التطبيق مفتوحة.
- تستخدم آلية Android الدائمة المناسبة مثل WorkManager.
- Network Constraint يمنع المحاولة دون شبكة.
- Retry/Backoff يعالجان الفشل المؤقت.
- يمكن استخدام Expedited Work للحالة الملائمة دون
  الاعتماد عليه كضمان مطلق.

المتطلب المنتج هو:

**المزامنة في أقرب فرصة يسمح بها نظام Android بعد عودة الاتصال.**

لا توثق عبارة «في نفس الثانية حتمًا» لأن نظام التشغيل
قد يؤجل تنفيذ الخلفية.

## 314 — ما بعد نجاح المزامنة

بعد نجاح Sync:

- تتحول العناصر المحلية إلى Synced.
- تحفظ المعرفات الخادمية أو تطابقها مع الهوية المحلية.
- تحدث البيانات المحلية.
- تنفذ إجراءات الخادم اللاحقة.
- تدخل الإشعارات وقنواتها المعتمدة في التدفق المناسب.
- لا يعاد إرسال نفس الحدث مرتين.

منطق الإشعارات الحالي وM-23 يجب أن يندمجا مع هذا
التدفق بدل إنشاء نظام إشعارات ثانٍ.

## 315 — جاهزية الجهاز والصلاحيات

التطبيق يحتاج Device Readiness / جاهزية الجهاز.

يفحص ويشرح ما ينطبق على إصدار Android والجهاز، مثل:

- صلاحية الإشعارات عند الحاجة.
- قدرة العمل في الخلفية.
- حالة قيود البطارية.
- حالة بيانات الخلفية عند إمكانية فحصها.
- إعدادات خاصة بالشركة المصنعة فقط إذا كانت معروفة
  ومختبرة.

لا يطلب التطبيق صلاحيات غير ضرورية لمجرد تحسين
احتمالية العمل في الخلفية.

لا يطلب Background Location أو Exact Alarm أو
Accessibility أو Overlay أو All Files إلا إذا ظهر
لاحقًا سبب أعمال مستقل ومعتمد لها.

## 316 — التعليمات والتذكير الدوري

في أول إعداد للجهاز تعرض شاشة توضح:

- لماذا يحتاج التطبيق للمزامنة الخلفية.
- ما الإعدادات المطلوبة.
- حالة كل إعداد.
- زر «إصلاح الآن» أو «فتح الإعدادات» عندما يسمح Android.

إذا بقي إعداد حرج ناقصًا:

- يظهر مؤشر دائم في «المزيد».
- يظهر تذكير دوري داخل التطبيق.
- الحد الافتراضي للتذكير المتكرر مرة كل 24 ساعة أثناء
  استخدام التطبيق، لا في كل نقرة.
- قبل عمل ميداني يعتمد على Offline يمكن إظهار تنبيه
  مختصر إذا كانت جاهزية الخلفية ناقصة.

لا يمكن للتطبيق منح نفسه Runtime أو Special Permission.

إذا قام المستخدم بForce Stop أو وضع التطبيق في Restricted
فقد يمنع Android العمل الخلفي.

بعد عودة المستخدم للتطبيق يعاد فحص الجاهزية ويشرح
الإجراء اللازم بدل ادعاء أن المزامنة الخلفية مضمونة.

**القرارات العامة الحاكمة:** ق-89، ق-90

## الغرض

تعطي الصفحة المستخدم صورة واضحة عن:

- قدرة التطبيق على العمل دون اتصال.
- قدرة Android على تنفيذ المزامنة في الخلفية.
- حالة الإشعارات.
- العمليات المحفوظة محليًا.
- آخر مزامنة ناجحة.
- الأخطاء والتعارضات التي تحتاج مراجعة.
- الإعدادات التي يستطيع المستخدم تحسينها.

لا تخلط الصفحة بين «العمل Offline» و«المزامنة
الخلفية» و«الإشعارات».

تعطل واحد منها لا يعني تلقائيًا تعطل البقية.

## 317 — ثلاث حالات مستقلة

في أعلى الصفحة تظهر ثلاث حالات منفصلة:

1. العمل دون اتصال.
2. المزامنة الخلفية.
3. الإشعارات.

مثال:

    العمل دون اتصال
    جاهز

    المزامنة الخلفية
    تحتاج إعداد

    الإشعارات
    غير مفعلة

لا يستخدم مؤشر واحد عام لإخفاء الفرق بينها.

## 318 — جاهزية العمل دون اتصال

تعتبر Offline Readiness جاهزة عندما يستطيع التطبيق
بأمان:

- الكتابة في Local Durable Database.
- إنشاء وحفظ Outbox.
- توليد وحفظ Command IDs.
- استرجاع الجلسة المحلية بعد Process Death.
- قراءة بيانات البئر الأساسية اللازمة للعمل.
- حفظ أحداث الجلسة قبل إعلان نجاحها محليًا.

مثال:

    العمل دون اتصال
    جاهز

    يمكنك بدء وإدارة جلسات السقي
    حتى بدون إنترنت.

إذا فشل التخزين المحلي الحرج فلا يجوز بدء جلسة Offline
لأن التطبيق لا يستطيع ضمان عدم فقد البيانات.

## 319 — بطاقة المزامنة

تعرض:

- آخر مزامنة ناجحة.
- عدد العمليات Pending.
- عمر أقدم عملية Pending.
- هل توجد عملية تحتاج مراجعة.
- زر «مزامنة الآن».

أمثلة:

    آخر مزامنة ناجحة
    18:42

    بانتظار المزامنة
    4 عمليات

أو:

    جميع البيانات متزامنة

زر «مزامنة الآن» مساعد، وليس شرطًا لعمل النظام.

## 320 — حالات المزامنة للمستخدم

الحالات الداخلية الأساسية:

- local_only.
- pending.
- syncing.
- synced.
- failed.
- conflict.

لكن تعرض بالعربية للمستخدم:

- محفوظ محليًا.
- بانتظار المزامنة.
- جارٍ الإرسال.
- تمت المزامنة.
- فشل — ستتم إعادة المحاولة.
- يحتاج مراجعة.

لا تعرض الأكواد الداخلية للمستخدم العادي.

## 321 — قائمة العمليات Pending

عند فتح عدد العمليات المنتظرة، تعرض قائمة مفهومة.

مثال:

    جلسة محمد علي
    بدأت 14:20
    بانتظار المزامنة

    تغيير مصدر الطاقة
    15:05
    بانتظار المزامنة

    دفعة 20,000 ريال
    15:07
    بانتظار المزامنة

    إنهاء الجلسة
    17:31
    بانتظار المزامنة

لا يحتاج المستخدم لمعرفة UUID أو Queue internals.

## 322 — المزامنة تلقائية

المزامنة الأساسية تلقائية.

لا يعتمد سير العمل على أن يتذكر المستخدم:

    فتح التطبيق
        ↓
    الضغط على مزامنة

عند توفر Pending Commands واتصال مناسب:

- يجدول التطبيق Background Sync.
- يعيد المحاولة حسب السياسة.
- يستفيد من WorkManager وفق ق-89.
- يزامن في أقرب فرصة يسمح بها Android.

زر المزامنة اليدوي خيار إضافي فقط.

## 323 — إعداد الجهاز للعمل الميداني

على جهاز جديد يظهر Setup قصير.

مثال:

    إعداد الجهاز للعمل الميداني

    التخزين المحلي        جاهز
    العمل دون اتصال       جاهز
    المزامنة الخلفية      تحتاج إعداد
    الإشعارات             تحتاج إعداد

    [ متابعة الإعداد ]

لا تفتح للمستخدم عدة صفحات Android دفعة واحدة.

يعالج كل بند في سياقه.

## 324 — قاعدة الصلاحيات والإعدادات

التطبيق يطلب ويهيئ كل الصلاحيات والإعدادات الضرورية
لوظائفه المعتمدة.

لا يطلب صلاحية لمجرد أنها متاحة في Android.

تبقى قاعدة Least Privilege حاكمة.

بعض الصلاحيات والإعدادات تحتاج موافقة المستخدم ولا
يمكن للتطبيق تفعيلها بنفسه.

يشرح التطبيق:

- ماذا يحتاج.
- لماذا يحتاجه.
- ماذا يحدث إذا رفض المستخدم.
- كيف يفتحه من الإعدادات عند الحاجة.

## 325 — المزامنة الخلفية والقيود

تعرض حالة Background Execution بوضوح.

مثال:

    المزامنة في الخلفية
    جاهزة

أو:

    Android يقيّد عمل التطبيق في الخلفية

    [ فتح الإعدادات ]

وجود Restriction لا يمنع التشغيل Offline.

تعرض رسالة مثل:

    يمكنك الاستمرار في العمل دون اتصال،
    لكن قد تتأخر المزامنة حتى فتح التطبيق
    أو إزالة القيد.

## 326 — البطارية

لا يطلب التطبيق تعطيل Battery Optimization تلقائيًا
من كل مستخدم.

WorkManager هو المسار الأساسي.

إذا أثبت الاختبار على جهاز أو نظام معين أن القيود تمنع
الوظيفة الأساسية:

- يظهر شرح واضح.
- يفتح إعداد البطارية المناسب إن أمكن.
- لا يدعي أن الإعداد إلزامي لكل Android.
- يراجع توافق سياسة المنصة قبل طلب أي Special Exemption.

## 327 — تعليمات الشركات المصنعة

يمكن للتطبيق التعرف على Manufacturer / Model / Android
Version لأغراض الإرشاد.

لا يعرض تعليمات Manufacturer-specific إلا إذا كانت:

- موثقة.
- مختبرة.
- مرتبطة بنطاق أجهزة/إصدارات معروف.

إذا لم توجد معرفة موثوقة:

- لا يخترع التطبيق تعليمات.
- تبقى الحالة عامة.
- تسجل الحاجة ضمن الاختبارات الميدانية م-21.

## 328 — الإشعارات مستقلة

الإشعارات لها حالة مستقلة.

مثال:

    الإشعارات
    غير مفعلة

    ستستمر مزامنة البيانات،
    لكن قد لا تصلك إشعارات التطبيق.

رفض Notification Permission لا يمنع:

- حفظ البيانات.
- العمل Offline.
- المزامنة.
- تنفيذ أوامر Backend.

## 329 — التذكير الدوري

إذا كان إعداد مهم للمزامنة ناقصًا:

- يظهر Indicator داخل التطبيق.
- يظهر تذكير دوري غير مزعج.
- الحد الافتراضي للتذكير أثناء الاستخدام مرة كل 24 ساعة
  طالما المشكلة نفسها ما زالت قائمة.
- يمكن إظهار تنبيه مختصر قبل عمل ميداني عندما يؤثر النقص
  على Background Sync.

بعد إصلاح الإعداد تتوقف تذكيرات المشكلة.

لا يعاد فتح System Permission Dialog بشكل متكرر بلا سبب.

## 330 — نوعا أخطاء المزامنة

### أخطاء تلقائية قابلة لإعادة المحاولة

مثل:

- انقطاع الشبكة.
- Timeout.
- Server unavailable مؤقتًا.

هذه:

- تبقى Pending/Failed transient.
- يعاد إرسالها تلقائيًا.
- لا تحتاج إزعاج المستخدم في كل محاولة.

### أخطاء تحتاج حسمًا

مثل:

- Duplicate ambiguity.
- Farm conflict.
- Historical pricing ambiguity.
- Permission changed.
- Session state conflict.
- Time integrity conflict.

هذه تتحول إلى:

**يحتاج مراجعة**

ولا تستمر Retry Loop بلا نهاية.

## 331 — عرض Conflict

عند وجود Conflict يمكن إظهار تنبيه في الرئيسية أو التشغيل:

    توجد عملية تحتاج مراجعة بعد المزامنة

    [ عرض التفاصيل ]

الرسالة تشرح السبب العملي.

لا تعرض:

    HTTP 409
    constraint violation
    RPC error

للمستخدم الميداني.

## 332 — حالة Sync داخل الجلسة

تفاصيل الجلسة تعرض مؤشرًا صغيرًا مثل:

    تمت المزامنة

أو:

    بانتظار المزامنة

أو:

    يحتاج مراجعة

هذا المؤشر لا يحول شاشة الجلسة إلى شاشة تشخيص.

## 333 — عودة الاتصال والتطبيق مغلق

لا يحتاج المستخدم إلى فتح التطبيق حتى يطلب Sync.

عند توفر الشروط:

- يحاول Background Worker تنفيذ المزامنة.
- يحدث Local State بعد Server ACK.
- تنفذ الإشعارات الخادمية المناسبة.
- عدم توفر Notification Permission لا يمنع Sync نفسه.

توقيت التشغيل الفعلي يبقى خاضعًا لAndroid وفق ق-89.

## 334 — Force Stop

Force Stop حالة منصة خاصة.

لا يدعي التطبيق أن Background Sync يستمر حتمًا بعدها.

بعد عودة المستخدم للتطبيق:

- يعاد فحص Device Readiness.
- تقرأ Outbox المحفوظة.
- تستأنف محاولات المزامنة.
- يظهر للمستخدم عدد العمليات التي كانت محفوظة.

مثال:

    تم استئناف التطبيق

    لدينا 6 عمليات محفوظة محليًا.
    جارٍ محاولة مزامنتها.

لا تضيع البيانات بسبب Force Stop.

## 335 — مدخل «جاهزية الجهاز والمزامنة»

داخل «المزيد» يوجد مدخل:

**جاهزية الجهاز والمزامنة**

وتعرض عليه شارة ذات أولوية.

الأولوية المقترحة:

1. يحتاج مراجعة / Conflict.
2. فشل مهم يحتاج المستخدم.
3. يحتاج إعداد جهاز.
4. Pending عادي.
5. جاهز.

لا تخفي Conflict خلف عدد Pending.

## 336 — ما الذي يمنع التشغيل؟

القاعدة العامة:

### لا يمنع بدء الجلسة بسبب:

- لا يوجد إنترنت.
- الإشعارات غير مفعلة.
- WorkManager لم يعمل بعد.
- Battery Restriction.
- Pending Sync عادي.
- مشكلة Background Sync غير حرجة.
- Conflict قديم لا يؤثر على صلاحية الجلسة الجديدة.

### يمنع عند وجود خطر حقيقي على سلامة العملية، مثل:

- Local Durable Storage غير قابل للكتابة.
- لا يمكن حفظ Command محليًا.
- البيانات الأساسية للجلسة غير موجودة أو غير صالحة.
- لا يمكن حفظ Session Identity.
- حالة محلية تثبت أن بدء الجلسة سيؤدي إلى فقد أو فساد
  بيانات حتمي.
- Conflict حرج يخص نفس المورد أو نفس الجلسة ويمنع
  العملية الجديدة وفق قاعدة أعمال موثقة.

المبدأ:

**مشكلة الراحة أو سرعة Sync = تحذير.**

**مشكلة سلامة حفظ وتشغيل البيانات = مانع.**

# UX-11 — Active Irrigation Session / شاشة الجلسة الجارية

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 337–360
**القرارات العامة الحاكمة:** ق-17، ق-20، ق-88، ق-89، ق-90، ق-91

## الغرض

هذه هي شاشة العمل اليومية الأساسية أثناء وجود جلسة سقي.

يجب أن تجيب فورًا عن:

- لمن نسقي؟
- أي أرض؟
- كم بلغ وقت السقي المحتسب؟
- كم المستحق حتى الآن؟
- كم دُفع؟
- ما مصدر الطاقة الحالي؟
- ما حالة المزامنة؟
- ما الإجراء التالي؟

لا تعرض تفاصيل تقنية لا يحتاجها المشغل.

## 337 — الجلسة هي العنصر الرئيسي

عند وجود جلسة جارية تصبح بطاقة الجلسة هي العنصر
الأكثر بروزًا.

تعرض:

- اسم المزارع.
- الأرض.
- مدة السقي المحتسبة.
- المستحق حتى الآن عندما يمكن حسابه.
- المدفوع عند وجوده.
- المتبقي أو الرصيد المقدم.
- المضخة.
- مصدر الطاقة.
- حالة Sync.
- إجراءات الجلسة.

## 338 — المزارع والأرض مثبتان بعد البدء

بعد بدء الجلسة لا يسمح بتغيير المزارع أو الأرض من
Dropdown عادي.

يمكن فتح التفاصيل للعرض.

إذا بدأت الجلسة على هوية خاطئة، يلزم مسار تصحيح مدقق
يحدد لاحقًا؛ لا يتم التعديل الصامت على سجل تشغيل مالي.

## 339 — الزمن المعروض

العداد الرئيسي هو:

**مدة السقي المحتسبة**

وهو الزمن القابل للفوترة.

يمكن في التفاصيل عرض:

- الزمن منذ بدء الجلسة.
- إجمالي التوقف.
- مدة السقي المحتسبة.

مثال:

    02:35:18
    مدة السقي المحتسبة

    منذ بدء الجلسة: 02:47:36
    إجمالي التوقف: 00:12:18

الزمن المالي يبقى بالثانية وفق الثوابت.

## 340 — المستحق تحت الزمن مباشرة

يظهر المستحق مباشرة تحت عداد الزمن.

مثال:

    02:35:18
    مدة السقي المحتسبة

    25,863 ريال
    المستحق حتى الآن

يتحدث العرض محليًا مع الزمن.

Backend يبقى مرجع التسوية النهائية.

## 341 — Pricing Pending

إذا لم توجد Pricing Snapshot موثوقة للجلسة Offline:

    مدة السقي المحتسبة
    02:35:18

    التكلفة بانتظار المزامنة

لا يظهر:

    0 ريال

ولا رقم مخمن.

بعد حسم السعر التاريخي يمكن تحديث العرض.

## 342 — المستحق والدفع حقيقتان منفصلتان

المستحق لا ينقص بمجرد تسجيل الدفع.

إذا لم توجد دفعة يظهر المستحق فقط.

إذا كان:

    المستحق حتى الآن: 25,863 ريال
    المدفوع: 20,000 ريال

يعرض:

    المتبقي حتى الآن: 5,863 ريال

وإذا تجاوز المدفوع المستحق الحالي:

    المستحق حتى الآن: 8,000 ريال
    المدفوع: 20,000 ريال
    رصيد مقدم: 12,000 ريال

لا تعرض أرقام سالبة للمستخدم بوصفها «متبقي».

## 343 — تسجيل دفعة أثناء الجلسة

يمكن عرض إجراء:

**تسجيل دفعة**

إذا كانت صلاحية المستخدم تسمح.

لأن تكلفة الجلسة النهائية لم تقفل بعد، تعامل الدفعة
المحصلة أثناء التشغيل وفق النموذج المالي المعتمد كدفعة/
رصيد مقدم، ثم تسوى بصورة آمنة عند الإقفال.

لا ينشأ مسار دفع موازٍ.

Online/Offline payment coordination يبقى خاضعًا لق-88
وق-89.

إذا كانت دفعة Offline محفوظة محليًا:

- يمكن أن تظهر في شاشة العمل باعتبارها مبلغًا استلمه
  المشغل فعليًا.
- تحمل حالة «بانتظار المزامنة».
- لا تعتبر Posted على الخادم قبل Server ACK.

## 344 — الإجراءات الأساسية

أثناء التشغيل تظهر الإجراءات المسموحة مثل:

- إيقاف مؤقت.
- تغيير مصدر الطاقة.
- تسجيل دفعة.
- إنهاء الجلسة.

إنهاء الجلسة إجراء نهائي وحساس ويجب فصله بصريًا
عن الضغطات اليومية العادية.

## 345 — نوع التوقف وسبب التوقف

Backend الحالي يملك نوعي Pause أساسيين:

- operator_pause.
- farmer_requested_pause.

هذا النوع لا يكفي وحده لتفسير سبب التوقف ميدانيًا.

النموذج المعتمد يفصل:

### نوع التوقف

- توقف من المشغل.
- توقف بطلب المزارع.

### السبب التفصيلي

أمثلة:

- عطل بالمضخة.
- مصدر الطاقة غير متاح.
- انتظار.
- صيانة.
- سبب تشغيلي آخر.

إذا اختير «آخر» يمكن إدخال ملاحظة قصيرة.

إضافة السبب التفصيلي Gap تنفيذية لـMigration 078+
أو أحدث ولا تعتبر منفذة حاليًا.

## 346 — شكل Pause

أثناء التوقف:

    الجلسة متوقفة مؤقتًا

    مدة السقي المحتسبة
    02:35:18

    مدة التوقف الحالية
    00:12:40

    المستحق حتى الآن
    25,863 ريال

    السبب
    عطل بالمضخة

    [ استئناف السقي ]

    [ إنهاء الجلسة ]

عداد السقي والجزء الزمني من المستحق لا يزدادان.

عداد التوقف الحالي يستمر.

## 347 — Resume بنفس المصدر والسعر

الاستئناف العادي يعيد:

- مصدر التشغيل السابق.
- السعر المثبت السابق للمقطع.

لا يلتقط سعرًا جديدًا لمجرد وجود Pause.

هذا يطابق إجراء Backend الحالي.

## 348 — Resume بمصدر طاقة جديد

هناك حالة ميدانية:

    شمسي
        ↓
    Pause
        ↓
    قرار الانتقال إلى ديزل
        ↓
    Resume مباشرة على الديزل

لا يجوز إجبار المستخدم على إنشاء مقطع تشغيل وهمي قصير
بالمصدر القديم ثم تغيير المصدر.

يلزم Contract ذري بمعنى:

**استئناف الجلسة بمصدر طاقة جديد**

يقوم منطقيًا بـ:

- إغلاق Pause.
- فتح مقطع التشغيل الجديد مباشرة.
- التقاط سعر المصدر الجديد حسب وقت الاستئناف.
- عدم إنشاء ثانية تشغيل وهمية بالمصدر السابق.

هذه Gap تنفيذية لـMigration 078+.

## 349 — تغيير الطاقة أثناء التشغيل

إذا كانت الجلسة تعمل بالفعل:

- يفتح مقطع جديد.
- تبقى الجلسة نفسها.
- يلتقط المقطع الجديد تسعيره الصحيح.

# UX-12 — Session Completion & Settlement / إنهاء الجلسة والتسوية

**الحالة:** معتمدة — 2026-08-18
**قرارات المناقشة:** 361–372
**القرارات العامة الحاكمة:** ق-17، ق-20، ق-89، ق-90، ق-91، ق-92

## الغرض

توضح الشاشة الفرق بين:

- انتهاء العمل محليًا.
- اكتمال التسوية على Backend.
- إصدار الفاتورة.
- تطبيق الدفعات.
- الرصيد النهائي للمزارع.

ويجب أن يكون التدفق Online وOffline متسقًا وقابلًا
لإعادة المحاولة دون تكرار.

## 361 — حالتان بعد الإنهاء

### بعد تسوية خادمية ناجحة

    تم إنهاء جلسة السقي

    المدة النهائية
    03:12:25

    التكلفة النهائية
    32,347 ريال

### بعد إنهاء Offline

    تم إنهاء الجلسة

    محفوظة على الجهاز
    بانتظار المزامنة

في الحالة الثانية لا يوصف المبلغ بأنه Server Final
قبل نجاح التسوية.

## 362 — إصدار الفاتورة تلقائيًا

بعد نجاح التسوية الخادمية تصدر فاتورة الجلسة تلقائيًا.

لا يحتاج المشغل زرًا مستقلًا باسم «إصدار فاتورة».

Backend الحالي يفصل بين إكمال الجلسة وإصدار الفاتورة،
لذلك يلزم Settlement Orchestration آمن في Migration 078+
أو أحدث.

إعادة المحاولة لا يجوز أن تنشئ فاتورتين للجلسة نفسها.

## 363 — الملخص المالي

بعد التسوية يمكن أن يظهر:

    التكلفة النهائية
    32,347 ريال

    المدفوع
    20,000 ريال

    المتبقي
    12,347 ريال

    مدفوع جزئيًا

إذا لم توجد دفعة:

- لا يظهر «المدفوع: 0».
- يظهر المستحق والحالة المناسبة فقط.

## 364 — الدفعة المقدمة المرتبطة بالجلسة

إذا استلم التطبيق دفعة في سياق الجلسة نفسها قبل
إقفالها، تطبق تلقائيًا على فاتورة هذه الجلسة بعد إصدارها.

مثال:

    الدفعة المستلمة: 40,000
    التكلفة النهائية: 32,347

النتيجة:

    المدفوع على الفاتورة
    32,347 ريال

    الرصيد المقدم المتبقي
    7,653 ريال

الجزء الزائد يبقى رصيدًا مقدمًا للمزارع.

### قاعدة مهمة

لا يستهلك النظام بصمت رصيدًا مقدمًا قديمًا غير مرتبط
بسياق هذه الجلسة لمجرد وجوده.

أي سياسة مستقبلية لتخصيص أرصدة قديمة تحتاج قرارًا
صريحًا أو إجراء تخصيص واضح.

## 365 — حالات الدفع

الحالات المفهومة للمستخدم:

- مدفوع بالكامل.
- مدفوع جزئيًا.
- غير مدفوع.
- رصيد مقدم متبقٍ.

يمكن أن تكون الفاتورة مدفوعة بالكامل وفي الوقت نفسه
يبقى للمزارع رصيد مقدم زائد.

لا تعرض أسماء الحالات الداخلية إلا في Diagnostics.

## 366 — دفعة بعد الإنهاء

إذا بقي مبلغ:

    المتبقي
    12,347 ريال

يمكن إظهار:

    [ تسجيل دفعة ]

فقط إذا كانت صلاحية المستخدم تسمح.

بعد نجاح الدفع والتخصيص يتحدث الرصيد والحالة.

## 367 — جلسة انتهت Offline

بعد Local Durable Completion:

    تم إنهاء الجلسة محليًا

    مدة السقي
    03:12:25

    الدفعة المسجلة محليًا
    20,000 ريال

    التسوية النهائية
    بانتظار المزامنة

عند الاتصال ينفذ التدفق بالترتيب المنطقي:

    مزامنة أحداث الجلسة
        ↓
    إكمال الجلسة على الخادم
        ↓
    حساب التكلفة النهائية
        ↓
    إصدار فاتورة واحدة
        ↓
    تطبيق دفعات الجلسة
        ↓
    إبقاء أي زيادة كرصيد مقدم
        ↓
    تحديث الرصيد
        ↓
    الإشعارات المعتمدة

لا يحتاج المستخدم لإعادة تنفيذ الخطوات يدويًا.

## 368 — اختلاف المحلي عن النهائي

إذا اختلف العرض المحلي عن نتيجة Backend بسبب بيانات
لم تكن محسومة محليًا:

- تعرض النتيجة النهائية.
- يمكن توضيح سبب الفرق إذا كان مهمًا.

أما إذا لم يكن الفرق قابلًا للتفسير وفق قواعد معروفة:

**يحتاج مراجعة**

ولا يعدل المال بصمت.

Live Amount وFinal Charge وInvoice يجب أن تتبع
السياسة المالية نفسها.

## 369 — الوقود منفصل عن فاتورة المزارع

وفق ق-17 وق-91:

- الوقود يتتبع تشغيليًا.
- يدخل في الرقابة والمخزون والتكلفة التشغيلية.
- لا يضاف Fuel Charge مستقل فوق سعر ساعة الديزل الشامل.

Migration 066.

## 370 — لا تعديل مباشر بعد التسوية

بعد التسوية النهائية لا يعدل المستخدم مباشرة:

- المزارع.

- سبب التصحيح.
- من نفذه.
- متى نفذه.
- الأثر المالي المقابل.

- التسوية.
- Conflict أو التصحيح.

نفس السجلات مصدر الحقيقة؛ الاختلاف في الصلاحية والعرض.

## 372 — الإجراءات النهائية

بعد الجلسة تظهر حسب الصلاحية والحالة:

- يعاد استخدام الكيان الحالي.
- لا ينشأ سجل جديد.

إذا كان التطابق Suspect:

- يحتاج اختيارًا أو مراجعة.
- لا يحفظ Duplicate بصمت.

### 383 — الأرض تتبع حساب المزارع في البئر

اختيار المزارع يسبق الأرض.

الأرض يجب أن تتبع Farmer Well Account نفسه وفق ق-80.

### 384 — أسماء الأراضي

يجوز تكرار اسم الأرض بين مزارعين مختلفين.

داخل المزارع نفسه إذا كانت أراضٍ مختلفة تحمل اسمًا
متشابهًا يستخدم وصف إضافي مفهوم مثل:

    أرض الوادي — الشرقية

ولا تفرض أسماء تقنية أو مصطنعة.

### 385 — الأرشفة بدل محو التاريخ

كيان مستخدم تاريخيًا لا يحذف من السجلات السابقة.

بالنسبة للأرض يعاد استخدام حالة:

    active / inactive

الموجودة في النموذج الحالي.

أما تعطيل المزارع أو حسابه في البئر فيحتاج عقدًا واضحًا
قبل التنفيذ إذا لم يكن موجودًا حاليًا.

### 386 — دمج التكرار

Merge عملية حساسة.

يجب:

- الحفاظ على الهوية Canonical.
- نقل العلاقات بطريقة مدققة.
- الحفاظ على التاريخ.
- منع فقد جلسات أو فواتير أو حجوزات.
- منع إنشاء هوية بديلة جديدة.

المصدر الحاكم للتفاصيل:

`technical/SEARCH_DEDUP_ARCHITECTURE.md`.

### 392 — بدء جلسة من الحجز

- المزارع.

إعادة الجدولة والإلغاء عمليتان صريحتان.

- لا ينهي الجلسة.

### 397 — لا جلسة جارية بلا مسؤول

لا يسمح مسار التطبيق العادي بإغلاق المناوبة مع جلسة
جارية غير محسومة.

قبل الإغلاق يجب:

- أو نقل مسؤوليتها إلى مشغل مخول وقبول النقل.

### 398 — ملخص التسليم التشغيلي

- من يسلّم.
- من يستلم.
- الوقت.
- الجلسة الجارية.
- الحجوزات القريبة.
- ملاحظات التشغيل.
- حالة Sync الحرجة.

هذا مفهوم تشغيلي ولا يساوي تلقائيًا Cash Handover.

### 399 — قبول المسؤولية

عند نقل مسؤولية جلسة جارية:

- المشغل المستلم يوافق صراحة.
- لا تنتقل المسؤولية بمجرد اختيار اسمه.
- الرفض يبقي الجلسة على مسؤولية المشغل الحالي.

### فصل مهم — Operational vs Cash Handover

يوجد في Backend الحالي مفهوم Cash Handover مالي
يؤكده المالك.

هذا لا ينسخ قرار 399.

قرار 399 يتعلق بقبول المسؤولية التشغيلية للجلسة/النقل.

لا تخلط Flutter بين:

- Operational responsibility transfer.
- Cash handover confirmation.

### 400 — Offline للمناوبة والتسليم

الإجراءات الميدانية المسموح بها Offline تحفظ Durable
ثم تدخل Outbox.

يجب استخدام Stable Command ID ومنع Duplicate عند Retry.

لا يعتبر Local acceptance Server acknowledged قبل Sync.

- النهاية.
- الجلسات المرتبطة.
- التسليمات.
- الحالة.

- قابل للتعديل قبل التنفيذ.
- ليس تسوية خفية.
- لا يستهلك Advance قديم تلقائيًا.

### 418 — سياق الجلسة أو الفاتورة

- تصبح هي الهدف الافتراضي.

الرصيد المقدم القديم لا يستهلك تلقائيًا.

    الرصيد المقدم = 10,000

- المبلغ.
- الطريقة.
- الدافع عند وجوده.

### 423 — الدفع Offline

عند الحفظ محليًا:

    تم حفظ الدفعة على الجهاز
    بانتظار المزامنة

لا تعرض:

    تم الترحيل محاسبيًا

ولا سند Server نهائي قبل ACK.

### 424 — منع التحصيل المكرر

الهدف:

- الاستقطاعات الخاصة به.
- صافي مستحقه.
- ما دفع له.
- المتبقي.

- تفاصيل مصروفات أو دفعات شخصية لشريك آخر بلا سبب.

# س — كلمات المرور / Option B

### PA-02-53 — Recoverable Current Password Vault

تم اعتماد **Option B**.

الهدف المنتج:

**Platform Super Admin يستطيع عرض Current Password
الحالية لأي حساب عندما تكون النسخة الموثوقة متاحة
في Password Vault.**

Supabase Auth يبقى مسؤول Authentication الأساسي.

لكن النظام يضيف مخزنًا منفصلًا:

**Recoverable Password Vault**

يحفظ نسخة مشفرة قابلة لفك التشفير من كلمة المرور.

لا تخزن Plaintext Password في Database.

### PA-02-54 — Coverage and Existing Passwords

كلمات المرور الموجودة قبل تشغيل Vault:

لا يمكن استرجاعها بأثر رجعي من Supabase Hash.

تتحول إلى Vault-managed عند أول:

- Account Creation.
- Password Change.
- Password Reset.
- Admin Password Reset.

يمر عبر Password Orchestrator الجديد.

إلى ذلك الوقت تعرض الإدارة:

    كلمة المرور الحالية غير متاحة في المخزن

ولا تعرض Guess.

### PA-02-55 — Reveal Password UX

داخل Account Security:

    كلمة المرور
    ••••••••••••
    [ عرض كلمة المرور ]

Reveal:

- Platform Admin only.
- masked by default.
- explicit action.
- short-lived display.
- audited.
- password نفسها لا تدخل Audit Payload.

إذا Vault غير موثوقة أو Stale:

لا يظهر Password قديمة بوصفها الحالية.

### PA-02-56 — Password Mutation Orchestration

كل Supported Password Mutation يجب أن تمر عبر
Trusted Password Orchestrator.

يشمل:

- user creation.
- first password.
- self password change.
- forgot-password reset.
- platform-admin reset.

Target sequence:

    authenticated/authorized request
        ↓
    validate password policy
        ↓
    encrypt candidate into pending vault version
        ↓
    update Supabase Auth password
        ↓
    promote vault version to active
        ↓
    audit metadata only

إذا فشل Auth update:

تلغى Pending Vault version.

إذا نجح Auth update ثم تعطل Finalization:

تبقى encrypted candidate قابلة للمصالحة بواسطة
Operation ID بدل فقد Password الجديدة.

### PA-02-57 — Password Vault Security Contract

Password Vault تحتاج:

- encryption in transit.
- authenticated encryption at rest.
- per-record random nonce.
- versioned encryption format.
- Envelope Encryption.
- Data Encryption Key.
- Master/Key Encryption Key خارج Database.
- key rotation.
- Platform Admin authorization.
- reveal audit.
- no plaintext logs.
- no analytics capture.
- no local/mobile cache.
- no sync outbox.
- no browser persistent storage.
- no password inside support notes.
- stale-state detection.
- no stale password shown as Current.
- permanent security tests.

التصميم المستهدف يستخدم خوارزمية Authenticated
Encryption قوية مثل AES-256-GCM أو ما يعتمد رسميًا
في بيئة التنفيذ لاحقًا.
