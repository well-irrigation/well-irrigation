# Documentation Gate — بوابة اكتمال التوثيق

**القرارات الحاكمة:** ق-97، ق-104
**آخر تحديث:** 2026-08-19
**الحالة:** إلزامية ونافذة

## 1. الهدف

هذه البوابة تمنع الانتقال من موضوع إلى موضوع جديد قبل
أن تصبح معرفة الموضوع الحالي محفوظة بصورة كافية داخل
المستودع.

القاعدة الأساسية:

**إذا احتاج نموذج ذكاء اصطناعي جديد إلى المحادثة السابقة
لفهم قرار مهم، فالتوثيق لم يكتمل بعد.**

## 2. متى تطبق؟

تطبق قبل الانتقال بعد أي دفعة تشمل واحدًا أو أكثر من:

- قرار مشروع جديد.
- تغيير قرار قديم.
- UX معتمد.
- قاعدة أعمال.
- قاعدة مالية.
- قاعدة أمنية.
- قاعدة Offline أو Sync.
- قرار معماري.
- Backend Contract.
- Migration.
- تنفيذ Flutter.
- إصلاح Bug مؤثر.
- فتح أو إغلاق Gap.
- تغيير طريقة العمل.
- تغيير طريقة التوثيق.
- تغيير بروتوكول الأوامر.
- تغيير مصادر الحقيقة.
- تغيير نقطة الاستئناف.

## 3. الشرط الصفري — تحديد نوع التغيير

قبل التوثيق يجب معرفة أي أنواع السجل تنطبق:

- Decision.
- UX.
- Architecture.
- Implementation.
- Verification.
- Open Issue.
- Documentation Governance.
- Terminal/Workflow Governance.
- Historical Record.

هذا يحدد الملفات التي يجب تحديثها.

## 4. Decision Record — سجل القرار

إذا كانت الدفعة تحتوي قرارًا حاكمًا، يجب أن يحفظ
`DECISIONS.md` ما ينطبق من:

- رقم القرار.
- التاريخ.
- الحالة.
- المشكلة أو السياق.
- القرار نفسه.
- سبب القرار.
- المصادر التي بني عليها.
- البدائل المهمة التي استبعدت، إن وجدت.
- سبب استبعاد البدائل المهمة.
- المخاطر أو Trade-offs المهمة.
- الأثر على UX.
- الأثر على Backend.
- الأثر على البيانات.
- الأثر على Offline/Sync.
- الأثر على الأمن والصلاحيات.
- الأثر المالي عند الانطباق.
- القرار السابق الذي ينسخه إن وجد.
- ما يحتاج تنفيذًا لاحقًا.
- ما يحتاج اختبارًا.
- المسألة المفتوحة الناتجة إن وجدت.

ليس مطلوبًا اختراع بدائل شكلية عندما لا توجد بدائل
حقيقية، لكن لا يجوز حذف بديل مهم كان مؤثرًا في القرار.

## 5. Rationale — أسباب القرار

عبارة:

    اعتمدنا X

وحدها غير كافية إذا كان السبب مهمًا لاستمرار المشروع.

يجب حفظ السبب الذي يحتاجه النموذج التالي لفهم:

- لماذا اخترنا هذا التصميم؟
- ما المشكلة التي يحلها؟
- ما الذي كنا نحاول تجنبه؟
- ما القيود التي أثرت في القرار؟
- ما الذي قد يجعلنا نعيد النظر مستقبلًا؟

لا تحفظ Chain of Thought داخلية.

يحفظ فقط Reasoning Record قابل للمراجعة:

- أدلة.
- افتراضات مهمة.
- خيارات حقيقية.
- Trade-offs.
- استنتاج.
- قرار.

## 6. UX Gate

إذا كانت الدفعة UX، يجب أن يحتوي `UX_UI_SPEC.md`
حسب الانطباق على:

- اسم الشاشة أو التدفق.
- الغرض.
- متى تظهر.
- من يراها.
- ترتيب المحتوى.
- البيانات المعروضة.
- الأزرار.
- الانتقالات.
- حالات Loading.
- حالات Empty.
- حالات Error.
- حالات Offline.
- حالات Sync.
- Conflict.
- Permissions.
- Accessibility.
- منع الضغط المزدوج عند الحاجة.
- الحالات المالية.
- حالات النجاح.
- حالات الفشل.
- ما يحدث بعد Process Death عند الانطباق.
- ما يحدث بعد Reboot عند الانطباق.
- Backend requirements.
- API requirements.
- Migration requirements.
- الاختبارات المطلوبة.
- ما هو مؤجل.
- ما هو غير منفذ.

## 7. Technical Gate

إذا نتج عن القرار أثر تقني، يجب تحديث المصدر التقني
الحاكم المناسب.

أمثلة:

- `API_ARCHITECTURE.md`
- `SYNC_ARCHITECTURE.md`
- `SEARCH_DEDUP_ARCHITECTURE.md`
- `ACTIVE_SESSION_ARCHITECTURE.md`
- `SESSION_SETTLEMENT_ARCHITECTURE.md`
- أي وثيقة تقنية مستقبلية حاكمة للموضوع.

يجب توثيق:

- الواقع الموجود حاليًا.
- العقد المستهدف.
- ما يعاد استخدامه.
- ما لا يجوز تكراره.
- حدود الأمن.
- مصدر الحقيقة.
- حالات الخطأ.
- Idempotency عند الحاجة.
- Concurrency عند الحاجة.
- Offline behavior.
- Acceptance criteria.

## 8. Open Issues Gate

أي Gap أو تعارض أو عمل إلزامي غير منفذ يجب أن يظهر
في `OPEN_ISSUES.md`.

يجب أن يوضح:

- المشكلة.
- الواقع الحالي.
- القرار الحاكم.
- سبب أهميتها.
- هل تمنع Production؟
- ما الذي يغلقها؟
- الاختبارات اللازمة للإغلاق.

لا يجوز دفن Gap فقط في:

- محادثة.
- UX spec.
- Comment في الكود.
- Commit message.

## 9. Progress Gate

`PROGRESS.md` يسجل فقط ما ثبت بالفعل.

يجوز أن يسجل:

- وثيقة أنشئت ورفعت.
- Commit مثبت.
- Migration اختبرت.
- Test result.
- UI نفذت وثبتت.
- فحص جهاز حقيقي.
- Field test.

لا يجوز أن يسجل Planned أو Pending بوصفه إنجازًا.

إذا لم تشغل الاختبارات، لا تحدث أرقام Baseline.

## 10. Changelog Gate

كل دفعة توثيق جوهرية تسجل في `DOC_CHANGELOG.md`.

يسجل:

- التاريخ.
- المجال.
- الملفات الرئيسية.
- ماذا تغير.
- لماذا تغير.
- القرار المبرر.
- هل التغيير توثيقي أم تنفيذي.
- هل تغير Baseline أم بقي كما هو.

## 11. Resume Gate

`RESUME_POINT.md` يجب أن يعكس بعد كل دفعة:

- آخر القرارات المهمة.
- ما أصبح معتمدًا.
- ما أصبح موثقًا.
- ما بقي Pending.
- المسائل المفتوحة الحرجة.
- آخر Baseline مثبت عند الحاجة.
- الموضوع التالي فقط.
- ما الذي يجب ألا يعاد فعله.

هو المصدر الوحيد لنقطة الاستئناف.

## 12. Project Map Gate

يحدث `PROJECT_MAP.md` عندما يتغير:

- آخر قرار حاكم.
- مصدر حقيقة.
- وثيقة جديدة حاكمة.
- ترتيب قراءة.
- اسم موضوع.
- مسار استئناف.
- بروتوكول عمل.

## 13. Implementation Matrix Gate

إذا كان القرار له أثر تنفيذي أو اختبار مستقبلي:

`DECISION_IMPLEMENTATION_MATRIX.md`

يجب أن يبين:

- القرار.
- الوضع الحالي.
- ما هو منفذ.
- ما هو Pending.
- الاختبارات أو الأدلة المطلوبة.
- حالة الإغلاق.

## 14. Invariants Gate

إذا أنتج القرار قاعدة لا يجوز كسرها أثناء التنفيذ،
تسجل في:

`technical/INVARIANTS.md`

ولا تكرر التفاصيل الكاملة؛ تسجل القاعدة الثابتة
وتشير للمصدر الحاكم.

## 15. README Gate

`README.md` لا يحدث لكل قرار.

يحدث فقط إذا تغير:

- مدخل المشروع.
- ترتيب القراءة.
- بروتوكول الاستلام.
- مصدر رئيسي يجب أن يعرفه أي نموذج جديد.

الهدف منع README من التحول إلى Snapshot سريع التقادم.

## 16. Evidence Gate

كل ادعاء من نوع:

- Implemented.
- Verified.
- Closed.
- Tested.
- Migrated.
- Pushed.

يحتاج دليلًا مناسبًا.

الأدلة تشمل:

- Terminal Output.
- Commit SHA.
- Push result.
- Test result.
- Migration log.
- Structural inspection.
- Device test.
- Field test.

لا يجوز ترقية الحالة اعتمادًا على النية.

## 17. Git Gate

دفعة التوثيق لا تغلق قبل:

1. `git diff --check`.
2. التحقق من الملفات المتوقعة.
3. Contract/content validation.
4. Stage.
5. `git diff --cached --check`.
6. Commit.
7. Push.
8. Worktree clean.

إذا فشلت خطوة، لا ينتقل العمل إلى الموضوع التالي.

## 18. Documentation Gate PASS

تعتبر البوابة ناجحة فقط إذا كانت جميع البنود المنطبقة
مكتملة.

علامة نجاح مقترحة:

    DOCUMENTATION_GATE=PASS

لكن العلامة وحدها ليست دليلًا إذا سبقها Failure.

## 19. Documentation Gate FAIL

تعتبر البوابة فاشلة إذا كان هناك عنصر منطبق ناقص.

أمثلة:

- قرار بلا سبب.
- UX بلا حالات خطأ لازمة.
- Gap معروفة غير مسجلة.
- تنفيذ يوصف Verified بلا اختبار.
- Changelog غير محدث.
- RESUME_POINT قديم.
- Commit غير موجود.
- Push فشل.
- Worktree غير نظيف.

عند FAIL:

**لا يبدأ النقاش التالي.**

يصلح النقص أولًا.

## 20. Meta-documentation — توثيق قواعد التوثيق نفسها

أي تغيير على:

- AI handoff.
- Collaboration method.
- Documentation Gate.
- Terminal command rules.
- Sources of truth.
- Documentation workflow.

يخضع للبوابة نفسها.

أي قرار جديد عن طريقة التوثيق يجب أن يسجل:

- في `DECISIONS.md`.
- في البروتوكول المتأثر.
- في `INVARIANTS.md` إذا أنتج قاعدة ثابتة.
- في `DECISION_IMPLEMENTATION_MATRIX.md`.
- في `DOC_CHANGELOG.md`.
- في `PROGRESS.md` بعد ثبوته.
- في `RESUME_POINT.md`.
- في `PROJECT_MAP.md` عند تغير الخريطة.
- وفي Git.

بذلك تكون قواعد التوثيق نفسها قابلة للتتبع.

## 21. قاعدة عدم التكرار

«توثيق كل شيء» لا يعني نسخ النص نفسه في عشرة ملفات.

المطلوب:

- الحقيقة التفصيلية في مصدرها الحاكم.
- القرار في Decisions.
- القاعدة المختصرة في Invariants.
- التنفيذ في Matrix.
- الإنجاز المثبت في Progress.
- تاريخ التعديل في Changelog.
- نقطة المتابعة في Resume.
- الإحالة في Project Map.

هذا يحقق الشمول دون خلق مصادر حقيقة متعارضة.

## 22. قاعدة Traceability

يجب أن يستطيع النموذج تتبع المسار:

    سبب
      ↓
    قرار
      ↓
    UX / Architecture
      ↓
    Gap أو Implementation Requirement
      ↓
    Migration / API / Flutter
      ↓
    Test
      ↓
    Verified Progress

وعكسه أيضًا:

    تنفيذ
      ↓
    أي قرار يبرره؟
      ↓
    أي اختبار يثبته؟

إذا انقطع هذا المسار في نقطة مهمة، فهناك Gap توثيقية.

## 23. Gate Checklist المختصر

قبل الانتقال اسأل:

- هل القرار موثق؟
- هل السبب موثق؟
- هل الحالة صحيحة؟
- هل الأدلة موثقة؟
- هل UX موثق؟
- هل التقنية موثقة؟
- هل Gap مسجلة؟
- هل الاختبارات المطلوبة معروفة؟
- هل Matrix محدثة؟
- هل Invariants محدثة عند الحاجة؟
- هل Progress يسجل فقط المثبت؟
- هل Changelog محدث؟
- هل Resume محدث؟
- هل Project Map محدث عند الحاجة؟
- هل Git Commit موجود؟
- هل Push نجح؟
- هل Worktree نظيف؟

إذا كانت إجابة عنصر منطبق «لا»:

    DOCUMENTATION_GATE=FAIL

## 24. قاعدة الانتقال

لا ينتقل النموذج من موضوع معتمد إلى الموضوع التالي
إلا بعد:

    DOCUMENTATION_GATE=PASS

الاستثناء الوحيد هو معالجة فشل التوثيق نفسه، وهي تبقى
جزءًا من الموضوع الحالي وليست انتقالًا لموضوع جديد.

## 25. Definition of Done

يعتبر الموضوع موثقًا بما يكفي للاستئناف عندما يستطيع
نموذج جديد، من المستودع وحده:

- معرفة ما قرر.
- معرفة لماذا.
- معرفة الواقع الحالي.
- معرفة ما هو غير منفذ.
- معرفة المخاطر والفجوات.
- معرفة مصدر الحقيقة.
- معرفة الاختبارات المطلوبة.
- معرفة آخر دليل مثبت.
- معرفة الخطوة التالية.
- متابعة العمل دون سؤال المالك لإعادة شرح التاريخ السابق.

## ق-104 — Research & Standards Evidence Gate

قبل Documentation Gate، إذا كانت الدفعة من النوع الذي
ينطبق عليه البحث، يجب إثبات أن:

- `RESEARCH_STANDARDS_GATE.md` طبقت.
- Source of Truth الداخلي قرئ أولًا.
- Standards الرسمية ذات الصلة روجعت.
- Official Platform Documentation روجعت عند الانطباق.
- User Feedback فصل عن Standards Authority.
- Project Fit وثق.
- Recommendation صنفت عند الحاجة.
- أي Standards Conflict ذكر صراحة.
- أي Supersession سجل في `DECISIONS.md`.

لا يجوز أن يمر Documentation Gate لقرار أمني جوهري
موصوف Best Practice إذا كان البحث الفعلي يظهر أنه
Exception ولم يوثق ذلك.

الترتيب:

    RESEARCH_STANDARDS_GATE=PASS
        ↓
    Adoption
        ↓
    Documentation Gate
        ↓
    Git closure
