## 2. أسباب تأخير المقدمة المثبتة والمغلقة محليًا

1. كان `OfflineSessionCoordinator._triggerSync` ينتظر
   `commandQueuedScheduler` قبل `SyncEngine.runAfterCurrent`. في التطبيق
   يمر ذلك عبر انتقال المصادقة ثم تسجيل `WorkManager`. إعادة إنتاج حتمية
   بمجدول محجوز: الأمر محفوظ لكن النقل لا يبدأ حتى تحرير المجدول. ينطبق
   الانتظار نفسه على `bookingSaved`.
2. كان `runAfterCurrent` يدمج طلبًا أثناء المرور الإضافي في مستقبله
   القائم بلا الاحتفاظ بإيقاظ لاحق. الاختبار يرسل أمرين ويبقي الثالث
   محفوظًا دون محاولة؛ بعد الإصلاح يرسل الثلاثة مرة واحدة، بلا دورات
   متوازية.
3. كان تحديث الإسقاط ينتظر نهاية تقرير الدورة كلها. اختبار قبول البدء مع
   انتظار دفعة مستقلة يثبت بقاء المنظور قديمًا حتى انتهاء الدفعة. إشعار
   بعد حفظ النتيجة يعيد إسقاط النطاق المعروض دون انتظار تلك الدفعة.

هذه أسباب مثبتة بالاختبارات، وليست نسبةً جازمةً لحادثة الهاتف إلى
`WorkManager`. ولم يثبت أن مؤشّر الاتصال أو تراجع أمر معيّن سبّبا حادثة
الهاتف.

## 3. المسار الحالي

فعل بشري ← إنشاء مغلف ثابت ← معاملة حفظ متينة مكتملة ← إيقاظ أمامي
فوري للمحرك وحجزه الحالي. تسجيل الخلفية مستقل ولا يحجز هذه الفرصة.

`ForegroundSyncWake` يجمع جدولة الخلفية المتداخلة حسب الحساب. قناة
المنسق تترك دمج التصريف للمحرك لتحفظ نطاق كل قارئ. قناة تأكيد الحجوزات
تدمج دوراتها حسب الحساب وتحتفظ بطلب مرور جديد أثناء الدورة القائمة.
`runAfterCurrent` يحتفظ أيضًا بإيقاظ وصل أثناء المرور الإضافي، ويجمع
مؤشرات التقدم لكي لا تضيع إشعارات نتائج الأرض أو الأوامر المقبولة.
لا مؤقت أو تأخير اصطناعي أو إنشاء Command ID جديد في هذه الآلية.

يملك `BookingRepository.saveLocalBooking` الإيقاظ بعد اكتمال حفظه، بدل
الاعتماد على بقاء نموذج الحجز مركبًا. أعيد استخدام نفس منسق تأكيد
الحجوزات داخل نسخة المستودع، مع بقاء الحجز الشرطي هو ضمان عدم تكرار
الإرسال.

فتح التطبيق وعودته وعودة الاتصال تطلب فرصة أمامية عبر الربط الموثّق
بالحساب. مؤشّر الشبكة لا يمنع أول فرصة أمامية؛ النقل هو الذي يثبت
نتيجتها. قيود الشبكة وكبح الإيقاظ وتراجع `WorkManager` بقيت للخلفية كما
كانت.

## 5. حفظ النتيجة والعرض

إشعار `onCommandSettled` يصدر بعد حفظ القبول والربط/الإيصال، وليس بمجرد
ورود HTTP. يعيد المنسق قراءة المسقط الحالي للنطاق المعروض فقط، مع حراس
تسلسل القراءة والحساب والبئر والأصل والاختيار الحالي. لا يصنع مالًا أو
حالة جلسة من رد خام. تغيير الاختيار يبطل تحديثًا متأخرًا أيضًا عند نهاية
الدورة. تعطل القارئ/الإشعار لا يلغي قبولًا محفوظًا ولا يعيد الإرسال.

القراءات الخادمية الكاملة عند الحاجة تبقى في تدفق الواجهة القائم، لا
داخل معاملة الحفظ أو الإشعار. المتابعة المالية المحلية تبقى قراءة فقط.
قواعد `not_found` و`unresolved` وreceipt-first و`legacy_retired` وعزل
التوابع القديمة لم تتغير. الحجز الشرطي وCommand ID الثابت باقيان.

## 6. التشخيص المؤقت للجهاز

المؤشر: `SYNC_LATENCY_DIAG`. الحقول المسموحة فقط: مرحلة، وقت UTC، نوع
أمر، زمن منذ `createdLocalAt`، حالة المغلف المقروء، عدد المحاولات، انتظار
موعد محاولة، وتصنيف نتيجة/حارس من قائمة مسموحة. لا IDs أو حمولة أو
بيانات مزارع أو tokens أو رسائل استثناء. مراحل الحساب العامة تحمل
نوعًا وزمن أمر فارغين لأنها لا تخص مغلفًا واحدًا. حالة الحقل هي حالة
المغلف الذي بدأ الخطوة، وليست إعادة قراءة بعد كل خطوة.

المراحل: `human_action`, `command_created`, `outbox_persist_begin`,
`outbox_persist_end`, `sync_requested`, `background_schedule_begin`,
`background_schedule_end`, `sync_engine_awake`, `candidate_found`,
`reservation_begin`, `reservation_acquired`, `reservation_blocked`,
`transport_begin`, `transport_end`, `result_persisted`,
`projector_refresh_begin`, `projector_refresh_end`, `drain_end`.

المقارنة المطلوبة من الجهاز: نهاية الحفظ إلى طلب المزامنة؛ طلبها إلى
استيقاظ المحرك؛ الاستيقاظ إلى المرشح؛ الحجز؛ انتظار النقل؛ حفظ النتيجة؛
تحديث الإسقاط. بداية النقل تقع قبل انتظار تسجيل الخلفية أو قبل انتهائه.
العمليات الأقدم قد تستغرق قراءات إيصال/شبكة داخل المحرك المتسلسل؛ تظهر
مدتها في `transport_begin/end` دون افتراض أنها أصل حادثة الهاتف.
لم يضف الإصلاح استردادًا موازيًا أو مهلةً تلغي طلبًا خرج إلى الشبكة.

## 7. الفجوة المنفصلة: تعليق SQLite على Android (F-SYNC / ق-138)

بعد إغلاق أسباب الإيقاظ الأمامي أعلاه، بقي على الجهاز نمط مختلف: تجمّد
متزامن لشاشات متعددة ثم عودة متزامنة، مع انتظار قراءات محلية يبلغ عشرات
الثواني ودقائق، بينما الخادم يعالج في أجزاء الثانية.

الأسباب الثلاثة في القسم 2 **لا تفسر هذا النمط**: الإيقاظ يقرر متى يُطلب
النقل، لا مدة انتظار قراءة محلية على قفل ملف. أُدرجت هذه الفجوة
مستقلة، وأُثبتت بأدلة جهاز مسجلة، ثم أُغلقت تقنيًا برقعة إنتاجية.

- السبب المثبت: `Android sqflite single-worker starvation under competing
  same-file connections` — `THREAD_COUNT=1` في `sqflite_android 2.4.3`.
- الدليل الحاسم: بداية قراءة الواجهة بعد تحرير المعاملة بـ12ms، وقياسات
  `132841ms` و`263242ms` و`87541ms` و`82644ms`.
- الإصلاح: نسخة vendored من `sqflite_android 2.4.3` في `third_party/`
  بـ`THREAD_COUNT=2`، بلا `devSetOptions` في الإنتاج.
- الحالة: **CLOSED** / IMPLEMENTED + LOCAL VERIFIED + DEVICE ACCEPTED +
  CI VERIFIED + MERGED (PR #70، merge commit
  `b7736d18cdffd89b39b776392256e2598a62f834`، 2026-11-13T18:36:21Z؛
  CI workflow `checks`، run `43482437255`، success).

كل الأرقام والأدلة والبدائل المستبعدة في
`SQLITE_TRANSACTION_LOCK_AUDIT.md`؛ ولا تُنسخ هنا.

**ما بقي غير مثبت:** النسبة الدقيقة لمدة الـ140 ثانية الأولى، والتحسن

## 8. مسألة مستقلة: المصالحة بعد التصحيح (F-RECON) — تنفيذ مغلق، ملاحظة E2E باقية

كان تصحيح الجلسة التشغيلي يُقبل على الخادم بينما يبقى سجل المصالحة
`status=pending` مع `attempt_count=0` و`last_attempt_at=NULL`، بلا
مستهلك runtime يبدأ `billing.reconcile_session_correction(...)`.
هذا **ليس** عطل مزامنة، ولا يُخلط بـF-SYNC.

**تحديث 2026-11-14 (ق-139):** المستهلك موجود ومُنشَّط — طابور متين،
معالج خاص، هوية تنفيذ تقنية، وإيقاظ مجدول fail-closed. الحالة:
**`CLOSED / PASS` / IMPLEMENTATION CLOSED + CLOUD ACTIVATED +
CONTROLLED CANARY VERIFIED + AUTOMATIC PRODUCTION BUSINESS E2E
VERIFIED**؛ وقد تحقق المسار التلقائي الإنتاجي كاملًا في `2026-11-14`
بتصحيح شرعي واحد بلا نداء يدوي.
عند وجود موافقة مالية يدوية سابقة لا تُكتب فوقها آليًا؛ ذلك يحل إلى
`financial_review_required`. التفصيل في
`R6C2_SESSION_FINANCIAL_RECONCILIATION.md` قسم `R6-C2-D`؛ ولا بند E2E
متبقٍ في `../memory/OPEN_ISSUES.md`.
