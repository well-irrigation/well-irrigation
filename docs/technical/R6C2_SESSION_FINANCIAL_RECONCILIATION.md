## نطاق التسليم والقرارات المعتمدة

- `MANUAL_VS_OLDEST_PRIORITY = CLOSED`: الفاتورة الأقدم المؤهلة تمنع
  اختيار الأحدث، ولو بقي من الأقدم جزء فقط. يحفظ اختيار المالك كما هو
  عند فشله لاحقًا؛ لا حجز ولا تبديل مصدر ولا اعتماد جزئي. الحفظ والاعتماد
  يعيدان الاشتقاق تحت الجذر نفسه، ويعرضان مراجعة المبالغ عند تغير الأهلية.
- سلطة استعمال واحدة: `finance.distribution_source_consumptions` للاستخدام
  الآلي واليدوي والسداد المنفصل للمستحق المتبقي لشريك خرج. المبلغ الأصلي
  دليل لا يكتب فوقه؛ المبلغ المؤهل الفعّال من المصدر القانوني الحالي،
  والمستخدم والمتبقي مشتقان منه ومن التاريخ الدقيق. لا دين فاتورة موازٍ.
  تصحيح C2 قد يغيّر الأساس الفعّال دون تعديل أصل الفاتورة؛ الاستعمال
  المعتمد محمي من التحرير/التعديل الذي يقتضي مراجعة وفق الأسس السابقة.
- المصروف المؤهل مستحق شريك مثبت بقيده الأصلي؛ الفاتورة مصدر خصم
  مرتبط بسياسة سقي الشريك ورصيدها القانوني القابل للتحصيل. لا مبلغ حر.
- الآلي هو الافتراضي. المالك النشط يختار جزءًا أو يعود للآلي قبل الاعتماد؛
  اختيار واحد فعّال بتاريخ نسخ. التعديل والإلغاء لا ينشئان قيدًا أو دفعة.
- الاعتماد يتحقق من جميع المقترحات أولًا، ثم يستهلك المقادير بالضبط مع
  الآثار المحاسبية في معاملة واحدة. أي فشل يعيد كل الأبناء. الاستخدام
  المتزامن في دورات لاحقة لا يتجاوز المتبقي، ولا يحمل إعادة الحساب أي
  اختيار يدوي تلقائيًا. الدورة القديمة بلا أساس مصادر دقيق تحتاج إعادة
  حساب صريحة، وفق قرار المالك، ولا يعاد كتابة توزيع معتمد.
- الغامض القديم محجور. مراجعة المصروف تحفظ المستهلك والمتبقي المؤكدين.
  مراجعة الفاتورة تدخل سلطة الدين الفعّال نفسها عبر 015؛ المبلغ المتنازع
  عليه محجوب عن التحصيل وإعادة الاستعمال حتى يقرر المالك النشط وحده.
- الشريك الخارج: لا سطر أرباح جديد لتسديد الباقي. السداد المنفصل للمالك
  النشط فقط، ينقص المستحق المثبت بقيد نقدي حقيقي واستهلاك في السلطة

- سياسة السقي تتغير للفواتير الجديدة فقط؛ التاريخ محفوظ، ولا تبديل لسياسة

## حدود المزارع المعتمدة في المتابعة

المشغل المخول. إيقاف الحساب يمنع جلسات وحجوزات جديدة، ويبقي تحصيل ديونه
السابقة والتاريخ متاحين. لا تغيير لحالته العامة في الآبار الأخرى.
حفظ الحد لا يعيد حساب دين أو جلسة قديمة ولا يخترع سياسة ائتمان جديدة.
التاريخ append-only، والنطاق والصلاحية يعاد فحصهما بعد الانتظار.

تنبيه تصحيح للتدقيق السابق: 072 تسحب منح الكتابة المباشرة الأقدم في

في المتابعات دفاع صريح ومعالجة لمنح الأعمدة أيضًا؛ لا إعادة منح DML
ولا توسعة سلطات اعتمادًا على منح تاريخية منسوخة. أزيل تعديل غير لازم
لسمة platform admin لأن استنتاج قابلية تعديلها من 017 وحدها لم يكن صحيحًا.

## الرسم الساكن قبل الإصلاح وبعده

قبل:

```text
C2: FINANCIAL ROOT -> WELL -> PERIOD
period update: PERIOD -> AUDIT INSERT -> WELL KEY SHARE
approval: FINANCIAL ROOT -> CYCLE
partner payment: LINE -> CYCLE -> POSTING -> FINANCIAL ROOT
financial command: COMMAND -> WELL
C1 operational command: WELL -> SESSION -> COMMAND
notification job: SESSION UPDATE -> NOTIFICATION -> WELL KEY SHARE
```

بعد، للمسارات العادية ذات البئر الواحد:

```text
FINANCIAL ROOT (transaction advisory, READ COMMITTED)
  -> WELL operational protection when required
  -> branch domain parents/children
  -> protected posting / audit / notification

period:      ROOT -> PERIOD rows ORDER BY id -> REOPEN REQUEST
             -> AUDIT / NOTIFICATION
source:      ROOT -> CYCLE -> LINE rows ORDER BY id
             -> SOURCE STATE rows ORDER BY id -> EXPENSE / INVOICE
             -> exact consumption + approval effects
payment:     ROOT -> WELL -> existing verified C0.2 account/payment/
             allocation/credit/invoice order (not cosmetically reordered)
correction:  ROOT -> WELL -> SESSION -> WORK -> ACCOUNT -> children
command:     ROOT -> WELL -> COMMAND for financial commands
operational: WELL -> SESSION / COMMAND (C1 stays operational-only)
posting:     already-owned ROOT -> draft journal domain row
             -> ensured PERIOD rows ORDER BY id, FOR SHARE
             -> protected posted status and child effects
scheduler:   WELL -> SESSION -> NOTIFICATION (no first root acquisition)
```

ليس المقصود فرض ترتيب كلي شكلي داخل C0.2. أقفال المسودات قد تسبق
صف الفترة داخل الفرع، لكن كل الطرفين الماليين يملكان الجذر نفسه قبلها؛
الفترة محمية قبل نشر القيد. لذلك لا يوجد تنفيذان ماليان متنافسان للبئر
نفسه يستطيع أحدهما امتلاك PERIOD والآخر امتلاك WELL بصورة متعاكسة.
العلاقات العكسية المحلية التي تهيمن عليها نقطة التسلسل المشتركة ليست
دورة انتظار متزامنة قابلة للوصول. أصناف الصيانة ليست ضمن هذا الإثبات.

`billing.lock_customer_credit_well(uuid)` يملك advisory transaction lock
فقط، لا صف well؛ المفتاح بالضبط `customer-credit-well:<uuid>`، ويشترط
READ COMMITTED. إعادة اكتسابه في المعاملة نفسها آمنة. فحص
`billing.require_customer_credit_well_lock` يتحقق من `pg_locks`، ولا يكتسب
قفلًا جديدًا. لا namespace إنتاجية موازية.

`finance.post_journal_entry` و`finance.ensure_periods` وطفل عكس القيد
ومساعدو النشر/التحديث يؤكدون الملكية السابقة، وتُنزع EXECUTE العادية
عنهم. التأمين الأول عند الحدود العليا، لا في عمق طفل مقفل سابقًا.
كل استدعاءات post_journal_entry الإنتاجية الحالية الخمسة عشر، واستدعاء
ensure_periods الوحيد من post_journal_entry، راجعت عبر تعريفاتها الحالية.
لا استدعاء ديناميكي إنتاجي مكتشف لهذين الاسمين. generate_distribution_batch
وnotify_distribution_finalized حُذفتا أصلًا في 052، فلا يعاد إحياؤهما.

مسارات الحدود العليا المغطاة: الفترات الأربعة؛ حساب/اعتماد/صرف التوزيع؛
تسجيل/قرار المصروف؛ استحقاق/صرف الراتب؛ اعتماد/ترحيل الافتتاحيات؛ شراء/
استهلاك/جرد الوقود؛ إكمال/إيقاف/استئناف/تغيير طاقة الجلسة؛ تسوية occurrence؛
التسليم والترحيل وفتح/إغلاق المناوبة والرد على نقل مسؤول التحصيل؛ تسجيل/
تخصيص/عكس الدفع؛ إصدار الفاتورة؛ إنشاء/حسم هوية المزارع وحساب البئر؛
والحدود المعتمدة للإعدادات والشركاء. فحص الدعوات غير المالي لا يترحل
إلى الجذر المالي من داخل قفل طلب؛ التأكيد الذي يغير علاقة مالية يمتلك
النطاق أولًا. core.merge_persons مقيد بالصيانة، والتزامن متعدد الآبار
مؤجل، ولا يدخل استنتاج إغلاق المسارات العادية.

المصادر الضمنية: FK audit.audit_logs.well_id باقٍ، وكذلك زناد track_changes.
المثل في notifications وjournal/invoice/payment/source foreign keys.
حماية well قبل صفوف الجلسة/الأمر في التدفقات المشتركة تمنع دورة
WELL -> COMMAND -> WELL. تعديل هوية حساب المزارع يملك نطاقه قبل صف
الشخص المشترك. إجراءات التنبيه التشغيلية تمسك well قبل session update.

## حفظ قيمة الدفع

قبل نشر دين أقل: يحرر الزائد من التسديد الصريح عبر release_credit_application
ثم release_payment_allocation بهويات مشتقة من correction+revision+type+target.

غير القابل للتحرير لا يُخترع له أثر؛ يبقى للمراجعة.
بعد نشر الرسم/الفاتورة، rebalance_payment_capacity يعالج سعة الدفع
المرتبط بالرسم عبر C0.2، دون payment أو receipt جديد. السعة المتبقية
للمصدر نفسه تتحول حسب primitive القائمة إلى credit مرتبط، مرة واحدة.
زيادة الدين لا تسحب رصيدًا صُرف في دين آخر ولا تنفق credit تلقائيًا؛
تظهر outstanding، ويمكن للإجراء الصريح القائم تطبيق المتاح لاحقًا.
تحرير application يحفظ صفه الأصلي ويستعمل C0.1 وصافيه الحالي.

10000 paid/10000 debt إلى 8000: الدفع ثابت، التسديد 8000، والفرق 2000
سعة/credit متتبع. 8000 paid/8000 debt إلى 10000: الدفع ثابت، outstanding
2000. لا قبض أو توزيع نقد جديد، ولا دفتر تسديد موازٍ.

## الترتيب والذرّية والإعادة

الأقفال: READ COMMITTED، financial well lock الحالي، operational well،
session، work، account، ثم الصفوف المالية. لا يُحمل قفل work/session ثم
يُنتظر قفل C0.2 المالي. C1 يحمل operational well ثم session ولا يطلب
قفلًا ماليًا، لذلك يسبق C2 قفل session بقفل النطاق ولا ينتظر النطاق
وهو يحمل session. التحقق من السياق بعد الانتظار إلزامي.
الإصدار اللاحق للفاتورة يتبع financial→operational→session أيضًا؛ لا
يحمل session ثم ينتظر FK البئر بينما C1 يحمل البئر وينتظر الجلسة.

كل N ينتظر تطبيق N-1؛ النتيجة pending/attempt_started=false لا تحجز
أمر مصالحة إذا لم يبدأ العمل أصلًا. مالية N تقرأ تصحيح N نفسه حتى مع
وجود تصحيحات تشغيلية أحدث. financial_applied_revision منفصل في العمل
والنموذج المالي، ولا يغير مؤشر التشغيل أو إيصال C1 الأصلي.

sync.processed_commands هو سجل الأمر المالي أيضًا. الأمر والحمولة
الكَنونية (النطاق، الفاعل، التصحيح، المراجعة، posted_at ومنطقة زمن سياق
الخادم posting_timezone) ثابتان؛ الإعادة
ترجع النتيجة الأصلية، بما فيها review. تغيير سياق تحت الأمر نفسه مرفوض.
يمكن لأمر محاولة جديد مخول إعادة معالجة review بسياق صريح جديد لأن
كل الأطفال السابقين تراجعوا؛ بعد applied تُرفض هوية محاولة جديدة.
المصادر الفرعية ثابتة، ولا يحمل مصدر ناجح سابق سياقًا مختلفًا.

الاشتقاق والتحرير والنشر والقيد وإعادة التوازن والعدادات وapplied كلها
داخل معاملة فرعية واحدة. التحقق المباشر يستعمل validators C0.1/C0.2
الموجودة قبل مغادرة النطاق القابل للتراجع، دون SET CONSTRAINTS ALL.
حماية تاريخ C2 مؤجلة لوقت الالتزام وتُفحص مباشرة أيضًا. عند review
يتراجع الأطفال والعدادات والنشر جميعًا؛ يبقى فقط عداد المحاولة وسببها
ونتيجتها في work وprocessed command. لا تراجع للتصحيح التشغيلي المقبول.
الأخطاء التشغيلية غير المصنفة (مثل انقطاع/تعارض قفل) تفشل المحاولة
ذرّيًا دون قبول مالي كاذب، وتبقى قابلة للاستعادة بهوية الأمر نفسها.
