# Booking Scheduler Architecture — عقد معمارية P2

**التاريخ:** 2026-10-04 (محدّث 2026-10-08)
**الحالة:** ق-135 باقٍ العقد المعماري المعتمد. التنفيذ اللاحق لـP2 Phase 2B دُمج عبر PR #58 وأثبت Candidate A سحابيًا؛ **Candidate A = READY FOR Q-137 REVIEW**، لكن **q-137 = NOT ADOPTED** ولا يوجد تفعيل Production أو Cron دائم.
**القرار المرجعي:** ق-135 (معتمد معماريًا 2026-10-06)؛ ق-134 والثوابت 748 و761–764 نافذة دون تغيير.
**النطاق:** P2 من `BOOKING_AUTOMATION_IMPLEMENTATION_PLAN.md`؛ لا يشمل P3–P8.

## 1. الهدف والواقع الحالي

الهدف لم يتغير: انتقال الحجوزات يحتاج مصدر إيقاظ يعمل حتى لو كان التطبيق مغلقًا، مع بقاء قرار الأعمال الذري داخل منفذ P1-B. منذ اعتماد ق-135 نُفذت وأُثبتت Phase 2B: مسار `Supabase Cron → Edge Adapter → DB execution`، الهوية التقنية المنفصلة عن Actor/Operator، الحماية من التكرار والتزامن، حالات رفض التفويض، kill switches، monitoring correlation، وتدوير الاعتماد. الدليل الكامل في `docs/audit/P2_AUTOMATED_EXECUTION_PHASE2_CLOUD_PROOF.md`.

هذا الإثبات **لا يعني نشر Scheduler إنتاجي دائم** ولا اعتماد ق-137. Job الإثبات أزيلت بعد القياس، وCandidate A جاهزة للمراجعة فقط. كما لا يعني أن طبقة Discovery العامة للآبار المتعددة أصبحت Production orchestration؛ إثبات Phase 2B ركز على الحدود التقنية والتنفيذ الذري والمراقبة. NEXT قبل P3 هو قبول الهاتف ثم مراجعة ق-137.

## 2. حدود المسؤولية

| الطبقة | المسؤولية المقترحة | ما لا تملكه |
| --- | --- | --- |
| `Runtime` | بعد حسم تقنيته لاحقًا: إصدار نبضة زمنية موثوقة، تسجيل المحاولة، كشف التأخر والفشل. | اختيار الحجز أو إغلاق الجلسة أو تسويتها. |
| `Adapter` | طلب Discovery، تنظيم المرشحات وإعادة المحاولة، تمرير نسخة السلسلة ومعرف الأمر عبر مسار مخوّل. | تقرير أهلية نهائية من قراءة قديمة أو تجاوز هوية التنفيذ. |
| `Business Execution` | إعادة فحص التفعيل والجلسة والسلسلة والحجز تحت الأقفال، ثم إغلاق الحالية وبدء التالية ذريًا. | اختيار تقنية الإيقاظ. |

المسار المقترح: `Runtime → Adapter → Discovery → Adapter → ops.execute_booking_transition`. لا يعني رجوع صف من Discovery إذنًا أو نجاحًا؛ الاستجابة المعتمدة تأتي من منفذ P1-B وحده.

## 3. Discovery: قراءة المرشحات فقط

الواجهة المرشحة للتصميم هي `ops.get_booking_transition_candidates`؛ اسم وتوقيع مقترحان لا دالة موجودة. تراجع، من بيانات الخادم، تفعيل `core.well_settings.booking_auto_transition_enabled`، وسلسلة `ops.booking_transition_chains` بحالة `active` ونسختها `decision_revision`، وجلستها الحالية المفتوحة المحجوزة، والحجز التالي المؤكد غير المستهلك، والزمن الموثوق `started_at + expected_duration_minutes` لا `scheduled_end` القديمة. يجب أن يكون الحجز التالي مستحقًا وفق ترتيب اختيار P1-B نفسه.

المرشح يحمل على الأقل البئر والسلسلة والجلسة الحالية والحجز التالي ونسخة قرار السلسلة ووقت الملاحظة الخادمي. نسخة إعداد التفعيل `booking_auto_transition_revision` مختلفة عن نسخة قرار السلسلة ولا تحل محل `p_expected_revision`. يلزم تمييز التوقف أو الانتظار أو القرار المعلق والحالة الفائتة قبل عرض المرشح بوصفه قابلًا لمحاولة التنفيذ؛ تفاصيل هذه السياسة ما زالت مفتوحة. لا تقفل Discovery الصفوف طويلًا ولا تغيّر حالة الأعمال ولا تضمن بقاء ما قرأته صحيحًا.

## 4. Execution وحدود الهوية

يبقى `ops.execute_booking_transition(uuid, bigint, uuid)` المنفذ الوحيد لانتقال P1-B. يحرس وضع ON، جلسة واحدة مفتوحة محجوزة، سلسلة `active` مطابقة، CAS على `decision_revision`، بلوغ النهاية التشغيلية، والحجز التالي المستحق، ويجمع الإغلاق المالي والبدء ودورة أمر `sync` في معاملة واحدة. لا يعيد Adapter كتابة هذه الشروط ولا يستدعي دالتي الإغلاق والبدء منفصلتين.

النواة الحالية تتطلب `auth.uid()` حقيقيًا، وصلاحية تنفيذها مسحوبة من `public` و`anon` و`authenticated` و`service_role`. كونها `SECURITY DEFINER` يحدد سياق صلاحيات جسم الدالة بعد استدعاء مخوّل؛ **لا يمنح Scheduler حق `EXECUTE` تلقائيًا، ولا ينشئ `auth.uid()` أو صلاحية أعمال للمستدعي**. لم يُحسم بعد كيف يصل Runtime غير التفاعلي إلى استدعاء مخوّل مع الحفاظ على هوية الفاعل والتدقيق والصلاحيات. لا يُسمح بحل ذلك بهوية مشغّل مصطنعة أو تجاوز RLS أو كشف النواة للتطبيق. أي مسار تفويض جديد يحتاج قرارًا وتنفيذًا واختبارًا مستقلين قبل التفعيل.

## 5. الوقت، التكرار والحالات الفائتة

- وقت الاستحقاق والملاحظة من الخادم، لا من ساعة الهاتف. أول بدء في السلسلة يدوي دائمًا.
- يمر Adapter بمعرف أمر ثابت لنفس محاولة الانتقال المنطقية عند إعادة المحاولة؛ شكل اشتقاقه أو حفظه لم يُحسم. لا يولد معرفًا جديدًا لكل Retry فينشئ محاولة أعمال مختلفة.
- تعدد النبضات أو العمال لا يكفي لإثبات انتقالين؛ يحسم منفذ P1-B الحالة تحت الأقفال ونسخة السلسلة، ويجب اختبار هذا التكامل مع Adapter فعليًا.
- لا تُعالج لحظة تنفيذ فائتة ببدء في الماضي أو بدء متأخر صامت. حد التأخر الذي ينقل الحالة إلى مراجعة بشرية، وطريقة حفظه، قراران مطلوبان قبل التنفيذ.
- التوقف الطارئ والانتظار والتمديد ومقطع توقف مفتوح لا يتحولون إلى انتقال ببلوغ الوقت وحده؛ تُحدد بواباتهم باختبار مستقل اتساقًا مع 763–764.

## 6. قرار Runtime المؤجل وبدائله

1. مجدول داخل القاعدة إن ثبت توفره وصلاحيته وتشغيله ومراقبته في المشروع السحابي.
2. عامل خارجي موثوق إذا تعذر الخيار الأول أو لم يستوفِ عقد الهوية والمراقبة.
3. توقيت الهاتف ليس المصدر الوحيد لـP2؛ يظل مسار Offline المحلي اللاحق ضمن P4، وله مصالحة تمنع ازدواج الأثر مع الخادم.

لا يُعتمد أي بديل أو تقنية أو وتيرة تشغيل الآن؛ قرار `Runtime` مؤجل إلى إثبات القدرة والهوية والتشغيل والمراقبة في البيئة المستهدفة. تفصل الواجهة بين Runtime وAdapter كي يمكن تبديل وسيلة الإيقاظ دون تغيير Discovery أو منفذ الأعمال.

## 7. الفشل والمراقبة والتوسع

يلزم تمييز: لا مرشحات، مرشح صار قديمًا، تعارض نسخة، مانع أعمال، فشل بنية تحتية، وانتقال نُفذ فعلًا. تسجل محاولات الفشل والتأخر وتُنبه المشغّل من دون الادعاء بوصول إشعار لم يثبت. لا تعتبر استجابة Discovery ولا إرسال التنبيه نجاحًا للانتقال.

للتوسع المستقبلي إلى آبار ومستأجرين وعمال متعددين: تتولى طبقة Adapter توزيع العمل وحدود الدفعات وإعادة المحاولة والمراقبة، مع عزل المستأجر ومنع الاستحواذ المزدوج؛ وتبقى سلطة قرار الأعمال في منفذ P1-B نفسه. لا تُضاف آلية حجز عمل أو جدول جديد قبل بيان الحاجة واختبارها.

## 8. ضمانات عدم كسر المستخدمين الحاليين

هذه شروط قبول للتنفيذ اللاحق، وليست نتائج اختبار لهذه المسودة:

- يبقى وضع الانتقال لكل بئر غير مفعّل ما لم يُفعّله المشغّل المخوّل صراحةً؛ لا يغيّر إنشاء Discovery أو Adapter إعدادات الآبار القائمة.
- يبقى بدء أول حجز يدويًا، ولا تتغير عقود البدء والإكمال اليدوي أو الجلسات المفتوحة عند إضافة وسيلة إيقاظ.
- لا تتغير حمولات أوامر الهاتف القديمة أو دلالات `pending/review` ونتائج إعادة إرسالها؛ لا يصبح الهاتف ملزمًا بتقنية Runtime المختارة.
- تظل Discovery قراءة فقط ونواة P1-B غير مكشوفة للعميل؛ لا تُضاف صلاحية تنفيذ عامة أو مسار إغلاق/بدء موازٍ.
- يُختبر التوافق مع المسارات الحالية والتزامن قبل التفعيل؛ يتطلب النشر اللاحق بوابة تشغيل وتراجع آمنًا يوقف الإيقاظ دون قطع الجلسات الجارية أو محو سجلاتها.

## 9. الحالة بعد Phase 2B ومعيار الإغلاق

أُغلقت موانع Cloud proof اللازمة لرفع Candidate A إلى **READY FOR Q-137 REVIEW**. البواقي ليست دليل فشل لـP2 Phase 2B، لكنها شروط قبل Production: نضج `pg_net`/Vault، مرور Authorization مؤقتًا في `net.http_request_queue`، عدم وجود Runtime دائم منشور، وقبول الهاتف/Offline وسباق الهاتف مع الخادم.

لا يُعتمد Candidate A رسميًا إلا بقرار ق-137 صريح. وقبل الانتقال إلى P3 في خطة المشروع الحالية، يُستكمل قبول الهاتف المتفق عليه: Online-first ثم cache/transition Offline، missed-start بلا وقت مختلق، الإشعارات/Device Readiness، واختبارات Android الفعلية. التحقق السحابي أو CI لا يحل محل القبول الميداني.
