## التاريخ والمعادلة الحاكمة

جدول جديد واحد: billing.account_credit_application_adjustments.
يحفظ الأصل application_id وحدث C0 وهوية المصدر والمراجعة والأصل الجامع،
والطلب الكامل والسبب الحرفي والفاعل والوقت وحالة accepted أو
financial_review_required وسبب المراجعة وربط القيد.
الصفوف غير قابلة للتعديل/الحذف، وأصل application/source/payment لا يكتب.

billing.effective_account_credit_applications هو المعادلة الواحدة:

`effective = original - accepted releases + accepted restores`.

يعرض كذلك original amount وreleased وrestored؛ طلب المراجعة لا يغير
المبالغ. حدود الإدراج تحت قفل التطبيق: `0 <= effective <= original`.
الاستعادة لا تتجاوز صافي التحرير، ولا تتجاوز المتاح أو دين الفاتورة.
ما فوق أصل التطبيق يحتاج application جديدًا عبر C0، لا تضخيم القديم.

## عكس مصدر الرصيد

معادلة C0 تبقى:

`available = issued - effective applications - restored_to_payment - held`.

receivable_review يصف عاقبة مستهلكة تنتظر التسوية؛ ليس مالًا إضافيًا يطرح
من المتاح مرة أخرى. عكس المصدر بعد تحرير التطبيق يرى المتاح الجديد
ويعيده إلى تخصيصه الأصلي أو يحجزه حسب عقد C0. لا يحرر حجز الدفع مرتين.

إذا سبق طلب عكس قيمة مستهلكة وترك receivable_review_minor>0، فإن تحرير
التطبيق أو استعادته لا يحسم تلك المراجعة تلقائيًا. يحفظ الطلب بحالة
financial_review_required / source_reversal_review_required، بلا تغيير
effective أو available أو قيد. هذا يمنع إحياء قيمة سبق طلب إلغائها.
لا تمحو الحزمة سجل المراجعة القديم أو تخترع تسوية ذمة له؛ تسويته الصريحة
مهمة لاحقة. عكس المصدر مع held/restored فقط يظل متوافقًا بالمعادلة أعلاه.

## المحاسبة والفترات

قيد التطبيق الأصلي في C0: مدين 2000، دائن 1100.
تحرير جزء منه: مدين 1100، دائن 2000 بالمقدار المحرر بالضبط.
الاستعادة: مدين 2000، دائن 1100 بالمقدار المستعاد.
يستعمل post_customer_credit_entry ثم finance.post_journal_entry دون
cashbox أو حساب نقد أو payment. كل قيد جديد مربوط بحدث التعديل، ومنه
بالأصل والمصدر، والقيد الأصلي يظل مرحلًا ومحفوظًا.

posted_at سياق محاسبي داخلي ثابت للهوية، ويمكن اختيار فترة مفتوحة لاحقة
دون إعادة فتح الفترة التاريخية. إن رفض الكاتب الحاكم الفترة المغلقة،
تتراجع المعاملة الفرعية بكل آثارها المالية، ثم يُحفظ الحدث والتعديل
بحالة financial_review_required / accounting_period_closed بلا قيد أو
تغير رصيد. التعرف على هذا الرفض محدد برسالة الكاتب الحالي؛ لا ابتلاع
عام لأخطاء أخرى. exact replay يحفظ نتيجة المراجعة؛ لا يتحول إلى قبول
صامت بعد فتح فترة لاحقًا.

المراجعة محفوظة أيضًا عند عدم توفر الرصيد للاستعادة، أو نقص الدين، أو
حالة فاتورة غير مؤهلة/ذات deducted_in_cycle_id. لا سالب أو تعديل توزيع
تاريخي لإخفاء النقص. حدود المبلغ/التحرير غير الصحيحة ترفض وفق SQLSTATE
23514، والطلب/الهوية غير الصحيحين أو changed replay وفق 22023.

التحرير/الاستعادة المقبولان يبطلان دورات C0 غير المعتمدة بالعقد القائم،

لقطة approved/paid. مدخل الالتزام يتبع used الفعال مرة واحدة؛ لا يفسر
التحرير كتحصيل أو الاستعادة كقبض. لا فروق توزيع خاصة بالجلسة هنا.

ترتيب الكاتب: قفل البئر المالي، ثم هوية المصدر، ثم الحساب، ثم الدفع
الممول، ثم الرصيد، ثم التطبيق، ثم الفاتورة. C0 apply/reverse يشتركان
بقفل البئر/الرصيد، لذلك التحرير والإنفاق والاستعادة متسلسلة دون إنفاق
مزدوج. الحراس الصفية والتفرد/التحقق المؤجل مكملة للقفل لا بديل عنه.

اختبار المالك المستقل يستعمل اتصالين حقيقيين عبر dblink وUnix socket
في قاعدة محلية قابلة للمحو مع تصريح GUC. يستعمل حاجزًا بعد إدراج التعديل
وpg_blocking_pids لإثبات انتظار الثاني للأول، ثم يفحص أربع حالات:
تحرير 800/800 ضد فعال 1000، تحرير مع إنفاق، استعادة 800/800 ضد سعة 1000،
وتكرار مطابق يتسابق مع الأصل. التجهيز محفوظ بين الجلسات، ويعاد بناء
القاعدة بعده؛ لا حذف للتاريخ المالي بغرض التنظيف.
