# Executive Summary

**التاريخ:** 2026-10-06

**الحالة:** مراجعة عقد معماري فقط. لا SQL، ولا Migration، ولا Grant، ولا
API أو Edge Function أو Scheduler منفذ، ولا تفعيل Runtime.

**القرارات الحاكمة:** ق-135 وق-136 معتمدان بوصفهما
`Adopted (Architecture & Governance)` فقط. لا يرفع هذا التقرير حالتهما إلى
`Implemented` أو `Verified` أو `Production-Ready`، ولا ينشئ ق-137.

**الحكم:** يمكن حل تعارض `auth.uid()` من دون إنشاء منفذ أعمال ثانٍ. الحل
الأقل اتساعًا هو مدخل أتمتة داخلي ضيق يصادق هوية تنفيذ تقنية مستقلة، وينشئ
`Trusted Automation Execution Context` لا يستطيع HTTP body إنشاؤه، ثم يستدعي
نفس `ops.execute_booking_transition` بعد إعادة تحقق ذرية من التفويض والحالة.
تبقى P1-B منسق الانتقال الوحيد، وتبقى دوال الإغلاق والبدء التابعة لها جزءًا
من المعاملة نفسها.

يفصل العقد ثلاثة أطراف لا يجوز دمجها:

| الطرف | المعنى |
| --- | --- |
| Business Actor | `actor_kind=system` و`actor_ref=booking_automation_system`؛ فاعل أثر آلي يستند إلى تفويض أعمال سابق صالح. |
| Technical Executor | خدمة أو مكوّن تقني مصادق عليه، قابل للإبطال والتدوير، يحمل `executor_id` و`credential_ref` غير سريين. |
| Responsible Operator | المشغّل البشري الحقيقي المسؤول ميدانيًا، ويحفظ في `operator_profile_id`. |

الخيار A، `Supabase Cron → Edge Function Adapter → Discovery → P1-B`، اجتاز
مراجعة قدرة المنصة وفق الدليل المقدم: Cron وEdge وVault والسجلات مدعومة، و
`cron.job_run_details` متاح بعد تفعيل `pg_cron`. لكنه لم يصبح Runtime نهائيًا:
`pg_cron` و`pg_net` غير مفعّلين في المشروع، ولا توجد وظيفة P2 أو مهمة، والأهم
أن مدخل التنفيذ الموثوق وإعادة التفويض الذرية والإيقاف والإقرار والتدقيق لم
تنفذ أو تُختبر بعد.

# Current P1-B Identity Conflict

الواقع الحالي ليس مشكلة HTTP أو Grant منفردة، بل تعارض دلالي ممتد عبر سلسلة
الاستدعاء:

1. `ops.execute_booking_transition` يقرأ `auth.uid()` إلى `v_actor` ويرفض
   `NULL`. يبني بصمة الأمر من إصدار العقد والبئر و`expected_revision`، ثم
   يستدعي `sync.begin_command` قبل أقفال الأعمال. عند النجاح يمرر `v_actor`
   إلى بدء الجلسة ويعيده في `executed_by`.

2. `ops.complete_irrigation_session` يعيد قراءة `auth.uid()`، ويشترط
   `iam.has_well_permission(..., 'session.complete')`، ويستخدم الفاعل في
   معاملات الوقود وفي `audit.audit_logs.user_id`.

3. `ops.start_booking_session_core` يعيد قراءة `auth.uid()`، ويرفض إذا لم
   يساوِ `p_operator_profile_id`، ثم يشترط صلاحية `session.start`. ويستدعي
   مسار بدء الجلسة بهوية الفاعل البشرية.

4. `iam.has_well_permission` يثبت السلطة من تعيين بئر نشط حيث
   `well_assignments.profile_id = auth.uid()`. لذلك لا يستطيع فاعل نظامي
   المرور من هذا المساعد من دون انتحال ملف بشري.

5. `audit.audit_logs.user_id` يقبل `NULL` بنيويًا، لكنه يُملأ حاليًا بالفاعل
   البشري في عقد الإكمال. أما `ops.irrigation_sessions.operator_profile_id`
   فهو `NOT NULL` ومرجع إلى `iam.profiles`، ودلالته الحالية متداخلة مع من
   بدأ السجل.

6. P1-B مسحوبة الصلاحية من `public` و`anon` و`authenticated` و
   `service_role`. كون الدالة `SECURITY DEFINER` لا ينشئ `auth.uid()` ولا
   يمنح حق استدعائها ولا يثبت تفويض أعمال.

وعليه، الحلول الآتية مرفوضة: السماح عند `auth.uid() IS NULL`، صناعة JWT
بشري، إنشاء مستخدم أو ملف مشغّل وهمي، تمرير مشغّل بشري بوصفه منفذ الأثر، أو
اعتبار `service_role` Actor أعمال.

# Proposed Automated Execution Contract

المسار المقترح هو:

```text
Scheduler Runtime
        ↓ wake-up only
Edge Function Adapter
        ↓ authenticates technical caller
Authenticated Technical Executor
        ↓ narrow internal invocation
Internal Automation Entry Point
        ↓ constructs trusted context; no business approval yet
Atomic Authorization Revalidation
        ↓ same database transaction and lock order
ops.execute_booking_transition (existing P1-B executor)
        ↓ complete + settle + start, or reject atomically
Business Receipt + Audit Correlation
```

## ما يثق به النظام

- نتيجة تحقق مشفر من اعتماد تقني مخصص، بعد فحص أنه نشط، غير مبطل، صحيح
  للبيئة والمشروع والغرض، ومقيد بعملية انتقال الحجوزات فقط.
- `executor_id` و`credential_ref` اللذان يشتقهما المدخل الموثوق من سجل
  الاعتماد المحقق، لا من body.
- `actor_kind=system` و`actor_ref=booking_automation_system` اللذان يثبتهما
  المدخل الداخلي ثابتين.
- حقائق قاعدة البيانات المقفلة وقت القرار: المستأجر والبئر والتفويض
  والتعيين والإعداد والجلسة والسلسلة والحجز والمراجعات والسياسة.
- وقت قاعدة البيانات عند الملاحظة والقرار، لا ساعة Runtime أو العميل.

## ما لا يثق به النظام

- أي `actor_ref` أو `actor_id` أو `operator_profile_id` أو tenant أو booking
  يأتي من HTTP body بوصفه حقيقة أو تفويضًا.
- نتيجة Discovery، لأنها مرشح قديم محتمل وليست تصريحًا.
- `service_role`، أو نجاح JWT/HTTP وحده، أو امتلاك اتصال قاعدة البيانات،
  بوصف أي منها Actor أعمال.
- توقيت Runtime، أو revision مرسل، أو حالة ON مخزنة في Adapter، من دون إعادة
  قراءتها والتحقق منها ذريًا.
- `HTTP 2xx` أو نجاح Cron أو وجود `pg_net.request_id` بوصفه نجاح أعمال.

## حد مسؤولية Edge Function

تنتهي مسؤولية Edge عند: مصادقة المستدعي التقني، رفض الاعتماد المجهول أو
المبطل، ضبط حجم الدفعة والمهلة، إنشاء `attempt_id` وربط `runtime_run_id`،
الحفاظ على `command_id` نفسه في الإعادة، تصفية شكل المدخل، استدعاء المدخل
الداخلي، وتصنيف النقل والنتيجة المجهولة. لا تختار Edge المشغّل، ولا تقرر
سريان التفويض، ولا تثق بمرشح Discovery نهائيًا، ولا تغلق أو تبدأ جلسة.

يبدأ قرار الأعمال الحقيقي داخل قاعدة البيانات، عند مدخل الأتمتة الداخلي،
ويكتمل فقط بإعادة التحقق الذرية داخل معاملة P1-B وتحت أقفالها. يجب ألا توجد
نافذة commit أو استدعاء منفصل بين قرار التفويض وبين الإغلاق والبدء.

# Technical Execution Identity

الهوية التقنية المقترحة كعقد، لا كتنفيذ، هي هوية خدمة مخصصة مثل
`booking-transition-executor`، منفصلة تمامًا عن `auth.users` و`iam.profiles`.
خصائصها الإلزامية:

- معرف ثابت غير سري `executor_id`، ونطاق بيئة ومشروع وغرض محدد.
- اعتماد مخصص مستقل عن مفاتيح التطبيق وعن هوية المستخدمين، لا يستخدم Actor
  أعمال ولا يحول `service_role` إلى Actor.
- قابلية الإبطال الفوري، والانتهاء، والتدوير مع تمييز كل نسخة اعتماد.
- نطاق واحد على الأقل: استدعاء مدخل انتقال الحجوزات الداخلي فقط؛ لا صلاحية
  عامة على `ops`، ولا قراءة أو كتابة عشوائية.
- عدم قبول هوية المنفذ من body أو header وصفي غير موقع؛ الهوية نتيجة التحقق
  من الاعتماد نفسه.

## Dedicated secret/API key

يمكن أن تكون هوية Cron إلى Edge سرًا/API key عالي العشوائية ومخصصًا لهذا
المسار، بشرط ألا يكون مفتاحًا عامًا أو `anon` وألا يعاد استخدامه خارج P2.
التحقق منه يثبت Execution Identity فقط؛ لا يمنح بئرًا أو مشغّلًا أو قرار
ON. لا يعتمد العقد النهائي نوع المفتاح الآن؛ يمكن استبداله لاحقًا باعتماد
قصير العمر أو توقيع خدمة من دون تغيير Business Actor.

## Vault reference

قيمة السر تحفظ في Vault أو secret store الخاص بالبيئة، لا كنص مكشوف في
Cron job أو مستودع الكود أو جدول أعمال أو سجل. تحتفظ طبقة التدقيق بمرجع غير
سري مثل alias وإصدار اعتماد، `credential_ref`، يكفي للقول أي نسخة استُخدمت
ولا يكفي لاسترجاع السر. تدوير الاعتماد ينشئ مرجعًا جديدًا، وتبقى السجلات
التاريخية تشير إلى المرجع القديم بعد إبطاله.

## Edge Function authentication

يجب أن تتحقق Edge بنفسها من الاعتماد المخصص ومن غرضه وبيئته وحالته؛ لا يكفي
تعطيل `verify_jwt` أو نجاح فحص منصة عام. وبعد ذلك تستخدم قناة داخلية ثانية
مقيدة إلى قاعدة البيانات أو إثبات خدمة قصير العمر. لا يُعاد إرسال سر Cron
بوصفه حقل أعمال، ولا يُسجل في logs أو `business_receipt`.

الاختيار النهائي بين اعتماد اتصال قاعدة مخصص ضيق أو assertion خدمة موقع
ومحدود العمر يبقى قرار تنفيذ لاحقًا. في الحالتين يجب أن تستطيع قاعدة البيانات
تمييز executor المصرح من أي حامل آخر لـ`service_role`؛ وإلا بقيت الهوية
التقنية غير مثبتة داخل حد الأعمال.

# Business Actor Model

العقد الثابت للانتقال الآلي هو:

```text
actor_kind = system
actor_ref  = booking_automation_system
```

لا يأتي الحقلان من HTTP أو Discovery أو العميل. يثبتهما مدخل الأتمتة الداخلي
بعد مصادقة Execution Identity، ولا يسمح باختيار Actor آخر عبر معاملات
الاستدعاء.

يرتبط Actor بالسياق الآتي، ويعاد اشتقاقه من قاعدة البيانات:

- `tenant_id`: من ملكية `well_id` الفعلية، لا من body.
- `well_id`: معرف مرشح فقط عند الدخول؛ يجب إثبات وجوده ونطاقه وعزل مستأجره.
- `authorization_source`: مرجع التفويض التشغيلي الساري وقرار ON الحالي،
  مع نسختهما وصاحب القرار البشري التاريخي. صاحب القرار ليس Actor كل انتقال.
- `operator_profile_id`: المشغّل البشري المسؤول الحالي، المحسوم من تعيين
  وتفويض ساريين وقت القرار.

Actor النظام لا يملك صلاحية مستقلة. إن انقطع أي رابط في السلسلة
`owner → active delegation → one responsible operator → explicit ON`، يفشل
الانتقال مغلقًا. ولا يؤدي رفض انتقال مستقبلي إلى قطع الجلسة الجارية.

# Authorization Revalidation

قبل أي أثر، وفي المعاملة نفسها التي تنفذ P1-B، يعاد التحقق من جميع الشروط
التالية. أي شرط مفقود أو ملتبس أو قديم يؤدي إلى رفض كامل بلا إغلاق أو بدء
جزئي:

1. البئر موجود، و`tenant_id` مشتق منه، وملكيته الحالية صحيحة.
2. تفويض المالك التشغيلي موجود، نشط، غير منتهي أو مسحوب، ويغطي البئر وفعل
   انتقال الحجوزات الآلي.
3. يوجد مشغّل مسؤول صالح واحد بالضبط. الصفر رفض، والتعدد غير المحسوم رفض.
4. تعيين ذلك المشغّل للبئر نشط ومتسق مع مصدر التفويض.
5. لم يتغير المشغّل منذ قرار التفعيل، أو توجد إعادة تفويض وتأكيد ON جديدان
   متوافقان معه.
6. الأتمتة ON الآن، ونسخة `automation_revision` توافق نية الأمر.
7. المفتاح العام للأتمتة غير مفعّل للإيقاف الطارئ.
8. حالة الأتمتة الخاصة بالبئر قابلة للتنفيذ وليست suspended أو
   pending re-authorization.
9. توجد سلسلة واحدة صالحة في الحالة `active`، و`decision_revision` مطابق.
10. توجد جلسة حالية مفتوحة واحدة، محجوزة، وهي جلسة السلسلة الحالية.
11. يوجد حجز تالٍ واحد وفق ترتيب P1-B، مؤكد، غير مستهلك، ولم يتغير أو يُلغَ.
12. بلوغ النهاية التشغيلية الموثوقة من وقت الخادم.
13. سياسة التأخر تسمح بالتنفيذ الآن؛ الطلب المتأخر خارج الحد يرفض إلى مراجعة
    بشرية، بلا catch-up تلقائي.
14. لا pause أو انتظار مفتوح أو توقف طارئ أو قرار معلق أو مانع طاقة/مضخة.
15. `policy_version` ونسخة سياسة الأتمتة اللتان دخلتا البصمة ما زالتا نافذتين.
16. بصمة نية `command_id` تطابق tenant والبئر والسلسلة والجلسة والحجز
    والمراجعات وحالة التفويض وActor؛ لا إعادة استخدام لمحتوى مختلف.
17. الاعتماد التقني ما زال صالحًا عند المدخل الداخلي. إبطاله يمنع محاولة
    جديدة، لكنه لا يمحو إقرارًا تاريخيًا سبق اعتماده.

يجب تعريف ترتيب أقفال موحد لاحقًا يشمل بوابة الإيقاف والتفويض قبل ترتيب
P1-B الحالي، وتلتزم به كل مسارات تعديل الحالة ذات الصلة لتجنب deadlock.
التحديد التنفيذي لذلك خارج هذه الجولة.

# P1-B Compatibility Strategy

أقل تعديل معماري ممكن يتكون من أربعة أجزاء مترابطة:

1. **Internal Automation Entry Point:** مدخل غير مكشوف لـFlutter أو `api.*`،
   لا يملك منطق إغلاق/بدء. يصادق Execution Identity ويثبت Actor النظام ويولد
   `Trusted Automation Execution Context`.

2. **Explicit execution mode:** سياق صريح `human` أو `automation`، لا يُشتق
   من كون `auth.uid()` فارغًا. المسار البشري لا يقبل mode من العميل؛ يشتقه من
   جلسة Auth. المسار الآلي لا يختلق Auth user؛ يبنيه المدخل الداخلي وحده.

3. **Separate authorization helper:** يبقى `iam.has_well_permission` حارس
   الإنسان كما هو دلاليًا. يضاف مستقبلًا مساعد تفويض مخصص لعملية انتقال
   الحجوزات الآلية، لا مساعد صلاحية عام، يعيد التحقق من سلسلة التفويض وActor
   والإيقاف والمراجعات تحت الأقفال. نجاحه لا يمنح صلاحيات لعمليات أخرى.

4. **Context-aware dependent calls:** تستقبل نواة الإكمال والبدء من P1-B
   سياقًا داخليًا موثوقًا يفصل Actor عن المشغّل المسؤول. في mode البشري تبقى
   فحوص `auth.uid()` و`session.start/complete` كما هي. في mode الآلي لا يجري
   bypass؛ يجري فحص التفويض الآلي المخصص، مع تمرير `operator_profile_id`
   المحسوم من القاعدة وتسجيل Actor النظام.

يمكن أن يبقى الاسم الحاكم `ops.execute_booking_transition` والتنسيق الحالي
كما هما مفهوميًا، مع refactor داخلي يتيح السياق الموثوق. المدخل الجديد ليس
منفذ أعمال ثانيًا؛ هو بوابة مصادقة وتكوين سياق تستدعي P1-B في المعاملة
نفسها. ممنوع أن يستدعي `complete_irrigation_session` و
`start_booking_session_core` منفصلتين.

لا يصلح transaction-local setting يكتبه أي مستدعٍ بوصفه سياقًا موثوقًا ما
لم يكن إنشاؤه محصورًا داخل boundary غير قابل للاستدعاء العام ومقترنًا بهوية
تقنية محققة. الأفضل دلاليًا سياق typed صريح لا يستطيع body تكوينه.

# Operator Identity Semantics

`operator_profile_id` هو المشغّل الميداني المسؤول الحقيقي، حتى عندما يكون
`actor_kind=system`. لا يعني من أرسل HTTP، ولا من أيقظ Cron، ولا من نفذ
السطر البرمجي، ولا من أكد واقعة ميدانية لم يرها.

قواعد القبول:

- مشغّل بشري واحد صالح ومفوّض ومُعيّن للبئر وقت القرار.
- توافقه مع `authorization_source` ونسخة التفعيل الحالية.
- عرض التقارير مستقبلًا لحقيقتين منفصلتين: «المشغّل المسؤول» و«بدأها/نقلها
  النظام».

قواعد الرفض:

- لا يوجد مشغّل صالح.
- يوجد أكثر من مشغّل محتمل ولا توجد قاعدة أعمال محسومة تحدد المسؤول.
- تغير المشغّل بعد ON ولم تحدث إعادة تفويض وتأكيد صريحان.
- يرسل Runtime أو العميل معرف مشغّل مختلفًا؛ القيمة تهمل كسلطة ويُرفض عدم
  التطابق.

# Kill Switch Contract

## A) Runtime Kill Switch

يوقف إنشاء نبضات أو طلبات جديدة، ويمنع Adapter من بدء دفعات إضافية. يجب أن
يكون قابلًا للتفعيل والإلغاء بواسطة مسؤول تشغيل محدد، مع وقت وسبب وتدقيق،
وأن يظهر في المراقبة. هذا مستوى احتواء سريع وتقليل حمل، وليس ضمان أعمال.

## B) Atomic Business Kill Switch

بوابة داخل قاعدة البيانات يعاد فحصها تحت القفل قبل القرار النهائي في كل
محاولة. إذا كانت OFF/blocked ترفض P1-B الانتقال الجديد بلا أثر جزئي. يجب
أن تشمل بوابة عامة وبوابة لكل بئر، مع مراجعة monotonic أو نسخة تدخل بصمة
النية عند الحاجة.

تعطيل Cron وحده غير كافٍ: قد يكون طلب خرج من Cron، أو وصل Edge، أو ينتظر
اتصالًا/قفلًا، أو يعاد إرساله بعد timeout. لذلك يلزم الحارس الذري كي يرفض
أي طلب كان بالفعل في الطريق إذا سبق الإيقاف لحظة قرار الأعمال. إذا سبق
commit الإيقاف، يبقى الأثر المقبول تاريخًا صحيحًا ولا يُمحى؛ معالجة أثره
تكون بتصحيح أعمال مستقل لا rollback تشغيلي صامت. كلا المستويين لا يقطع
جلسة جارية تلقائيًا.

# Command / Attempt / Replay Semantics

## المعرفات

- `command_id`: هوية نية أعمال واحدة محددة. ثابت عبر جميع retries والعمال
  لنفس الانتقال، ولا يعاد استخدامه لأثر جديد بعد تغير الحالة أو إعادة
  التفويض.
- `attempt_id`: محاولة تقنية واحدة لإرسال/تنفيذ الأمر. جديد في كل retry،
  ولا يدخل في تعريف نية الأعمال.
- `runtime_run_id`: نبضة Scheduler أو تشغيل دفعة واحدة؛ قد تحتوي عدة أوامر
  ولكل أمر عدة محاولات. هو correlation تقني لا تفويض ولا idempotency key.

## بصمة النية المطلوبة

ترتبط البصمة منطقيًا على الأقل بـ:

```text
tenant_id
well_id
chain_id
current_session_id
next_booking_id
decision_revision
automation_revision
policy_version
authorization_source + authorization_version/state
actor_kind + actor_ref
contract_version
```

لا يدخل `attempt_id` أو `runtime_run_id` فيها. ويمكن أن يدخل `executor_id`
في سجل المحاولة، لا في نية الأعمال، حتى لا يغيّر تدوير المنفذ معنى الأمر.

## تقييم البصمة الحالية

البصمة الحالية في P1-B **غير كافية لعقد الأتمتة**. فهي تحتوي
`booking_execution_contract_version=113` و`well_id` و`expected_revision`
فقط. لا تثبت الجلسة الحالية أو الحجز التالي أو نسخة ON/السياسة أو حالة
التفويض أو Actor. كما أن التفرد الحالي `(tenant_id, command_id)` يمنع
إعادة استخدام المعرف بحمولة مختلفة عند اكتشافه، لكنه لا يمنع أمرين مختلفين
من تمثيل نية انتقال واحدة.

الإرجاع المبكر لإقرار `accepted` الحالي قبل فحص ON مناسب دلاليًا فقط بوصفه
إقرارًا تاريخيًا، بشرط أن تسبقَه مصادقة المنفذ وفحص نطاق الاطلاع، وأن تطابق
البصمة الكاملة المخزنة. لا يجوز أن يتحول replay إلى إعادة تنفيذ أو إلى
اختبار تفويض الأعمال الحالي.

كما أن رفض الأعمال الحالي يقع داخل معاملة تتراجع، فلا يضمن وحده سجلًا
دائمًا لكل محاولة مرفوضة أو مجهولة. يلزم عقد durable لمحاولات التنفيذ
ونتائجها خارج أثر الأعمال القابل للتراجع، من دون فتح مسار كتابة أعمال ثانٍ.

# Unknown Outcome Recovery

السيناريو الحاكم:

```text
Edge أرسلت command_id = C بمحاولة attempt_id = A1
        ↓
قاعدة البيانات نفذت P1-B واعتمدت الأثر وإقرار C
        ↓
انقطع الرد قبل أن تستلمه Edge
```

المسار الصحيح:

1. تسجل Edge النتيجة `unknown_pending_reconciliation` لـA1؛ لا تعلن نجاحًا
   ولا تولد `command_id` جديدًا.
2. تعيد المصالحة باستخدام **نفس** C وبصمة النية نفسها، بمحاولة A2 جديدة أو
   قراءة داخلية مخولة لسجل الأمر.
3. يقرأ المدخل الموثوق `sync.processed_commands` ضمن tenant والنطاق الصحيح.
4. إذا كان C `accepted` وبصمته مطابقة، يعاد `business_receipt` المخزن نفسه
   مع `result=replayed`. لا تعاد دوال الإغلاق أو البدء ولا أي أثر مالي.
5. إذا كان C ما زال `processing` أو مصيره غير محسوم، يبقى unknown ويعاد
   الفحص مع backoff ومراقبة؛ لا يقفز النظام إلى أمر جديد.
6. إذا لم يوجد C بعد إثبات أن المعاملة لم تعتمد، يمكن إعادة **نفس** C، لا
   أمر جديد، ما دامت النية لم تصبح فائتة أو قديمة. تغير الحالة يؤدي إلى
   رفض النية القديمة وإعادة Discovery بعد حسم مصيرها.

شرط القبول هو: جلسة واحدة، أثر مالي واحد، صف أمر واحد، وإقرار أعمال واحد
قابل لإعادة العرض. لا يمثل `HTTP 2xx` أو timeout أيًا من هذه الحقائق.

# Audit Contract

الحقول المنطقية المطلوبة لكل محاولة ونتيجة:

| الحقل | الدلالة |
| --- | --- |
| `actor_kind` | `system` للانتقال الآلي؛ منفصل عن هوية الاتصال. |
| `actor_ref` | ثابت داخليًا إلى `booking_automation_system`. |
| `executor_id` | المكوّن التقني الذي حمل المحاولة بعد التحقق. |
| `credential_ref` | alias/version غير سري للاعتماد المستخدم؛ لا السر. |
| `authorization_source` | مرجع التفويض وقرار ON الساريين، مع النسخة والحالة. |
| `tenant_id`, `well_id` | نطاق الأعمال المشتق والمتحقق. |
| `chain_id` | سلسلة الانتقال التي تعلقت بها النية. |
| `operator_profile_id` | المشغّل البشري المسؤول الحقيقي. |
| `current_session_id` | الجلسة التي قصد الأمر إغلاقها. |
| `next_booking_id` | الحجز الذي قصد الأمر بدءه. |
| `command_id` | نية الأعمال الواحدة. |
| `attempt_id` | المحاولة التقنية الواحدة. |
| `runtime_run_id` | نبضة/دفعة Runtime التي أنشأت المحاولة. |
| `decision_revision` | نسخة قرار السلسلة. |
| `automation_revision` | نسخة ON/حالة الأتمتة للبئر. |
| `policy_version` | نسخة سياسة التأخر والتوقف والتنفيذ. |
| `observed_at` | وقت اكتشاف المرشح من الخادم. |
| `attempted_at` | وقت إرسال/دخول المحاولة. |
| `decided_at` | وقت قرار الأعمال داخل قاعدة البيانات. |
| `result` | accepted/replayed/rejected/transient/unknown وغيرها. |
| `failure_reason` | سبب منظم لا يكشف أسرارًا. |
| `business_receipt` | الإقرار النهائي المرتبط بالأمر والجلسة والتسوية. |

يجب أن يستطيع المدقق بعد أشهر الإجابة منفصلةً عن:

- **Business Actor:** النظام الآلي الذي نُسب إليه أثر الانتقال.
- **Technical Executor:** الخدمة والاعتماد اللذان حملا المحاولة.
- **Responsible Operator:** الإنسان المسؤول ميدانيًا عن البئر والجلسة.

سجل المحاولة لا يستبدل `audit.audit_logs` أو `sync.processed_commands`، بل
يربطهما. لا يُملأ `audit_logs.user_id` بمشغّل بريء لإخفاء Actor النظام؛ يلزم
تمثيل صريح يحافظ على معنى السجلات البشرية السابقة وعلى append-only.

# Trust Boundary

| Input | Source | Trusted? | Revalidated where? |
|-------|--------|----------|--------------------|
| `well_id` | Discovery/Adapter | لا؛ selector فقط | الوجود والمستأجر والملكية داخل المدخل ثم تحت أقفال P1-B |
| `command_id` | مخزن نية Adapter الدائم | موثوق كمعرف بعد تحقق الشكل فقط؛ لا كدلالة | يطابق tenant والبصمة الكاملة في سجل الأوامر داخل DB |
| `attempt_id` | Edge Adapter | موثوق للربط التقني بعد مصادقة Edge؛ لا للأعمال | uniqueness/correlation في سجل المحاولة |
| `runtime_run_id` | Runtime/Edge | موثوق للربط فقط؛ لا للتفويض | مراقبة Runtime وسجل المحاولة |
| `actor_ref` | لا يقبل من الخارج | لا | يثبته المدخل الداخلي إلى `booking_automation_system` |
| `operator_profile_id` | قد يظهر كتلميح Discovery | لا | يحسم من التعيين والتفويض الحاليين ذريًا داخل DB |
| `chain_id` وbooking/session ids | Discovery | لا؛ قديمة محتملة | إعادة قراءة وقفل ومطابقة في P1-B |
| `decision_revision` | Discovery/Adapter | لا كحقيقة حالية | CAS على السلسلة المقفلة |
| `automation_revision` | Discovery/Adapter | لا كحقيقة حالية | إعداد البئر/حالة الأتمتة المقفلة |
| `policy_version` | Adapter | لا منفردًا | سياسة DB النافذة وبصمة الأمر |
| credential | Vault/header/connection | نعم فقط بعد تحقق مشفر من الصلاحية والنطاق والإبطال | Edge أولًا، ثم حد الاستدعاء الداخلي بصورة مستقلة |
| timestamps | Runtime/Edge | لا لقرار الأعمال | `observed_at/decided_at` من وقت الخادم؛ الخارجي telemetry فقط |
| authorization state | لا يقبل من body | لا | ملكية + تفويض + تعيين + ON تحت القفل داخل المعاملة |
| `tenant_id` | body/Discovery | لا | يشتق من البئر داخل DB ولا يسمح للمتصل باختياره |

# Security Failure Modes

| الحالة | Prevention | Atomic guard | Audit result |
| --- | --- | --- | --- |
| سرقة اعتماد تقني | اعتماد مخصص ضيق، Vault، انتهاء وتدوير وإبطال، عدم تسجيل السر، rate limits | فحص صلاحية الاعتماد ونطاق المشروع والغرض، ثم إعادة تفويض البئر؛ الاعتماد لا يخلق سلطة | `rejected_executor_revoked` أو accepted مع `executor_id/credential_ref` للتحقيق؛ تدوير فوري |
| إعادة HTTP request | نفس `command_id` والبصمة، `attempt_id` جديد، حماية replay على قناة المصادقة إن توفرت | سجل الأمر يعيد الإقرار المقبول ولا يعيد الأثر | `replayed` مرتبط بالمحاولة الجديدة والإقرار الأصلي |
| نبضة Scheduler قديمة | مدة صلاحية للنبضة ووقت خادمي وسياسة تأخر | مراجعات السلسلة/الأتمتة/التفويض وسياسة lateness | `rejected_stale_runtime_pulse` أو `rejected_late_transition` |
| تغير المشغّل أثناء الطريق | لا تثق بـoperator من Discovery، وتعليق ON حتى إعادة التفويض | حسم مشغّل واحد ومطابقة authorization version تحت القفل | `rejected_operator_changed_pending_confirmation` |
| سحب التفويض أثناء الطريق | revocation قابل للرصد فورًا، وعدم caching بوصفه إذنًا | فحص التفويض المقفل قبل الأثر | `rejected_revoked_delegation`؛ الجلسة الجارية لا تُقطع |
| إطفاء الأتمتة أثناء الطريق | Runtime stop + revision لكل بئر | قفل إعداد البئر وفحص OFF قبل القرار | `rejected_automation_disabled` |
| عمال مكررون | deterministic intent + claimant واحد + backoff | أقفال P1-B وCAS وسجل الأمر | accepted واحد؛ البقية `replayed` أو `stale/conflict` |
| `command_id` مختلفان لنفس الانتقال | مفتاح/بصمة فريدة للنية المنطقية، لا UUID عشوائي لكل عامل | intent-level uniqueness مع أقفال السلسلة؛ حالة P1-B تمنع أثرًا ثانيًا | أمر canonical مقبول؛ الآخر `duplicate_intent` أو stale |
| إعادة متزامنة لنفس `command_id` | صف أمر واحد وclaim ذري | أحدهما ينفذ، والآخر ينتظر ثم يعيد الإقرار؛ لا processing دائم | محاولة accepted وأخرى replayed؛ نفس receipt |
| طلب متأخر بعد تغير الحجز التالي | لا تعتمد مرشح Adapter القديم | قفل واختيار التالي ومطابقة البصمة والrevision من جديد | `rejected_next_booking_changed` أو `stale_revision` |
| عميل خبيث يستدعي المسار الداخلي | لا كشف عبر `api.*`، لا سر في الهاتف، اعتماد خدمة مخصص، أقل صلاحية، رفض مباشر للأدوار العامة | مدخل داخلي يثبت Execution Identity ولا يقبل mode/actor من body | `rejected_untrusted_caller` بلا أثر أعمال، مع redaction |
| حامل `service_role` يحاول تجاوز Edge | لا يعد `service_role` هوية executor؛ قناة DB تميز executor المخصص | رفض غياب إثبات المنفذ المخصص ولو كان الاتصال privileged | `rejected_executor_unproven` |
| DB commit نجح والرد انقطع | لا command جديد؛ حالة unknown ومصالحة | إعادة نفس command تعيد receipt المخزن | A1=`unknown_pending_reconciliation` ثم A2=`replayed` |
| global kill switch فُعل والطلب في الطريق | إيقاف Runtime لا يكفي | بوابة أعمال عامة مقفلة قبل P1-B | `rejected_global_automation_disabled` |

# Required Future Changes

هذه أقل مجموعة تغييرات مستقبلية محتملة، وليست إذنًا لتنفيذها الآن:

1. مدخل أتمتة داخلي واحد غير مكشوف للعميل، وهوية executor مخصصة وقابلة
   للإبطال والتدوير، مع أسرار في Vault و`credential_ref` غير سري.
2. refactor محدود لـP1-B والدوال التابعة لقبول سياق تنفيذ موثوق صريح، مع
   إبقاء مسار الإنسان وحراس `auth.uid()` دون إضعاف.
3. مساعد تفويض آلي مخصص للعملية يعيد فحص الملكية والتفويض والمشغّل وON
   والإيقاف والمراجعات داخل معاملة P1-B.
4. تمثيل durable لدورة التفويض ونسختها ومصدر ON إن كانت البيانات الحالية لا
   تثبتها على نحو غير ملتبس؛ المخطط الحالي يسمح بتعيينات متعددة ولا يقدم في
   الفهارس المقروءة إصدار تفويض آلي كاملًا.
5. بوابة إيقاف عامة ذرية وحالة تنفيذ لكل بئر، منفصلتان عن إيقاف Runtime.
6. توسيع بصمة نية الأمر، ومنع command IDs مختلفة للنية نفسها، وحفظ الإقرار
   التاريخي الكامل.
7. سجل محاولات/نتائج إضافي فقط يربط actor/executor/operator والمعرفات
   والمراجعات والأوقات والرفض والنتيجة المجهولة، من دون سر.
8. Discovery وEdge Adapter وRuntime والمراقبة، بعد اعتماد التقنية، مع عدم
   نقل أي قاعدة أعمال إليها.
9. اختبارات دائمة وسلبية وتزامنية وتكامل Cloud قبل التفعيل.

بعض العقد يمكن تنفيذه بلا schema change: حفظ السر في Vault، مصادقة Edge،
رفض حقول Actor/operator الواردة، تثبيت `attempt_id/runtime_run_id` في logs،
وRuntime kill switch في طبقة التشغيل. لكن حل `auth.uid()` داخل وظائف قاعدة
البيانات، والحارس الذري، والبصمة الدائمة، ودورة التفويض والتدقيق durable
تغييرات قاعدة بيانات؛ وبحسب عقد المشروع يجب أن تأتي في Migration لاحقة مع
اختبار دائم. لا يحدد هذا التقرير رقمًا أو SQL.

# Remaining Blockers Before Q-137

قبل ق-137 يجب إثبات عمليًا، لا توثيقًا فقط:

1. أن مشروع Supabase الفعلي يستطيع تمكين وتشغيل ومراقبة Cron/`pg_net` وEdge
   ضمن الخطة والحدود، مع وصول Vault وسجلات Edge، لا مجرد دعم المنصة العام.
2. أن الاعتماد التقني المخصص ينجح ويُرفض عند الخطأ والانتهاء والإبطال وتغير
   البيئة، وأن تدويره لا يقطع التدقيق ولا يكشف السر.
3. أن `anon` و`authenticated` والهاتف والاستدعاء المباشر و`service_role`
   غير المقيد لا يستطيعون بلوغ مدخل الأتمتة أو تشكيل Actor/context.
4. أن تغيير المشغّل وسحب التفويض وOFF والمفتاح العام، حتى أثناء السباق، تمنع
   الانتقال المستقبلي ذريًا ولا تقطع الجلسة الجارية.
5. أن same command concurrent retry يعيد receipt واحدًا، وأن command IDs
   مختلفة لنفس النية لا تنشئ أثرين، وأن تغير الحجز أو revision يرفض القديم.
6. أن ضياع الرد بعد commit يُصالح من `processed_commands` من دون جلسة أو
   رسوم أو تدقيق مكرر.
7. أن سياسة التأخر/pause/wait/التوقف والطاقة تمنع catch-up الصامت وتنتج سبب
   رفض منظمًا.
8. أن التدقيق يربط Actor وExecutor وOperator والاعتماد والنية والمحاولة
   والنبضة والإقرار، وأن logs لا تحتوي أسرارًا.
9. أن المراقبة تفرق بين نبضة ناجحة، HTTP ناجح، رفض أعمال، انتقال مقبول،
   unknown، وتراكم تأخر، مع إنذار وتجربة kill switch.

حتى إغلاق هذه البوابات، Candidate A **مرشح معماري قابل للمتابعة** لا Runtime
نهائيًا ولا مبررًا لق-137.

# Decision Readiness

**A. هل يمكن حل تعارض `auth.uid()` دون إنشاء منفذ أعمال ثانٍ؟** نعم. بمدخل
مصادقة داخلي وسياق تنفيذ صريح ومساعد تفويض آلي مخصص، ثم استدعاء P1-B نفسها
في معاملة واحدة. لا يسمح الفرع بسبب `auth.uid() IS NULL` ولا ينتحل إنسانًا.

**B. هل يمكن الحفاظ على P1-B كمنفذ وحيد؟** نعم. يجب أن تبقى
`ops.execute_booking_transition` منسق الإغلاق والتسوية والبدء ودورة الأمر.
المدخل الداخلي boundary للهوية والتفويض، لا executor أعمال موازيًا.

**C. هل Candidate A جاهز بعد هذا العقد؟** اجتاز Platform Capability Review
وأصبح له عقد معماري متماسك، لكنه غير جاهز لاعتماد Runtime نهائي أو تفعيل.
تبقى عوائق التنفيذ والإثبات الذري والاعتماد والإبطال والإيديمبوتنس والمراقبة.

**D. ما الذي يجب إثباته عمليًا قبل ق-137؟** مصادقة المنفذ وتدويره وإبطاله،
رفض كل المستدعين غير المخولين، إعادة التفويض الذرية في السباقات، الإيقاف
بمستوييه، بصمة النية ومنع التكرار، unknown-outcome recovery، التدقيق الكامل،
ومراقبة Candidate A في مشروع Supabase الفعلي.

**E. هل نحتاج Migration لاحقة؟** نعم لحل تعارض وظائف قاعدة البيانات وتثبيت
الحارس الذري والبصمة والتدقيق/التفويض durable. يمكن تنفيذ أجزاء Edge/Vault
وRuntime kill switch وتنسيق telemetry بلا schema change، لكنها لا تكفي
للتفعيل.
