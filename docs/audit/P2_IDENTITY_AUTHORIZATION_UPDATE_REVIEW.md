# Summary

**التاريخ:** 2026-10-05

**النطاق:** تحديث توثيقي فقط لوثيقة هوية P2 ومسودة ق-136، استنادًا إلى Decision C الذي قرره المالك.
**الحالة:** المبادئ المصرّح بها من المالك معتمدة مصدرًا لهذا التحديث؛ صياغة ق-136 نفسها تبقى `Proposed` وتنتظر مراجعة المالك، ولا تعني تنفيذًا أو تفعيلًا.

فُصلت ملكية المورد عن تشغيله اليومي وعن هوية المحاولة التقنية. لم يتغير SQL أو Migration أو Grant أو API أو Edge Function أو Scheduler أو كود التطبيق؛ ولا يمنح هذا التوثيق صلاحية جديدة للمستخدمين الحاليين.

# Applied Principles

| المبدأ | الصياغة المضافة | الحد المقصود |
| --- | --- | --- |
| ملكية البئر | المالك صاحب الحق الأعلى ويمنح أو يسحب التفويض التشغيلي. | الملكية لا تعني أن واجهة V1 تتيح له كل أمر تشغيل مباشر الآن. |
| مسؤولية المشغّل | المشغّل المسؤول يدير التشغيل والحجوزات ويفعّل الأتمتة ضمن تفويض ساري. | `operator_profile_id` لهويته الميدانية، لا لهوية النظام. |
| فاعل الأعمال | `Actor Identity` جهة مخوّلة أصلًا للفعل والبئر؛ الأثر الآلي يستند إلى تفويض سابق. | التسجيل في Auth أو امتلاك حجز لا ينشئ حق تشغيل. |
| منفذ المحاولة | `Execution Identity` للمكوّن الذي نفذ المحاولة التقنية. | `Runtime` لا يصبح Actor ولا يمنح حق أعمال. |
| الأتمتة | تنفيذ تفويض موجود، لا مصدر تفويض جديد. | لا مستخدم وهمي ولا `service_role` بوصفه هوية أعمال. |

# Q-136 Changes

اقتصر التعديل في [مسودة ق-136](../memory/DECISIONS.md) على نصها: دُقّق تعريف `Actor Identity` و`Execution Identity`، وأضيف فصل حق المالك عن مهمة المشغّل، وثُبّت معنى `operator_profile_id` وحدّ فحص الملكية أو التفويض الصريح قبل التشغيل أو إدارة الحجز أو تفعيل الأتمتة. نُصّ أيضًا على أن `Runtime` ينفذ ولا يمنح صلاحية، وعلى أن قيد ON/OFF الحالي للمشغّل في V1 وتحكم المالك الحي المؤجل إلى P7 لم يتغيرا.

لم يتغير عنوان ق-136 أو حالتها `مقترح / Proposed` أو بقية القرارات. إضافة مبادئ المالك إلى المسودة لا تجعل المسودة `Adopted` أو `Implemented` أو `Verified`.

# Documentation Changes

أضيف قسم `Business Authorization Boundary` إلى [معمارية هوية المجدولة](../technical/BOOKING_SCHEDULER_IDENTITY_ARCHITECTURE.md)، وفيه تسلسل «مالك البئر ← التفويض ← المشغّل المسؤول ← تفعيل الأتمتة ← تنفيذ Runtime ← منفذ P1-B»، مع شرط `Ownership / Delegation Check` وحدود الهوية والتفعيل. عُدّل تعريف Actor والمنفذ التقني، وثُبّت أن `operator_profile_id` للمشغّل الحقيقي، واستُبعد الحساب الافتراضي بدل الاكتفاء بوصفه غير مفضل. بقي اختيار تقنية `Runtime` مؤجلًا وحالة الوثيقة `Proposed Study`.

التقرير السابق [عن حدّ التفويض](P2_IDENTITY_BUSINESS_BOUNDARY_REVIEW.md) كان مصدر تحليل الفجوة، و[مراجعة الهوية](P2_IDENTITY_CONTRACT_REVIEW.md) تحدد ما لم يحله هذا التحديث. لم تُعدَّل أي منهما أو [معمارية P2 العامة](../technical/BOOKING_SCHEDULER_ARCHITECTURE.md).

# Remaining Gaps

1. **مصدر التفويض وإبطاله في التنفيذ:** يلزم تحديد كيف يُثبت تفويض المالك للمشغّل لكل بئر وفعل، وما مصير ON عند سحب التفويض أو تبديل المشغّل، وكيف يُرفض انتقال بدأ بعد الإبطال دون المساس بانتقال سبق قبوله.
2. **التعارض مع العقد الحالي:** نواة P1-B والدوال التابعة تشترط `auth.uid()` البشري و`session.start`/`session.complete`؛ البدء يساوي `operator_profile_id` بالمستدعي، والتدقيق الحالي يربط `audit_logs.user_id` به. لم تُصمم بعد مواءمة آمنة لفاعل نظام دون انتحال مشغّل أو مسار أعمال ثانٍ.
3. **تدقيق الأثر الآلي:** يلزم فصل صاحب التفويض، والمشغّل المسؤول، وActor النظام، والمنفذ التقني، ومعرّف الأمر والمحاولة والنتيجة، مع الحفاظ على السجلات الإضافية القائمة وعدم نسبة فعل مالي إلى إنسان لم ينفذه.
4. **جاهزية P2:** لم تُحسم وسيلة إثبات هوية Runtime وحدود اعتماده، ولا سياسة الإيقاف والتأخر وإعادة المحاولة والتزامن مع أوامر الهاتف، ولا قدرة البيئة المستهدفة. لا يُعد وجود P1-B أو صياغة Decision C إثبات تشغيل سحابي أو إنتاجي.
5. **حد مالك البئر في V1:** Decision C يمنح المالك سلطة التفويض، لكن P1-A الحالي يحصر ضبط ON/OFF بالمشغّل المخوّل، وق-134 يؤجل التحكم الحي للمالك إلى P7. إن أراد المالك تفعيلًا مباشرًا الآن، يلزم قرار منفصل وتغيير منفذ ومختبر؛ هذا التحديث لا يفترضه.

# Approval Readiness

**النتيجة:** تحديث الوثيقتين جاهز **لمراجعة المالك**، لا للاعتماد التلقائي لمسودة ق-136 ولا لتفعيل P2. يراجع المالك خصوصًا صياغة العلاقة بين سلطة التفويض وحق المشغّل في تفعيل ON، وسياسة سحب التفويض أو تبديل المشغّل. بعد الموافقة يمكن استكمال عقد الهوية ومسار التفويض/التدقيق واختبارهما في جولة مستقلة؛ لا يُستنتج من هذه الوثيقة إذن بأي Migration أو Grant أو Scheduler أو اختيار ق-137.

**التحقق:** عُرض فرق الوثيقتين قبل حفظه؛ نجح `git diff --check` بعد الحفظ. لم تُشغَّل اختبارات قاعدة أو Cloud لأن الجولة توثيق فقط ولا تغيّر تنفيذًا.
