# دراسة مقارنة لاختيار بيئة تشغيل مجدولة انتقال الحجوزات — P2

**التاريخ:** 2026-10-05
**الحالة:** دراسة قرار؛ لا تعتمد بيئة تشغيل ولا تنشئ صلاحية أو تنفيذًا.
**النطاق:** إيقاظ انتقالات الحجوزات الخادمية بعد دمج PR #54؛ لا يشمل تنفيذ P3–P8 أو جدولة الهاتف المحلية.

## الخلاصة التنفيذية

**التوصية المشروطة:** اختبار الخيار **A** أولًا: `Supabase Cron → Edge Function (Adapter) → Discovery → ops.execute_booking_transition`، إذا أثبت المالك قدرة المشروع السحابي، وأُقرّ عقد هوية وتفويض وتدقيق آمن، وأغلقت بوابات التأخر والتوقف. هذا **ترشيح لإثبات صلاحية** لا اعتماد `Runtime` ولا إذن بتفعيله. الخيار **C** بديل احتياطي إذا تعذر إثبات A أو تشغيله بمراقبة موثوقة. الخيار **B** ليس تنويعًا مستقلًا عن A: واجهة Supabase Cron نفسها مبنية على `pg_cron`، وجدولة Edge Function تمر عادةً عبر `pg_net`. الخيار **D** يقلل شبكة HTTP لكنه يصطدم أكثر بعقد الهوية والعزل، فلا يوصى به. [توثيق Supabase Cron](https://supabase.com/docs/guides/cron)، [جدولة Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions).

**قرار الجاهزية:** لا يجوز اعتماد أو تشغيل أي خيار الآن. نواة P1-B تتطلب `auth.uid()` حقيقيًا، و`EXECUTE` مسحوب من `public` و`anon` و`authenticated` و`service_role`؛ لا يحوّل مفتاح خدمة أو `SECURITY DEFINER` ذلك إلى هوية أعمال أو تفويض. لم تُنفذ `Discovery` أو `Adapter` أو `Runtime`، ولم تثبت قدرة السحابة المستهدفة في هذه الجولة.

### سلسلة السلطة المطلوبة

`Runtime` يصدر نبضة فقط؛ `Adapter` يصادق مصدرها وينظم الدفعات وإعادة المحاولة؛ `Discovery` تقرأ مرشحين دون منح إذن؛ **P1-B وحده** يعيد الفحص تحت الأقفال وينفذ إغلاق الجلسة وتسويتها وبدء التالية في معاملة واحدة. لا يستدعي Adapter `ops.complete_irrigation_session` و`ops.start_booking_session_core` منفصلتين، ولا ينشئ مسار أعمال بديلًا. هذه الحدود مقررة في `BOOKING_SCHEDULER_ARCHITECTURE.md` ومسودة ق-135، وتحكمها ق-134.

النواة الحالية تبدأ بـ`auth.uid()` وترفض `NULL`، ثم تمرر الفاعل إلى مسار البدء وتُعيده ضمن `executed_by`. مفاتيح `service_role` تعرّف اتصالًا تقنيًا يتجاوز RLS، **ولا تنتج مستخدم Auth بشريًا**؛ والمنح تُفحص قبل RLS. حتى مع `SECURITY DEFINER`، يظل حق `EXECUTE` مطلوبًا. لذلك كل الخيارات التالية محجوبة بالعقد نفسه إلى أن يُعتمد تصميم هوية آلية محدود ومُدقق دون انتحال مشغّل أو تجاوز `auth.uid()` أو كشف `ops` للهاتف. [توثيق مفاتيح Supabase والصلاحيات](https://supabase.com/docs/guides/getting-started/api-keys).

### فجوة أعمال مستقلة عن اختيار Runtime

النواة تتحقق من `started_at + expected_duration_minutes`، وكون الحجز التالي `scheduled_start <= now()`، ثم تبدأه بزمن `clock_timestamp()`. لا يوجد في مقطع P1-B الظاهر حدّ أقصى صريح للتأخر؛ لذلك قد تتحول نبضة متأخرة إلى بدء لاحق بصمت ما لم تُحسم بوابة الفوات في عقد الأعمال وتُفحص داخل مسار التنفيذ الذري. كما لا يظهر حرس مستقل لمقطع توقف طارئ مفتوح في هذه النواة؛ لا تكفي تصفية Discovery لأنها قراءة قد تصبح قديمة. **هذا تعارض محتمل يحتاج إثباتًا باختبارات تنفيذية، لا حكمًا بأن الأثر وقع فعلًا**، مع الثابت 753 بشأن اللحظة الفائتة والثابتين 763–764 بشأن الانتظار والتوقف وحفظ الدقائق. لا تعالج تقنية الجدولة هذه الفجوة بذاتها.

## 2. معايير المقارنة المشتركة

أي خيار مقبول لاحقًا يجب أن يحقق ما يلي:

1. نبضة مستقلة عن فتح تطبيق الهاتف؛ أول حجز يبدأ يدويًا، ولا يُستدرك فوات البداية الصامتة أو بوقت مختلق.
2. اكتشاف مستحقات من ساعة الخادم ونسخة السلسلة، بقراءة محدودة/مجزأة حسب المستأجر؛ إعادة الفحص النهائي في P1-B. `booking_auto_transition_revision` ليس `decision_revision`.
3. هوية **Actor Identity** للأثر الآلي منفصلة ومصرح بها، وهوية **Execution Identity** للنبضة والوظيفة والمفتاح/الحساب؛ لا انتحال مشغّل ولا اعتبار `service_role` فاعل أعمال.
4. أقل صلاحية ممكنة لاستدعاء محصور، مع سجل تدقيق دائم يربط قرار التفعيل البشري ومحاولة النظام ونتيجة P1-B ومعرف الأمر والنسخة والبئر/المستأجر، دون حفظ أسرار أو حذف سجلات تدقيق.
5. `command_id` ثابت للانتقال المنطقي نفسه عند إعادة المحاولة مع الحمولة نفسها؛ تعدد النبضات أو العمال لا يولد أثرين. لا تُعتبر قراءة المرشحين أو HTTP 200 أو `pg_net.request_id` إثبات نجاح أعمال.
6. تصنيف صريح: لا مرشح، سبق التنفيذ/تغير النسخة، مانع أعمال، فوات يحتاج تأكيدًا، فشل عابر، وخطأ غير قابل للإعادة؛ مع مراقبة تراكم التأخر وإنذار مسجل لا يُدعى وصوله دون إثبات.
7. مفتاح إيقاف عالمي لنبضات المجدولة، وإعداد OFF لكل بئر، وتراجع يوقف المحاولات الجديدة دون قطع الجلسة الحالية أو محو سجل الأوامر.

## 3. الخيارات

### A) Supabase Cron → Edge Function → Adapter → P1-B

**المعمارية والمتطلبات:** مهمة دورية واحدة أو عدد محدود من المهام داخل مشروع Supabase تستدعي وظيفة Edge محمية. الوظيفة تصادق النبضة، تقرأ Discovery على دفعات، وترسل المرشحين عبر مسار تنفيذ داخلي مصرح به إلى P1-B. يلزم إثبات توافر Cron و`pg_net` في المشروع الفعلي، وظيفة Edge جديدة، إدارة سر/هوية تقنية، مسار تفويض قاعدة صريح، مراقبة النبضة والنتيجة، وقياس زمن الدفعات. تدعم Supabase الواجهة المرئية/SQL للمهام، وتستخدم `pg_cron` للمحرك، وتوثق اقترانه بـ`pg_net` لاستدعاء Edge Function؛ لا يُفترض أن نموذجها الإرشادي للمفتاح العام وحده يكفي لحماية نقطة تنفيذ أعمال. [Cron](https://supabase.com/docs/guides/cron)، [جدولة Edge](https://supabase.com/docs/guides/functions/schedule-functions).

**التوافق:** الأقرب إلى فصل `Runtime/Adapter/Execution` في مسودة ق-135 وإلى تفضيل مجدول القاعدة إذا ثبت توفره في الخطة. لا تعني هذه الأفضلية اعتماد ق-135 أو اختيار تقنية نهائيًا.

**الهوية والصلاحيات والتدقيق:** يمكن عزل مستدعي Edge بمفتاح تقني محدد والتحقق منه في المعالج؛ `verify_jwt=false` لخدمة غير تفاعلية يعني أن فحص المنصة لا يكفي وحده، ويجب مصادقة الطلب داخل الوظيفة. توثق Supabase نمط مفتاح `apikey` سري مخصص للخدمات، لكن عميل الإدارة الناتج يتجاوز RLS ولا يمثل Actor. لا يوجد اليوم تفويض لاستدعاء P1-B ولا `auth.uid()` صالح للمجدول؛ يحتاج عقدًا معتمدًا وتغييرًا لاحقًا محدودًا واختبارات رفض مباشرة. سجل `cron.job_run_details` أو سجل Edge تقني فقط؛ يلزم أثر أعمال دائم يميز الإنسان عن النظام. [مصادقة Edge](https://supabase.com/docs/guides/functions/auth-headers)، [أنماط حماية Edge](https://supabase.com/docs/guides/functions/auth).

**الفشل وإعادة المحاولة والتزامن:** `pg_net` يرسل HTTP بصورة غير متزامنة بعد اعتماد المعاملة ويعيد معرف طلب، لا نتيجة الانتقال. جداول طلباته/استجاباته غير مسجلة WAL، ونتائج الاستجابة الافتراضية قصيرة العمر؛ لا تصلح وحدها كدفتر تسليم دائم. يجب أن يعيد Adapter الاكتشاف لاحقًا عند غياب الإقرار، ويثبت `command_id` والحمولة، ويقرأ إقرار P1-B النهائي. السباق مع أوامر الهاتف يحسمه قفل P1-B و`decision_revision` واختبار تكامل، لا زمن Cron. [pg_net](https://supabase.com/docs/guides/database/extensions/pg_net).

**التكلفة/التعقيد/الإيقاف/الاختبار:** خدمة أقل عبر مزود واحد، لكن كل نبضة تستهلك موارد قاعدة ودعوة Edge، مع كلفة تتناسب مع التواتر والحجم؛ يجب قياس خطة المشروع وحدود الوظيفة قبل تحديد التواتر. يمكن إيقاف المهمة وفوق ذلك رفض التنفيذ عند OFF، مع مراقبة ألا توقف الجلسة الجارية. محليًا يمكن اختبار وظيفة Edge والمنطق والتنافس وفشل HTTP ببدائل مضبوطة؛ وجود Cron المحلي لا يثبت قدرة سحابة المشروع، ولا يثبت تشغيله مع التطبيق مغلقًا. تضع Supabase توجيهًا تشغيليًا لعدد المهام المتزامنة ومدتها، وحدودًا منفصلة لوظائف Edge. [Cron](https://supabase.com/docs/guides/cron)، [حدود Edge](https://supabase.com/docs/guides/functions/limits).

**خطر الإنتاج:** متوسط إلى عالٍ قبل إغلاق الهوية والفوات؛ تشارك جدولة SQL والبيانات مورد قاعدة واحدًا، وقد يعطي نجاح الجدولة انطباعًا خاطئًا بنجاح الانتقال.

### B) PostgreSQL pg_cron → pg_net → Edge Function أو RPC

**المعمارية والمتطلبات:** إدارة `cron.schedule` و`net.http_post` مباشرة، أو استدعاء RPC/دالة داخل القاعدة من المهمة. يلزم إثبات الامتدادين وإعدادات تشغيلهما وامتيازات إنشاء/إدارة المهمة، وإدارة الأسرار — مثل Vault إذا استُخدم HTTP — والمراقبة والترقية والصيانة. مسار **Edge** في B هو عمليًا التنفيذ منخفض المستوى للخيار A، لا محرك جدولة مستقل. مسار **RPC مباشر** مختلف لأنه يسقط Edge، ويحتاج Adapter داخليًا مصممًا ومصرحًا به؛ لا يجوز للمهمة استدعاء P1-B مكشوفًا أو تخطيه. [جدولة Edge](https://supabase.com/docs/guides/functions/schedule-functions)، [Cron](https://supabase.com/docs/guides/cron).

**التوافق:** مسار Edge متوافق بعد تنفيذ الطبقات لكنه يزيد مسؤولية SQL التشغيلية؛ مسار RPC قد يضع التحويل داخل القاعدة، فلا بد من حفظ فصل الاكتشاف والتنفيذ والمراقبة وعدم تحويل وظيفة SQL إلى منفذ أعمال ثانٍ.

**الهوية والصلاحيات والتدقيق:** مستخدم `pg_cron` أو مالك الوظيفة ليس `auth.uid()` ولا Actor أعمال. مسار HTTP يحتاج حماية الوظيفة كما في A؛ المسار المباشر يحتاج امتياز مهمة وقيد تنفيذ أضيق من منح عام، وتدقيقًا يسجل هوية المهمة والفاعل الآلي. لا يكفي `SECURITY DEFINER` أو `service_role`، ولا يجوز تعطيل RLS أو تزوير مطالبة مستخدم لتجاوز الحارس.

**الفشل وإعادة المحاولة والتزامن:** في HTTP تتكرر مشكلة `pg_net` غير المتزامن؛ نجاح المهمة قد يعني إرسال الطلب فقط. في RPC مباشر تظهر نتيجة SQL بوضوح أكبر، لكن إعادة المحاولة والتصنيف ومنع التداخل ما زالت لازمة؛ خطأ في معاملة الدفعة لا ينبغي أن يخفي آبارًا أخرى. قفل P1-B ونسخة السلسلة هما الحد النهائي أمام أوامر الهاتف؛ تعاد التجربة مع أوامر يدوية وOffline تصل متأخرة.

**التكلفة/التعقيد/الإيقاف/الاختبار:** قد يوفر دعوة Edge في فرع RPC لكنه يحمل قاعدة البيانات منطق التشغيل ومراقبته؛ لا يزيل تكلفة التنفيذ أو ضغط الاتصالات. إيقاف المهمة ممكن، لكن SQL طويل أو مهمة جارية يحتاجان خطة إيقاف لا تقتل معاملة أعمال نصفية. الاختبارات المحلية ممكنة إن وُجدت الامتدادات، أما القدرة السحابية وامتيازات الإدارة/المراقبة فغير مثبتة. خطر الإنتاج **عالٍ** إذا عُومل هذا الخيار على أنه حل تلقائي لمشكلة الهوية، أو استُخدمت صلاحية واسعة على `ops`.

### C) External Managed Scheduler → Edge Function/API

**المعمارية والمتطلبات:** خدمة جدولة مُدارة مستقلة — مثال مرجعي Google Cloud Scheduler — ترسل طلب HTTPS إلى نقطة Edge غير عامة، ثم Adapter وDiscovery وP1-B كما في A. بديل API خادمي ممكن فقط إذا كان endpoint مخصصًا ومحميا، وليس غلاف `api.*` يوسع صلاحيات الهاتف. يلزم حساب خدمة، مصادقة بين المزودين، أسرار/تدوير أو تحقق OIDC، مراقبة مزودين، زمن/منطقة تشغيل، وسياسة تكرار. توثق Google التسليم **مرة على الأقل** وإمكان تكرار الطلب، كما تدعم حساب خدمة وOIDC لأهداف HTTP؛ هدف خارج Google يجب أن يتحقق من الرمز بنفسه. هذا مثال تقني لا افتراض بأن المشروع يملك حساب Google أو أن Supabase Edge يتحقق من OIDC تلقائيًا. [ضمان التسليم](https://docs.cloud.google.com/scheduler/docs/overview)، [مصادقة أهداف HTTP](https://docs.cloud.google.com/scheduler/docs/http-target-auth).

**التوافق:** يحافظ على فصل الطبقات ولا يعتمد على امتدادات قاعدة Supabase؛ يُستخدم إذا فشل إثبات A أو لم تحقق مراقبته/موثوقيته المعايير. يضيف اعتمادًا على مزود آخر، لكنه يفصل نطاق فشل الإيقاظ عن قاعدة البيانات. لا يعني استقلال المزود ضمان نجاح الانتقال إذا تعطلت قاعدة Supabase.

**الهوية والصلاحيات والتدقيق:** OIDC أو سر مخصص يثبت **Execution Identity** للطلب بعد تحقق صحيح من التوقيع/الجمهور/المُصدر، ولا يخلق Actor أو `auth.uid()`؛ تظل فجوة P1-B والمنح كما هي. يسجل الدفتر ارتباط job/schedule time بمعرف الأمر وأثر الأعمال، مع منع تمرير مفاتيح قاعدة واسعة في URL أو سجلات مزود خارجي.

**الفشل وإعادة المحاولة والتزامن:** إعادة المحاولة من المزود قد تصل بعد نبضة لاحقة أو بعد تغيير الهاتف؛ يلزم dedupe منطقي وثبات الحمولة ومراجعة النسخة قبل P1-B. يتعذر اعتبار `2xx` نجاحًا إذا كان Adapter قد قبل العمل دون إتمامه؛ إمّا رد نتيجة أعمال مؤكدة ضمن المهلة، أو حالة durable قابلة للمصالحة. فوات الوقت لا يعالج بالاستدراك التلقائي. اختبارات محلية لمحاكاة HTTP/OIDC وتكرار الطلب، ثم تجربة Cloud مراقبة، لازمة.

**التكلفة/التعقيد/الإيقاف/الاختبار:** رسوم خدمة ثانية وتشغيل أسرار/سياسات ومراقبة بين مزودين؛ التكلفة المباشرة للوظيفة قد تكون صغيرة لكن كلفة التعقيد أعلى. إيقاف الوظيفة الخارجية ممكن مع بوابة تنفيذ داخلية مستقلة؛ يجب اختبار طلبات متأخرة بعد الإيقاف. خطر الإنتاج **متوسط إلى عالٍ** بحسب نضج المصادقة والتشغيل، ولا يقلل مخاطر الأعمال والهوية.

### D) Supabase Cron → Adapter داخل PostgreSQL → P1-B بلا HTTP

**مبرر الإدخال:** تعطي Supabase Cron خيار تنفيذ SQL/دوال مباشرة، وهو مقارن مفيد لمعرفة هل طبقة HTTP ضرورية فعلًا أم مجرد كلفة. [توثيق Cron](https://supabase.com/docs/guides/cron).

**المعمارية والمتطلبات:** نبضة SQL تنادي دالة Adapter داخلية محدودة الدفعة؛ هذه تقرأ Discovery، ثم تفوض إلى P1-B فقط. لا `pg_net` ولا Edge. يلزم تصميم عقد تشغيل/هوية وقيد صلاحية وتدقيق ومراقبة داخل القاعدة من الصفر، مع ضبط المهلة والحمل وعدم تعليق موارد قاعدة طويلة.

**التوافق والهوية/الصلاحية/التدقيق:** الفصل المنطقي ممكن، لكن حدود `Runtime` وAdapter تتداخل داخل قاعدة البيانات؛ حساب Cron لا يخلق `auth.uid()`، ولا يبرر منح `EXECUTE` عامًا أو انتحال مستخدم. التدقيق يحتاج تمييز مهمة قاعدة عن فاعل أعمال وإثبات علاقة قرار التفعيل البشري بالأثر؛ سجلات Cron التقنية لا تكفي.

**الفشل/التزامن/الكلفة/الإيقاف/الاختبار:** نتيجة SQL أقرب من HTTP إلى المعاملة، لكن تنفيذ دفعة كبيرة قد يطيل الأقفال ويؤثر على أوامر الهاتف؛ يظل P1-B الحاسم الذري، ويلزم عزل فشل كل مرشح ومصالحة الإعادة. أقل كلفة شبكة، أعلى حساسية لأداء القاعدة وتعقيد الصلاحيات. يمكن تعطيل المهمة لكن يجب عدم قطع جلسة أو إجهاض تسوية جارية. اختباره محليًا ممكن إن توفر Cron؛ السحابة غير مثبتة. **غير موصى به الآن**: لا ميزة حاسمة تحل مانع الهوية، ومخاطر ازدواج المسؤوليات وضغط القاعدة أعلى.

## 5. التوصية ولماذا

**اختيار الاختبار الأول: A، لا التفعيل.** يحتفظ بحدود القرار ق-135 المقترحة: Runtime صغير للإيقاظ، Adapter قابل للاختبار، وP1-B منفذ الأعمال الوحيد. واجهة Supabase Cron توفر إدارة ومراقبة مبدئيتين فوق محرك `pg_cron` نفسه؛ هي أقرب لنية الخطة الحالية بتفضيل مجدول القاعدة إن ثبتت ملاءمته، وتقلل نظام تشغيل خارجيًا. فرع Edge يجعل مصادقة المستدعي وتصنيف النتائج والدفعات أوضح من مهمة SQL مباشرة، دون أن يحل الهوية وحده.

**لماذا لا B أولًا؟** مسار Edge فيه هو تنفيذ منخفض المستوى لـA لا فائدة استقلال له؛ فرع RPC يقلل HTTP لكنه يضغط منطق التشغيل والامتيازات داخل القاعدة. **لماذا لا C أولًا؟** يضيف مزودًا ومراقبة/هوية عبر حدود سحابية قبل إثبات عجز الحل الأقرب للمشروع؛ يبقى البديل إذا تعذر إثبات توافر A أو موثوقيته. **لماذا لا D؟** يوفر قفزة شبكة لكنه لا يزيل مانع الهوية، ويزيد خطر إخفاء منطق Scheduler في SQL وصعوبة عزله عن موارد أعمال الهاتف.

**شرط الانتقال إلى C:** فشل اختبار قدرة Cron/`pg_net` على مشروع Supabase المستهدف، أو تعذر تشغيل/رصد A ضمن متطلبات التأخر والفشل والأسرار، بعد تقييم موثق وليس مجرد تخمين. إذا فشل عقد هوية P1-B نفسه، فلا ينتقل القرار إلى C بوصفه إصلاحًا؛ تُوقف كل الخيارات.

## 7. قرارات لازمة قبل أي Migration أو Grant أو API

1. اعتماد أو رفض ق-135 وق-136 بصيغة نهائية مع حدود `Runtime/Adapter/Discovery/Execution`، وتحديد ما إذا كان اختيار A قرارًا نهائيًا أو تجربة محددة بمهلة ومعيار توقف.
2. تحديد Actor آلي مشروع منفصل عن المستخدم البشري، ونسبة كل أثر إلى قرار التفعيل البشري وإلى هوية التنفيذ التقنية، وكيفية تمثيله داخل عقود P1-B التابعة دون تغيير معنى `auth.uid()` أو تمرير هوية مزورة. إذا تعذر ذلك دون تغيير عقد P1-B، يُقر التغيير اللازم صراحةً مع بقاء الدالة منفذ الأعمال الوحيد، ولا يُتجاوز الحارس في Adapter.
3. تحديد سطح استدعاء داخلي ضيق والامتيازات المطلوبة له وحده، ومن يملكها ومن يستطيع إبطالها، مع اختبارات رفض الاستدعاء المباشر عبر `api` أو أدوار الهاتف. لا منح شامل لـ`ops`، ولا افتراض أن `SECURITY DEFINER` تفويض.
4. تحديد دلالات «لحظة فائتة»، عتبة التأخر، التوقف الطارئ والانتظار، تصنيف ما يحتاج قرار مشغّل، ومتى يغلق/لا يغلق الحجز الجاري، ثم إثبات أن القرار النهائي داخل مسار ذري لا في Discovery وحدها.
5. تعريف `command_id` للانتقال المنطقي عبر نبضات وعمال وإعادة تشغيل، مع مفاتيح المستأجر والبئر والجلسة/السلسلة والنسخة، وإثبات ثبات الحمولة وحدود إعادة استخدام المعرّف.
6. تحديد وتيرة النبضة وحجم الدفعة وميزانية التأخر والمهلة والتوازي وآلية ACK والتنبيه والاحتفاظ بسجل التدقيق، بناءً على حجم الآبار وحدود الخطة الفعلية، لا على رقم عام للمورّد.
7. تحديد مفتاح إيقاف عالمي ومسؤولية تشغيله ومتى يستخدم OFF لكل بئر؛ الإيقاف يمنع محاولات جديدة ولا يلغي سجلات أو يمس الجلسة الحالية.

## Decision Readiness

- **هل نحن جاهزون لاعتماد Runtime؟** لا للاعتماد أو التفعيل الإنتاجي. نعم فقط لترشيح A كأول تجربة إثبات مشروطة.
- **النواقص:** قدرة سحابة المشروع غير مثبتة؛ ق-135/ق-136 مقترحان؛ لا هوية Actor آلي أو تفويض لاستدعاء P1-B؛ لا Discovery/Adapter/Runtime؛ سياسة الفوات والتوقف والحارس الذري لها غير مغلقة؛ لا اختبار تكامل أو مراقبة نجاح أعمال أو Kill Switch مجرّب.
- **القرار المقترح:** إبقاء الحالة `Proposed`، والموافقة فقط على بوابتي حسم العقد وإثبات قدرة A قراءةً وتجربةً غير إنتاجية لاحقًا بيد المالك؛ إن أخفق A يُدرس C، ولا تُحل مشكلة الهوية بتبديل المزود.
- **مستوى الثقة:** **Medium** في ترتيب البدائل بناءً على الكود المحلي ووثائق المورّد الرسمية؛ **لا ثقة كافية لاتخاذ قرار تشغيل** قبل دليل مشروع Supabase السحابي والاختبارات المذكورة.
