# Executive Summary

**التاريخ:** 2026-10-06
**الحالة:** تقرير مراجعة معماري مقترح للمالك؛ توثيق فقط، بلا تنفيذ أو صلاحيات أو تعديل في Runtime أو كود التشغيل.
**النطاق:** استكمال عقد هوية وتفويض Scheduler P2 بإضافة دورة حياة التفويض التشغيلي (Delegation Lifecycle)، وأثر سحب أو تغيير التفويض على الأتمتة، وسلامة الجلسات الجارية، وضمانات أوامر التزامن والإقرار التاريخي.

يستكمل هذا التقرير مواءمة عقد الهوية والتفويض مع المبادئ والسلوكيات المعتمدة من المالك:
1. مالك البئر هو صاحب الحق الأعلى على المورد ومصدر منح التفويض التشغيلي وسحبه.
2. المشغّل المسؤول هو المسؤول الميداني الفعلي عن البئر والجلسة (`operator_profile_id`).
3. الأتمتة تنفذ التفويض السابق ولا تنشئ صلاحية جديدة، ولا يمثل `service_role` أو `Scheduler` أو أي مستخدم وهمي فاعل أعمال.
4. سحب التفويض يمنع الانتقالات الآلية المستقبلية فورًا بفشل مغلق (fail-closed).
5. تغيير المشغّل المسؤول لا ينقل الأتمتة بصمت، ويستلزم إعادة التحقق والتأكيد الصريح قبل أي انتقال آلي جديد، مع منع الاستدراك الآلي المتأخر.
6. سحب التفويض أو تغيير المشغّل لا يقطع جلسة سقي جارية تلقائيًا أو بصمت.
7. منع الانتقالات الجديدة (Automation Disable) منفصل جوهريًا عن إيقاف جلسة السقي الجارية (Running Session Stop).
8. إعادة التفويض لا تعيد استخدام أمر انتقال قديم لتنفيذ أثر جديد، ولا تعيد تشغيل انتقال فات تلقائيًا؛ وإعادة إرسال أمر مقبول سابقًا (Replay) هي مجرد استرجاع للإقرار التاريخي.

تبقى مسودة ق-136 في حالة `مقترح / Proposed` بانتظار مراجعة المالك، ولا يمنح هذا التوثيق أي إذن بتنفيذ Migrations أو منح صلاحيات أو تفعيل المجدولة.

# Delegation Lifecycle

تحدد دورة حياة التفويض التشغيلي خمس حالات دقيقة تحكم العلاقة بين المالك والمشغّل ونظام الأتمتة:

```text
       [Grant]
          ↓
      (Active) ──[Change]──→ (Suspended / Non-executable)
          │                              │
       [Revoke]                     [Re-authorize]
          ↓                              ↓
    (Fail-Closed) ←──────────────────────┘
```

### A) المنح (Grant)
- يصدر التفويض التشغيلي بإرادة صريحة من مالك البئر (صاحب الحق الأعلى على المورد) لصالح مشغّل بشري محدد لمورد بئر معيّن.
- يثبت التفويض هوية المشغّل المسؤول ميدانيًا ونطاق صلاحياته المأذونة في تشغيل البئر وإدارة حجوزاته.
- لا ينشأ التفويض ضمنيًا بمجرد امتلاك حساب في `auth.users` أو ملف في `iam.profiles` أو وجود صلة بمزرعة أو حيازة حجز.

### B) السريان التشغيلي (Active)
- في ظل تفويض سارٍ وتعيين نشط، يمارس المشغّل المسؤول التشغيل الميداني وإدارة الحجوزات.
- يملك المشغّل المسؤول، ضمن حدود تفويضه الساري، ضبط وتفعيل خيار انتقال الحجوزات الآلية (ON) للبئر في مسار V1.
- الأتمتة المفعلة تنفذ إرادة المشغّل وتفويض المالك؛ ولا تكتسب الأتمتة أي سلطة مستقلة بذاتها.

### C) تغيير المشغّل (Operator Change)
- إذا تغيّر تعيين المشغّل المسؤول عن البئر (سواء باستبداله بمشغّل آخر، أو إعفائه، أو تعيين بديل):
  - **منع الانتقال الصامت (No Silent Transfer):** لا تنتقل ميزة الأتمتة بصمت أو تلقائيًا إلى المشغّل الجديد؛ لأن التفعيل الأصلي اقترن بمسؤولية المشغّل السابق وتفويضه.
  - **حالة غير قابلة للتنفيذ (Non-executable State):** تصبح الأتمتة معلقة وغير قابلة للتنفيذ لأي انتقالات مستقبلية فور رصد التغيير، حتى تتم إعادة التحقق من التفويض وتأكيد استمرار الأتمتة صراحةً.
  - **منع الاستدراك الآلي المتأخر (No Automatic Late Catch-up):** أي انتقال حجز استحق وقته أثناء فترة التغيير أو التعليق يُعامل كفرصة فائتة تتطلب مراجعة بشرية واعية، ولا يجوز للنظام تنفيذه آليًا بأثر رجعي بمجرد استقرار المشغّل الجديد.

### D) سحب التفويض (Revocation)
- يملك مالك البئر الحق المطلق في سحب التفويض التشغيلي من المشغّل في أي وقت.
- بمجرد سحب التفويض:
  - **فشل مغلق فوري (Fail-Closed):** تمنع أي انتقالات آلية مستقبلية وتفشل محاولاتها مغلقًا عند بوابة التحقق الذرية.
  - لا ينفذ أي انتقال حجز جديد (لا إغلاق مالي آلي ولا بدء حجز تالٍ آلي).
  - **سلامة الجلسة الجارية (Running Session Safety):** سحب التفويض لا يقطع تلقائيًا أو بصمت جلسة سقي جارية فعليًا في الحقل (انظر قسم سلامة الجلسة الجارية أدناه).

### E) إعادة التفويض (Re-authorize)
- إذا استلم مشغّل جديد (أو المشغّل السابق نفسه) تفويضًا تشغيليًا مجددًا من المالك:
  - تظل الأتمتة محجوبة ومعطلة إلى حين استيفاء شروط التفويض والتفعيل الصريحة، وتأكيد وضع الأتمتة بقرار جديد مسجل.
  - **منع إعادة تشغيل الانتقالات الفائتة (No Automatic Replay of Missed Transitions):** لا يعاد تنفيذ أي انتقال تجاوزه الوقت أثناء فترة انقطاع التفويض، وتُعامل مواعيد الانتقالات السابقة وفق سياسة المراجعة البشرية المستقلة.

# Operator Change Semantics

تغيير المشغّل المسؤول حدث أعمال جوهري ينقل المسؤولية الميدانية والقانونية والمالية:
1. **فصل الأتمتة عن هوية البئر المجردة:** الأتمتة ليست مجرد علم رقمي (Flag) على جدول البئر يستمر بالعمل تلقائيًا أيا كان المشغّل؛ بل هي أداة مسندة إلى مسؤول ميداني يمثله `operator_profile_id`.
2. **التعليق الفوري للانتقالات:** بمجرد رصد فك ارتباط المشغّل أو تغييره، تصبح المحاولات الآلية محظورة وتفشل مغلقًا (`rejected_authorization: operator_changed_pending_confirmation`).
3. **تأكيد الاستمرار:** لا تستأنف الأتمتة إلا بعد فحص تعيين المشغّل الجديد وتفويضه من المالك، وصدور تأكيد تفعيل صريح من المشغّل الجديد ضمن مسؤوليته الميدانية.
4. **حظر الاستدراك التراكمي:** منع النظام من تراكم الحجوزات غير المنفذة ومحاولة إطلاقها دفعة واحدة بعد تعيين المشغّل الجديد؛ ذلك يمنع الكوارث المائية والمالية الناتجة عن تشغيل المضخة في غير موعد المزارعين.

# Revocation Semantics

سحب التفويض التشغيلي من قبل مالك البئر قرار أعلى يُلزم النظام البرمجي بالانصياع الفوري:
1. **الفشل المغلق (Fail-Closed):** لا يُسمح بتنفيذ أي انتقال حجز آلي تالٍ بعد لحظة السحب. إذا حاولت مجدولة النظام أو وسيط التنفيذ استدعاء الانتقال، يُرفض الطلب فورًا عند الفحص الذري بسبب سحب التفويض (`rejected_authorization: revoked_delegation`).
2. **منع إنشاء التزامات مالية جديدة:** لا يقوم النظام آليًا باحتساب استهلاك حجز تالٍ أو بدء عدّادات جديدة بعد سحب التفويض.
3. **الحفاظ على التدقيق:** يوثق حدث السحب وهوية المالك الساحب وتاريخه الخادمي، مع عزل أي محاولات إيقاظ تقنية تصل بعد السحب وتسجيلها كمحاولات مرفوضة ومحمية.

# Running Session Safety

يؤكد العقد المعماري على الفصل الحاسم بين:
- **تعطيل الأتمتة (Automation Disable):** يمنع انتقالات آلية جديدة مستقبليًا (إغلاق آلي أو بدء حجز تالٍ آلي).
- **إيقاف الجلسة الجارية (Running Session Stop):** قرار ميداني وتشغيلي لإيقاف تدفق المياه والمضخة.

### مبررات الفصل:
1. **السلامة الزراعية والميدانية:** قطع المياه المفاجئ والتلقائي أثناء جريانها في قنوات الري قد يؤدي إلى تلف المحاصيل أو انفجار الأنابيب أو هدر الضغط المائي دون تسجيل سليم لعداد الساعات.
2. **دقة المحاسبة والقياس:** جلسة السقي الجارية تملك عدّاد بداية وقراءة موثقة ومزارعًا ينتظر حصته؛ إنهاؤها يتطلب إغلاقًا منظمًا يسجل قراءة العداد النهائية وسبب الإيقاف، إما يدوياً بواسطة المشغّل الميداني أو عبر مسار الطوارئ المعتمد.
3. **الامتثال للثوابت والقرارات:** يخضع إيقاف الجلسة الجارية لعقد الإيقاف التشغيلي والطوارئ المستقل (ق-134، الثوابت 763–764، ومسار `session.complete` المحروس)، ولا يترتب تلقائيًا على مجرد سحب تفويض الأعمال أو تغيير المشغّل في السجلات الإدارية.

# Retry and Replay Impact

يتكامل عقد دورة حياة التفويض مع معمارية التزامن والإيديمبوتنس (`sync`):
1. **دلالة نية الانتقال (`command_id`):** كل أمر انتقال يرتبط بنيّة أعمال فريدة مقيدة بـ: `(tenant_id, well_id, chain_id, current_session_id, next_booking_id, decision_revision)`.
2. **منع إعادة استخدام الأمر القديم بعد إعادة التفويض:**
   - إذا رُفض أمر انتقال بسبب سحب التفويض أو تغيير المشغّل، يُسجل رفضه.
   - إذا أُعيد التفويض لاحقًا، **يحظر قطعًا** استخدام نفس `command_id` القديم لفرض أثر تشغيلي جديد.
   - يتطلب أي انتقال جديد اشتقاق أمر انتقال جديد تمامًا بنيّة جديدة ووقت حالي وتأكيد سارٍ.
3. **دلالة Replay التاريخي:**
   - إذا أُعيد إرسال أمر انتقال سبق قبوله بنجاح في الماضي (`status = accepted` في `sync.processed_commands`)، فإن النظام لا ينفذ أي أثر تشغيلي أو مالي جديد.
   - يقتصر Replay على قراءة استرجاعية للإقرار التاريخي المخزن وإعادته للمتصل لتأكيد الإيديمبوتنس وحسم النتيجة المجهولة.
4. **عزل المحاولات المرفوضة:** تكرار محاولة أمر رُفض بسبب حالة التفويض يعيد نفس نتيجة الرفض ما دامت شروط الرفض قائمة، ولا يُفتح أي مسار لتجاوز الحظر.

# Q-136 Changes

تم تحديث مسودة ق-136 في [DECISIONS.md](../memory/DECISIONS.md) لتثبيت المعاني المعتمدة دون ترقية حالتها:
1. **إضافة البند 8:** تثبيت دورة حياة التفويض التشغيلي (Grant, Active, Change, Revoke, Re-authorize)، وحظر الانتقال الصامت للأتمتة عند تغيير المشغّل، وإلزام إعادة التحقق والتأكيد الصريح، ومنع الاستدراك المتأخر، وتطبيق الفشل المغلق عند السحب مع حماية الجلسة الجارية.
2. **إضافة البند 9:** تثبيت الفصل التام بين تعطيل الأتمتة وإيقاف الجلسة الجارية، وتأكيد قواعد `command_id` في منع استخدام أوامر قديمة بعد إعادة التفويض، وحصر Replay في الإقرار التاريخي.
3. **تحديث المخاطر ومتطلبات التنفيذ:** النص صراحة على ضرورة التحقق المستمر الذري لسلسلة التفويض حتى P1-B، وتدقيق أحداث دورة الحياة وسبب رفض الانتقالات.
4. **تثبيت الحالة:** بقيت حالة ق-136 **مقترح / Proposed** بصورة قاطعة، مع الإشارة إلى أنها تنتظر مراجعة المالك واعتماده.

# Remaining Gaps

تظل الفجوات الآتية قائمة وتمنع اعتبار P2 جاهزًا للتنفيذ أو التفعيل البرمجي:
1. **تعارض حارس `auth.uid()` في النواة الحالية:** تشترط `ops.execute_booking_transition` ودوال الإغلاق والبدء الحالية هوية `auth.uid()` حقيقية لمشغّل يملك `session.complete` و`session.start`، وتسجل التدقيق بهويته البشرية. لا يوجد حاليًا مسار فاعل نظام آلي منفذ دون انتحال بشري.
2. **تنفيذ الفحص الذري لدورة حياة التفويض في القاعدة:** لم تُنفذ بعد في SQL آليات كشف سحب التفويض أو تغيير المشغّل تحت قفل P1-B؛ يتطلب ذلك تصميمًا دقيقًا ومختبرًا يمنع أي تأثير على زمن المعاملة.
3. **اعتماد `Runtime` والوسيط التقني:** اختيار تقنية المجدولة لا يزال مؤجلًا بموجب مسودة ق-135، ولم يُعتمد بعد شكل الاعتماد المشفر أو قناة الاتصال الموثوقة القابلة للإبطال.
4. **واجهة المالك التشغيلية في V1:** مسار V1 الحالي يحصر ضبط ON/OFF بالمشغّل المخوّل فقط، بينما تحكم المالك المباشر مؤجل وفق ق-134 إلى P7. تمكين المالك من إجراءات فورية يتطلب قرارًا وتصميمًا مستقليْن.

# Approval Readiness

**الخلاصة:**
أصبح عقد هوية وتفويض P2 مكتملًا من الناحية المعمارية ومستوفيًا لدورة حياة التفويض التشغيلي وكافة المحددات الصادرة من المالك. الوثائق جاهزة بالكامل **لمراجعة المالك واتخاذ القرار**. لا يُعتبر ق-136 معتمدًا ولا يُرقى إلى `Adopted` أو `Implemented` أو `Verified` إلا بقرار صريح ومستقل من المالك.

| Item | Status | Blocking? |
| --- | --- | --- |
| Owner authority | Defined / Documented | No for review; Yes for V1 direct execution |
| Operator delegation | Defined / Documented | No for review; Yes for runtime execution |
| Operator change | Defined / Documented | No for review; Yes for runtime execution |
| Revocation | Defined / Documented | No for review; Yes for runtime execution |
| Running session behavior | Defined / Documented | No |
| Re-authorization | Defined / Documented | No for review; Yes for runtime execution |
| Q-136 readiness | Proposed (Pending Owner Review) | Yes for implementation |
